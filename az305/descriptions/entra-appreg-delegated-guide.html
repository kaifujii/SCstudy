② なぜ「アプリ登録」が最初のステップなのか

Entra ID で認証を行うには、まず「このアプリは存在する」と Entra ID に登録して認証の主体（アイデンティティ）を作る必要があります。アプリ登録なしでは、Entra ID はそのアプリが誰なのか判断できません。

③ 「委任された権限」とは何か ─ アプリケーション権限との違い

APIアクセス許可には2種類あります。今回のシナリオで使うのは「委任された権限（Delegated Permissions）」です。

✅ 委任された権限（Delegated）← 今回

  • ログインユーザーの代わりに API を呼ぶ
  • 「ユーザーが持っている権限の範囲内」で動作
  • トークンにユーザー情報が含まれる
  • ユーザーまたは管理者の同意が必要
  • Functions が EasyAuth でユーザーを認証して後続 API を呼ぶ場合に使用
VS

アプリケーション権限（Application）

  • ユーザー不在でアプリ自身として API を呼ぶ
  • バッチ・デーモン・完全自律サービス向け
  • トークンにユーザー情報が含まれない
  • 必ず管理者同意が必要
  • マネージド ID による client_credentials フロー

⚡ ポイント：On-Behalf-Of（OBO）フロー
Functions A がユーザーから受け取ったトークンを使って、Entra ID に「ユーザーの代わりに Functions B を呼びたい」と新しいトークンを要求する仕組みです。ユーザーの委任が連鎖します。

④ 具体的な設定手順

設定の全体ステップ
1
【最初のステップ】各 Functions のアプリ登録を Entra ID に作成する
Portal → Microsoft Entra ID → アプリの登録 → 新規登録
Functions A・B・C それぞれに1つずつ作成する。これで Client ID が払い出される。
2
呼び出される側（Functions B）の「スコープ（scope）」を定義する
Functions B のアプリ登録 → 「API の公開」→ スコープを追加
例：api://functions-b/API.Call というスコープを定義する。
3
呼び出す側（Functions A）に「委任された権限」を付与する
Functions A のアプリ登録 → 「APIのアクセス許可」→ アクセス許可の追加
→ 「自分のAPI」から Functions B のスコープ（API.Call）を選択
→ 種類は「委任されたアクセス許可（Delegated）」を選択する。
4
各 Functions で EasyAuth（組み込み認証）を有効化する
Functions アプリ → 認証 → ID プロバイダーの追加 → Microsoft
作成済みのアプリ登録を紐付けることで、コード変更なしでトークン検証が有効になる。
5
Functions A のコードで On-Behalf-Of フローを使って Functions B を呼ぶ
ユーザーから受け取ったトークンを使い、Entra ID から Functions B 向けの新トークンを取得して呼び出す。

✅ 漏洩リスクなし・管理コストゼロ
📌 まとめ：なぜ「委任された権限」なのか
  • 今回のシナリオは「ユーザーが操作する → Functions A → Functions B」というユーザーの操作起点のフロー
  • ユーザーの認証情報を起点にして、OBO フローで連鎖的にトークンを取得するため「委任された権限」が適切
  • 委任された権限はユーザーのトークンに乗っかるため、アプリ自身のシークレットが不要
  • もしユーザー不在のバックグラウンド処理（バッチ・デーモン）なら「アプリケーション権限」＋マネージド ID になる
⚠️ 試験頻出の引っかかりポイント
  • 「最初のステップ = マネージド ID を有効化」→ △：マネージド ID はシークレット不要だが、ユーザー委任フローではなくアプリ権限（Application）で動作する。ユーザー起点のフローには委任された権限が必要
  • 「アプリ登録は1つでよい」→ ❌：呼び出す側・呼び出される側それぞれにアプリ登録が必要
  • 「委任された権限はユーザー同意だけで使える」→ △：スコープの内容によっては管理者同意が必要な場合もある
  • 「EasyAuth を使えばコードを書かなくていい」→ △：トークン検証はコードレスだが、OBO フロー（B を呼ぶ処理）はコード実装が必要
