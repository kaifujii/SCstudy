Cluster Autoscaler

Cluster Autoscaler
ノード数を自動で増減する

AKSクラスターのノード数をワークロードの需要に応じて自動調整します。Pending状態のPodを検知してVMSSのノードを追加し、使われていないノードを削除します。Linux・Windows 両方のノードプールに対応します。

試験ポイント — 頻出問題

「Windows Server 2019 ノードを使用。スケールアウト時のプロビジョニング時間を最小化し、Windows Server コンテナの自動スケーリングをサポートしたい」

Virtual Node アドオンは Linux のみ対応。Windows Server コンテナに対応した自動ノードスケーリングができるのは Cluster Autoscaler のみ。

✅ Cluster Autoscaler — Windows Server ノードプール対応 + VMSS自動増減。これが唯一の正解
❌ Virtual Node with Virtual Kubelet ACI — アドオンは Linux のみ（Windows は手動インストール必要 = 「自動」にならない）
❌ HPA — Pod 数をスケールするだけ。ノード（コンピューティングリソース）を追加しない
Virtual Node & Virtual Kubelet

Virtual Node / Virtual Kubelet
ACIを「ノード」として扱い秒単位でスケール

Virtual NodeはAKSアドオンとして、Virtual Kubeletはその基盤のOSS技術として、Azure Container Instances(ACI)をKubernetesノードのように扱い、Podを秒単位でスケールします。Cluster Autoscaler（数分）との最大の違いはこの速度です。

HPA — Horizontal Pod Autoscaler

HPA
Pod のレプリカ数を CPU / メモリで自動調整

HPA は Kubernetes 標準の Pod スケーリング機能です。CPU やメモリの使用率を監視し、設定した閾値を超えると Pod 数を自動で増減します。Metrics Server が必要です（AKS 1.8+ では標準搭載）。

HPA の制御ループ

02 マニフェスト例

# HPA — CPU使用率70%をトリガーにPodを2〜10台でスケール apiVersion: autoscaling/v2 kind: HorizontalPodAutoscaler metadata: name: myapp-hpa spec: scaleTargetRef: apiVersion: apps/v1 kind: Deployment name: myapp minReplicas: 2 # 最小Pod数（0にはできない） maxReplicas: 10 # 最大Pod数 metrics: - type: Resource resource: name: cpu target: type: Utilization averageUtilization: 70 # CPU 70% を超えたらスケールアップ
試験ポイント

「Web アプリの Deployment を、CPU 使用率 80% を超えたら自動で Pod を増やしたい。最大 10 Pod、最低 2 Pod を維持したい」

✅ HPA — CPU使用率ベースのPodスケーリング。min/max設定対応。Kubernetes標準機能
❌ Cluster Autoscaler — Pod ではなくノード（VM）をスケールする
❌ KEDA — CPU ではなく外部イベント（キュー等）をトリガーにするもの。CPU ベースのスケールには HPA を使う
KEDA — Kubernetes Event-Driven Autoscaling

KEDA
外部イベントでPodを自動スケール（0台まで縮小可能）

KEDA は CNCF のプロジェクトで、Azure Service Bus・Event Hub・Storage Queue・Kafka などの外部イベントソースに基づいて Pod をスケールします。Scale to ZERO（完全に 0 Pod まで縮小）が最大の特徴で、HPA では不可能です。

03 よくある間違いと正しい理解

落とし穴 #1

「Virtual Node アドオンは Windows Server コンテナをサポートする」→ しない

Virtual Node アドオン（az aks enable-addons virtual-node）が自動作成するのは「virtual-node-aci-linux」のみ。Windows コンテナを ACI で動かすには Virtual Kubelet を手動でインストールする必要がある。つまり「自動」ではない。

✅ Windowsコンテナ + 自動スケーリング → Cluster Autoscaler（VMSS ベース）
❌ Virtual Node アドオンは Linux のみ。Windows は「手動インストール」が必要なため試験で「自動スケーリング」の選択肢にならない
落とし穴 #2

「KEDA は HPA の代替として同じワークロードに共存できる」→ できない

KEDA は内部で HPA を拡張する形で動作します。同一ワークロードに KEDA の ScaledObject と独立した HPA の両方を設定すると、互いに干渉してスケールが不安定になります。KEDA を使う場合は HPA を直接設定せず、KEDA に任せます。

✅ イベントドリブン → KEDA のみ設定。CPU/メモリ → HPA のみ設定。同一 Deployment には一方だけ
落とし穴 #3

「HPA だけで Pod もノードも自動スケールできる」→ ノードはスケールしない

HPA は Pod のレプリカ数を増やすだけです。Pod が増えてもノードのリソースが足りなければ Pod は Pending 状態になります。ノードを追加するには別途 Cluster Autoscalerが必要です。

✅ 完全な自動スケール = HPA（Podスケール）+ Cluster Autoscaler（ノードスケール）の組み合わせ

1

Windows Server + 自動スケーリング

AKS クラスターで Windows Server 2019 ノードを使用します。次の要件を満たすスケーリング方法はどれですか？
・スケールアウト時のコンピューティングリソースのプロビジョニング時間を最小化する
・Windows Server コンテナの自動スケーリングをサポートする

  • A. Virtual nodes with Virtual Kubelet ACI
  • B. Cluster autoscaler
  • C. Horizontal pod autoscaler
  • D. Kubernetes バージョン 1.20.2 以降を使用する
✅ 正解: B — Cluster autoscaler

Virtual Node アドオンは Linux のみ対応（virtual-node-aci-linux）。Windows Server コンテナには対応していません。Windows Server コンテナの自動スケーリングには Cluster Autoscaler が唯一の選択肢です。CA は Windows Server ノードプールに対応しており、Pending Pod を検知して VMSS を自動スケールします。

なぜAは不正解か: Virtual Node アドオンは Linux のみ。Windows を ACI で動かすには Virtual Kubelet を手動インストールする必要があり、「自動スケーリング」とは言えない。
なぜCは不正解か: HPA は Pod 数をスケールするが、ノード（コンピューティングリソース）は追加しない。「コンピューティングリソースのプロビジョニング」という要件を満たさない。
なぜDは不正解か: K8s バージョンはスケーリング方法ではない。
2

外部イベントベースのスケーリング

Azure Service Bus キューでメッセージを受信して処理する AKS アプリケーションがあります。要件は次のとおりです：
・キューのメッセージ数に応じて処理 Pod を自動スケールしたい
・メッセージがない夜間は Pod を 0 まで縮小してコストを最小化したい
最適なスケーリング方法はどれですか？

  • A. HPA（CPU ターゲット使用率 70%）
  • B. Cluster autoscaler（min-count: 0, max-count: 10）
  • C. KEDA（azure-servicebus スケーラー、minReplicaCount: 0）
  • D. Virtual Node（ACI を使用したバーストスケール）
✅ 正解: C — KEDA

「Service Bus メッセージ数でスケール」「0 Pod まで縮小」の 2 条件を同時に満たせるのは KEDA のみです。

なぜAは不正解か: HPA は CPU/メモリをトリガーにします。Service Bus のメッセージ数を直接トリガーにできない。また HPA は最低 1 Pod なので 0 Pod にできない。
なぜBは不正解か: Cluster Autoscaler はノード（VM）をスケールします。Pod 数をコントロールしない。また CA はメッセージ数をトリガーにしない。
なぜDは不正解か: Virtual Node は Pod を ACI 上で動かす手段であり、スケールのトリガーを定義するものではない。KEDA + Virtual Node の組み合わせなら可能だが、Dの選択肢はそうなっていない。
3

超高速バーストスケーリング

EC サイトの AKS アプリケーションで、セール時に突発的なトラフィックバーストが発生します。次の要件を満たすソリューションはどれですか？
・Linux コンテナのプロビジョニングを秒単位で完了させたい
・通常時はコストを最小化し、バースト時のみ追加リソースを確保したい
・Azure CNI ネットワークは既に設定済み

  • A. Virtual nodes アドオンを有効化し、KEDA でバースト時に Virtual Node 上の Pod を増やす
  • B. Cluster autoscaler（min: 1, max: 20）で VMSS を自動スケール
  • C. HPA（CPU 80%）で Pod を 1〜50 の範囲でスケール
  • D. Windows Server ノードプールを追加して Virtual Kubelet でスケール
✅ 正解: A — Virtual Node + KEDA

「秒単位」「Linux」「コスト最小」の 3 条件に最も合う構成です。KEDA がイベント（HTTP リクエスト数等）で Pod をスケールし、Virtual Node（ACI）が秒単位でそのPodを起動します。ACI は使った分だけの課金のため通常時のコストも最小化できます。Azure CNI 設定済みという前提条件も Virtual Node の要件を満たしています。

なぜBは不正解か: CA は VMSS ベースで VM 起動に数分かかる。「秒単位」の要件を満たさない。
なぜCは不正解か: HPA だけではノードも Pod のスケジュール先もないため、ノード追加がなければ Pending になるだけ。「秒単位」でもない。
なぜDは不正解か: 要件は「Linux コンテナ」。Windows ノードプールは不要。
4

技術の役割理解

次の AKS スケーリング技術のうち、「Pod のレプリカ数」ではなく「クラスターのノード数」をスケールするものはどれですか？（2つ選択）

  • A. HPA（Horizontal Pod Autoscaler）
  • B. Cluster Autoscaler
  • C. Virtual Node（仮想ノードアドオン）
  • D. KEDA（Kubernetes Event-Driven Autoscaling）
✅ 正解: B と C

B. Cluster Autoscaler — VMSS の実ノード（VM）の台数を増減します。
C. Virtual Node — ACI コンテナを「仮想ノード」として追加します。実 VM ではありませんが、K8s からはノードとして見えます。

なぜAは不正解か: HPA は Deployment/ReplicaSet の Pod レプリカ数を変更します。ノードには触れません。
なぜDは不正解か: KEDA も Pod レプリカ数を変更します（内部的に HPA を通じて）。ノードには触れません。
5

KEDA と HPA の違い

次のうち、KEDA を使用する必要があり、HPA では対応できないシナリオはどれですか？

  • A. Web アプリの CPU 使用率が 70% を超えたら Pod を増やしたい
  • B. メモリ使用率に基づいて StatefulSet をスケールしたい
  • C. Azure Event Hub のイベント数が増えたら Pod を増やし、イベントがなくなったら Pod を 0 にしたい
  • D. Deployment の Pod を最低 2 台、最大 10 台の範囲で自動スケールしたい
✅ 正解: C

C には 2 つの KEDA 専用要件が含まれています：
①「Azure Event Hub のイベント数」 → 外部イベントトリガー。HPA は CPU/メモリのみ対応
②「Pod を 0 にしたい」 → Scale to ZERO。HPA は最低 1 Pod の制約があり 0 にはできない

なぜAは不正解か: CPU 使用率ベースのスケール = HPA で対応可能
なぜBは不正解か: メモリ使用率ベースのスケール = HPA で対応可能
