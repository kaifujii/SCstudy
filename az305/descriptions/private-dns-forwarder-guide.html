Azure プライベート DNS ゾーン
オンプレミスからの名前解決 完全解説

なぜ VM1 のフォワーダーを 168.63.129.16 に向けるのか。DNS の流れを図解で徹底解説します。

① 前提知識：168.63.129.16 とは何者か

🔑 168.63.129.16 は Azure が提供する「仮想 DNS サーバー」の IP アドレスです。
Azure 上のすべての VNET から到達可能な特殊な予約済み IP で、Azure DNS・プライベート DNS ゾーン・パブリック DNS を解決する能力を持ちます。
このIPは実際のサーバーではなく、Azure プラットフォームが提供する仮想エンドポイントです。
168.63.129.16 でできることできないこと
✅ Azure プライベート DNS ゾーンの解決（VNET にリンクされていれば）
✅ Azure パブリック DNS の解決（*.blob.core.windows.net 等）
✅ インターネット上のパブリック DNS の解決 		❌ VNET の外（オンプレミス）からは直接到達不可
❌ オンプレミスの DNS サーバーはこの IP に問い合わせできない
⚠️ これが今回の問題の核心
  • オンプレミスのクライアントは 168.63.129.16 に直接アクセスできない
  • そのため「VNET 内にいる VM1（カスタム DNS）」を中継役（フォワーダー）として使う
  • VM1 は VNET 内にいるため 168.63.129.16 に到達できる → これがポイント

③ 各選択肢の正誤と理由

❌ A：apexcore.com の DNS クエリをパブリック DNS ゾーンに転送するよう VM1 を構成する

なぜ間違いか：

  • パブリック DNS ゾーンにはプライベート IP アドレスの情報が存在しません
  • パブリック DNS ゾーンの apexcore.com（あれば）はパブリック IP しか返せない
  • そもそも今回解決したいのは Azure プライベート DNS ゾーンに登録されたリソースです
  • パブリック DNS に転送すると「レコードが見つからない」か「パブリック IP が返ってしまう」という結果になります
✅ B：apexcore.com の DNS クエリを Azure 提供の DNS（168.63.129.16）に転送するよう VM1 を構成する ← 正解

なぜ正解か：

  • VM1 は VNET1 内にいるため 168.63.129.16 に到達できる
  • 168.63.129.16 は VNET1 にリンクされたプライベート DNS ゾーン（apexcore.com）を参照できる
  • オンプレミスから直接 168.63.129.16 にアクセスできない問題を VM1 が中継することで解決する
  • VM1 が「橋渡し役（フォワーダー）」として機能し、オンプレミス ↔ Azure DNS の境界を越えられる
  • フォワーダー設定は VM1 の DNS サーバーソフト（Windows Server の場合は DNS マネージャー）の「条件付きフォワーダー」で設定する
⚠️ C：VNet1 でカスタム DNS サーバーを Azure 提供の DNS（168.63.129.16）に設定する

なぜ間違いか（引っかかりやすい選択肢）：

  • VNET の DNS サーバー設定を変更すると VNET 内の VM が使う DNS が変わるだけ
  • この設定は「Azure VNET 内のリソース」が 168.63.129.16 を使うようになるだけで、オンプレミスクライアントには何の影響もありません
  • 今回の問題は「オンプレミスクライアントが解決できるようにする」要件なので、この設定では解決しない
  • また現状 VM1 をカスタム DNS として使っているため、これを変えると VM1 が使われなくなり構成が崩れる
💡 C は「VNET 内のリソースがプライベート DNS を解決できるようにする」シナリオでは正しいアプローチです。今回とは要件が異なります。

④ 実際の設定内容（VM1 のフォワーダー設定）

VM1 が Windows Server の場合、DNS サーバーの「条件付きフォワーダー（Conditional Forwarder）」を設定します。

🖥️ Windows Server DNS での設定手順

1
VM1 に RDP ログイン → サーバーマネージャー → DNS マネージャーを開く
2
「条件付きフォワーダー」を右クリック → 「新しい条件付きフォワーダー」
3
DNS ドメイン：apexcore.com　マスターサーバーの IP アドレス：168.63.129.16 を入力して OK
4
オンプレミス DNS サーバーに「apexcore.com のクエリを VM1 の IP に転送する」条件付きフォワーダーを追加（忘れがちなステップ）
⚠️ よく忘れる「もう1つの設定」
  • VM1 側のフォワーダー設定だけでは不十分です
  • オンプレミスの DNS サーバーにも「apexcore.com → VM1 の IP」という条件付きフォワーダーが必要です
  • この2つがセットになって初めてオンプレミスクライアントから名前解決できます
  • 問題文では「VM1 に構成するフォワーダー設定」が問われているため、答えは B ですが、実際の構成では両方必要です

🎯 試験頻出ポイント

📌 必ず覚える3点
  • 168.63.129.16 はオンプレミスから直接届かない：VNET 内のリソースからしかアクセスできない特殊 IP
  • VM1（カスタム DNS）が中継役：VNET 内にいる VM1 だけが 168.63.129.16 にアクセスできるため、オンプレミスとの橋渡し役になる
  • VNET リンクが前提：プライベート DNS ゾーンが VNET1 にリンクされていないと、168.63.129.16 がそのゾーンを参照できない
⚠️ 引っかかりやすいパターン
  • 「VNET の DNS サーバー設定を 168.63.129.16 にする」→ VNET 内のリソース向けの設定であり、オンプレミスには効果なし（選択肢 C）
  • 「プライベート DNS ゾーンを作るだけで解決できる」→ VNET リンクとフォワーダー設定がなければオンプレミスからは解決不可
  • 「VM1 のフォワーダーだけ設定すればよい」→ オンプレミス DNS にも条件付きフォワーダーが必要（両方必要）
  • 「パブリック DNS に転送すればよい」→ プライベート IP はパブリック DNS には存在しない（選択肢 A）
🎯 最終まとめ：正解は B の理由
オンプレミスのクライアントは 168.63.129.16 に直接アクセスできません。
そこで VNET1 内にいる VM1 を中継役として使い、
「apexcore.com → 168.63.129.16」というフォワーダーを VM1 に設定することで、
オンプレミス → VM1 → 168.63.129.16 → プライベート DNS ゾーン という経路で名前解決が実現します。
これが選択肢 B が正解の理由です。
