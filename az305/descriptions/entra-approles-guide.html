② アプリロール（App Roles）

アプリロールとは、アプリケーション独自のロールを定義する仕組みです。Entra ID の組み込みロール（全体管理者など）とは別物で、アプリ固有のアクセス制御に使います。

🏢 具体例：経費申請システム

【API側アプリ登録】で定義するアプリロール
Expense.Submit経費申請者
allowedMemberTypes: User
Expense.Approve経費承認者
allowedMemberTypes: User
Expense.Admin管理者
allowedMemberTypes: Both
Expense.ReadAll全データ読取
allowedMemberTypes: Application
↓ ユーザー/グループ/サービスプリンシパルに割り当て
👤 山田 太郎→ Expense.Submit
👤 鈴木 課長→ Expense.Approve
👥 IT管理者G→ Expense.Admin
⚙ バッチサービス→ Expense.ReadAll
↓ ログイン時のJWTトークンに反映
JWT roles クレーム："roles": ["Expense.Submit"]山田さんがログインした際のトークンに自動で含まれる

📝 マニフェスト（JSON）

"appRoles": [
  {
    "allowedMemberTypes": ["User"],       // User / Application / Both
    "displayName": "経費申請者",
    "id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",  // 一意のGUID（必須）
    "isEnabled": true,
    "description": "経費申請の提出が可能",
    "value": "Expense.Submit"   // ← トークンの roles クレームに入る値
  }
]

allowedMemberTypes の使い分け

  • User：人間ユーザー・グループへの割り当て
  • Application：デーモン・バッチ・サービスへの割り当て
  • Both：どちらにも割り当て可能

割り当て方法

  • Portal → エンタープライズアプリ → ユーザーとグループ
  • Microsoft Graph API での一括割り当て
  • Applicationロールはサービスプリンシパルに割り当て
  • 割り当て後、次回ログイン時のトークンに反映

③ APIアクセス許可（API Permissions）

クライアントアプリが「どのAPIの、どの権限を使うか」を宣言するのがAPIアクセス許可です。Delegated（委任）とApplication（アプリケーション）の2種類があります。

🔑 Delegated vs Application の違い

Delegated（委任）
👤 ユーザーがログイン
↓
📱 クライアントAppユーザーの代わりにAPIを呼ぶ
↓
🎫 トークン（ユーザー情報入り）
↓
⚙ API（ユーザー権限で応答）
・有効なユーザーが必要
・ユーザーの同意（Consent）が必要
・例：ログインユーザーのメール一覧取得
Application（アプリケーション）
⚙ サービス/デーモンユーザー不在で動作
↓ client_credentials フロー
🎫 トークン（アプリ情報入り）
↓
⚙ API（アプリ権限で応答）
・ユーザー不在で動作
・管理者の同意のみ必要（ユーザー同意不要）
・例：夜間バッチが全ユーザーのデータ処理
比較項目Delegated（委任）Application（アプリ）
ユーザーの有無必要（対話型）不要（非対話型・バックグラウンド）
認証フローAuthorization Code / Implicit 等Client Credentials
同意（Consent）ユーザー同意 or 管理者同意管理者同意のみ
トークンの主体ユーザー（sub クレーム = ユーザーID）アプリ（sub クレーム = アプリID）
典型的ユースケースWebアプリ・モバイルアプリ・SPAバックグラウンドサービス・デーモン・バッチ
Graph API の例User.Read（自分のプロフィール読取）User.Read.All（全ユーザー読取）
⚠️ 試験頻出：Application パーミッションは必ず管理者同意が必要
  • Application パーミッションは強力な権限のため、必ずテナント管理者の同意が必要
  • Delegated でも User.Read.All など高権限のものは管理者同意が必要
  • 管理者同意なしでは 403 エラーになる（よくある試験のひっかけ）

④ トークン構成（Token Configuration）

JWTトークンに「どのクレームを含めるか」を設定する機能です。アプリケーションがユーザー情報やロール情報を取得するために必要な設定です。

📋 主要クレーム一覧

クレーム名内容設定方法用途
roles ユーザーに割り当てられたアプリロール アプリロール割り当てで自動付与 アプリ内のロールベースアクセス制御
groups ユーザーが所属するグループのID トークン構成でオプショナルクレーム追加 グループベースのアクセス制御
email ユーザーのメールアドレス オプショナルクレームで追加 アプリでのユーザー識別
upn ユーザープリンシパル名 オプショナルクレームで追加 ユーザー名表示
oid ユーザーのオブジェクトID（変わらない） デフォルトで含まれる ユーザーの一意識別
sub サブジェクト（アプリ固有のユーザーID） デフォルトで含まれる アプリ内ユーザー識別
scp Delegatedパーミッションのスコープ APIアクセス許可の設定で自動付与 Delegated権限の確認
aud トークンの対象（クライアントID） デフォルトで含まれる トークンの正当性確認

⚙️ トークン構成の設定方法（Portal）

1
Azure Portal → Microsoft Entra ID → アプリの登録
2
対象アプリを選択 → 左メニュー 「トークン構成」 をクリック
3
「オプションの要求を追加する」 → トークン種類（ID/Access/SAML）を選択
4
追加したいクレーム（email, upn, groups 等）を選択して保存
5
グループクレームの場合は 「グループ要求を追加する」 から別途設定

📝 JWTトークンの実例（経費申請システム）

// 山田太郎さんがログインした際のアクセストークン（Payload部分）
{
  "iss": "https://login.microsoftonline.com/{tenant}/v2.0",
  "aud": "api://expense-app",           // このトークンの対象API
  "oid": "a1b2c3d4-...",              // 山田さんのオブジェクトID（不変）
  "name": "山田 太郎",
  "upn": "yamada@contoso.com",        // オプションクレームで追加
  "email": "yamada@contoso.com",       // オプションクレームで追加
  "roles": ["Expense.Submit"],       // アプリロール割り当ての結果
  "groups": ["grp-id-1", "grp-id-2"], // グループクレームで追加
  "scp": "Expense.Submit",           // Delegatedスコープ
  "exp": 1700000000,                // 有効期限（Unixtime）
  "iat": 1699996400                 // 発行時刻
}

⚠️ groups クレームの注意点

グループ数が多い場合のオーバーフロー問題（試験頻出）
  • ユーザーが所属するグループが 200個を超える と groups クレームはトークンに含まれなくなる
  • 代わりに "_claim_names": {"groups": "src1"} という超過通知クレームが入る
  • 対処法：Microsoft Graph API の /me/memberOf を呼び出してグループ情報を取得する
  • または アプリロール を使用してグループクレームへの依存を減らすことを検討する

⑤ 試験で問われやすいポイントと間違いやすい箇所

問われる内容正解間違いやすいポイント
アプリロールはどこに定義するか API側のアプリ登録 クライアント側に定義すると誤解しがち。APIが「自分はこんな権限を持っている」と定義する
Applicationパーミッションの同意 管理者同意のみ 「ユーザーが同意できる」と誤解しがち。Applicationパーミッションは必ず管理者同意が必要
groupsクレームのオーバーフロー閾値 200グループ超 150や100と誤解しがち。200超でクレームがトークンから除外される
roles クレームと scp クレームの違い roles = アプリロール
scp = Delegatedスコープ		 混同しがち。rolesはアプリロール割り当ての結果。scpはDelegatedパーミッションのスコープ
サービス間通信に使うパーミッション Application デーモン・バッチにDelegatedを使おうとする。ユーザー不在の処理はApplicationパーミッション
アプリロールとEntra IDロールの違い アプリロール = アプリ固有
Entra IDロール = テナント全体		 「全体管理者」などのEntra IDロールとアプリロールは別物。アプリロールはアプリだけに効果がある
トークン構成でgroupsを追加する方法 「グループ要求を追加する」から別途設定 「オプションの要求を追加する」のgroupsとは別の設定項目。混同に注意
IDトークン vs アクセストークン IDトークン = 認証（誰か）
アクセストークン = 認可（何ができるか）		 どちらにrolesが含まれるかを問われる。どちらも含まれるが、APIはアクセストークンのrolesを検証する

🎯 シナリオ別の選択指針

📌 このシナリオならアプリロール
✓

✓
アプリ内で細かいロールベース制御をしたい
✓
バッチサービスに特定の権限を与えたい
✓
グループ数が多くgroupsクレームが使えない
📌 このシナリオならDelegatedパーミッション
✓
ユーザーが自分のデータにアクセスするWebアプリ
✓
ユーザーの代わりにGraph APIを呼ぶSPA
✓
ユーザーが自分のメール・予定を操作するアプリ
✓
モバイルアプリでのユーザーログイン操作
📌 最重要まとめ
  • アプリロールはAPI側のアプリ登録で定義し、ユーザー/グループ/サービスプリンシパルに割り当てる。JWTの roles クレームに反映される
  • APIアクセス許可は Delegated（ユーザー代理）と Application（サービス単独）の2種類。Applicationは必ず管理者同意が必要
  • トークン構成でオプショナルクレーム（email・upn・groups等）を追加できる。groupsは200超でオーバーフローする
  • roles と scp は別物：rolesはアプリロール、scpはDelegatedスコープのパーミッション一覧
