Always On FCI vs AG — 完全解説
AZ-305 / SQL Server HA・DR
SQL Server High Availability

フェールオーバークラスター (FCI)
vs 可用性グループ (AG)

どちらも「SQL Serverを止めない」ための技術ですが、保護の単位とストレージの考え方がまったく異なります。 この違いを根本から理解することが、試験でも実務でも差がつくポイントです。

FCI = インスタンス単位 AG = データベース単位 両者: WSFC 必須

01 一番重要な違い — 保護の粒度とストレージ

FCI は「SQL Serverインスタンス全体」を共有ストレージで守る。AG は「選択したデータベース群」を独立ストレージで複製して守る。

FCI vs AG — アーキテクチャ根本比較
i
一言で覚える核心的な違い FCIは「ひとつのSQL Serverインスタンスを複数のノードで共有する」— ストレージは共有、アクティブなのは1ノードのみ。
AGは「同じデータベースをそれぞれのSQL Serverで持ち合い、同期する」— ストレージは各自が持つ、セカンダリも稼働中。

02 6つの観点で比較する

FCI の特徴
  • ▶保護単位: SQL Serverインスタンス全体（DB・ログイン・Agent Job・設定すべて）
  • ▶ストレージ: 共有ストレージ必須（SAN / iSCSI / Storage Spaces Direct / SMB）
  • ▶セカンダリの活用: 完全に待機専用。読み取り不可・バックアップ不可
  • ▶フェールオーバー時間: 30〜60秒（全DB のクラッシュリカバリが必要）
  • ▶エディション: Standard でも使用可能（コスト優位）
  • ▶管理の手間: シンプル（インスタンスが1つ。ログイン同期不要）
  • ▶地理冗長（DR）: ストレージが共有のため別データセンターへの対応が困難
  • ▶Azure対応: 可能だが共有ストレージ構成が複雑（Azure Shared Disks等）
vs
AG の特徴
  • ▶保護単位: 選択したデータベースのグループ（DB単位で制御可能）
  • ▶ストレージ: 各レプリカが独自のストレージを持つ（共有不要）
  • ▶セカンダリの活用: 読み取り専用クエリのオフロード・バックアップのオフロードが可能
  • ▶フェールオーバー時間: 通常30秒以内。自動フェールオーバー対応（同期レプリカ）
  • ▶エディション: 原則 Enterprise 推奨（Standard は制限あり: 1DB/グループ、2レプリカまで）
  • ▶管理の手間: 複雑（ログイン・Agent Job を全レプリカに同期する必要あり）
  • ▶地理冗長（DR）: 非同期レプリカを別リージョンに配置して DR を実現できる
  • ▶Azure対応: Azure VM で最も一般的なHA構成（共有ストレージ不要のため）
!
FCI はインスタンスレベル、AG はデータベースレベル — 組み合わせも可能 FCI と AG は排他的な選択肢ではありません。FCI ノード上に AG レプリカを配置することができます（例: FCI が Primary レプリカを担当し、AG で別サイトに DR レプリカを持つ）。ただし FCI 上の AG レプリカは 自動フェールオーバーが使えない（手動フェールオーバーのみ）という制限があります。
FCI — Failover Cluster Instance

フェールオーバークラスター
インスタンス 詳細解説

SQL Serverインスタンス全体を単一の論理サーバーとして複数ノードにまたがらせる技術。アクティブノードが障害を起こすと、パッシブノードがインスタンス全体を引き継ぎます。

01 FCI のフェールオーバーフロー

1
通常稼働: Node 1 がアクティブ

Node 1 が SQL Serverインスタンスを実行中。共有ストレージの所有権を持ち、全DBへの読み書きを担当。Node 2 は SQL Server が停止しており、待機のみ。

2
障害検知: WSFC がノード障害を検知

WSFC のヘルスチェックが Node 1 の障害を検知（ハートビート途絶など）。フェールオーバーポリシーに従って Node 2 へのフェールオーバーを開始。

3
ストレージの所有権移転

共有ストレージ（SAN / SMB / S2D）の所有権が Node 2 に移転。Node 2 から同じデータファイルが見える状態になる。これがFCIの核心。

4
Node 2 で SQL Server 起動 + クラッシュリカバリ

Node 2 で SQL Server インスタンスが起動。全 DB のクラッシュリカバリ（コミット済みトランザクションのロールフォワード・ロールバック）を実行。これが30〜60秒かかる原因。

5
フェールオーバー完了: アプリは同じ仮想IPに接続

WSFC の仮想ネットワーク名・仮想IPアドレスが Node 2 に移動。アプリケーションは接続文字列を変更せず同じ名前で接続可能。RPO = ゼロ（コミット済みデータは共有ストレージに存在）。

AG — Always On Availability Group

可用性グループ
詳細解説

選択したデータベースを複数のレプリカで同期する技術。SQL Server 2012 で導入。プライマリが障害を起こすと、セカンダリが自動でプライマリに昇格します。

01 AG のフェールオーバーフロー

1
通常稼働: Primary レプリカが読み書きを担当

Primary レプリカがすべての読み書きを担当。トランザクションログがセカンダリに送信される。同期レプリカは commit 前にセカンダリへの書き込みを待つ（RPO=0）。非同期レプリカは待たない（高性能だが RPO > 0）。

2
障害検知: WSFC がプライマリの障害を検知

WSFC のヘルスチェックがプライマリの障害を検知。自動フェールオーバーが設定されている場合、候補のセカンダリに自動で切り替え開始（同期レプリカのみ自動フェールオーバー可）。

3
セカンダリが Primary へ昇格

対象のセカンダリは SQL Server がすでに稼働中なので、DBを読み書き可能状態（ONLINE）にするだけで昇格完了。クラッシュリカバリは不要（ログが常に同期済み）。FCI より大幅に速いのはこのため。

4
AG Listener の仮想IPが新プライマリに向く

AG Listener の仮想IPアドレスが新プライマリのノードに向く。アプリは Listener の名前（Data Source=listener-name;）で接続していれば透過的に新プライマリへ接続。ApplicationIntent=ReadOnly の接続は読み取り可能セカンダリへルーティング。

04 Contained Availability Groups（SQL Server 2022）

i
SQL Server 2022 の新機能: Contained AG 通常の AG では、ログイン・SQL Server Agent ジョブ・msdb オブジェクトなどの「インスタンスレベルオブジェクト」は AG で複製されず、各レプリカに手動で同期する必要がありました。 SQL Server 2022 の Contained AG では、master / msdb データベースが AG のスコープに含まれるため、ログイン・Agent ジョブ・リンクサーバーなども AG のフェールオーバーと一緒に移動します。FCI の「インスタンス全体を守る」という強みと、AG の「柔軟性」を組み合わせた形です。
試験ポイント

「セカンダリを読み取り専用レポートに使いたい。また別リージョンにDR拠点を持ちたい」

✅ Always On AG — 読み取り可能セカンダリ（ApplicationIntent=ReadOnly）＋ 非同期コミットで別リージョンDRが可能
❌ FCI — セカンダリは待機専用で読み取り不可。DR対応も困難

シナリオ問題演習

選択肢をクリックして正誤を確認。解説で「なぜ他は間違いか」まで理解してください。

1

SQL Standard + コスト重視 + HA

中規模の業務システムで、SQL Server Standard エディションを使用しています。コストを最小化しながら、サーバー障害時に自動でフェールオーバーするHA構成を組みたい。最も適切な構成はどれですか？

  • A. Always On フェールオーバークラスターインスタンス (FCI)
  • B. Always On 可用性グループ (AG) — Enterprise Edition に変更して
  • C. ログ配布 (Log Shipping)
  • D. データベースミラーリング
✅ 正解: A — FCI

SQL Server Standard でも FCI は使用可能です。AG は Enterprise Edition 推奨（Standard では 1DB/グループ・2レプリカの制限）なのでコストが増大します。

なぜCは不正解か: ログ配布は RPO が数分以上あり、自動フェールオーバーも手動操作が必要です。
なぜDは不正解か: データベースミラーリングは SQL Server 2012 以降で非推奨（Deprecated）です。
2

読み取りオフロード + DR

大規模なECサイトのデータベースで、次の2つの要件があります。①本番DBへの影響なしでレポートクエリを実行したい ②東日本リージョン障害時に西日本リージョンにDRフェールオーバーしたい。最適な構成はどれですか？

  • A. FCI（共有ストレージを東西リージョンに延伸）
  • B. AG（同期コミット+読み取り可能セカンダリで東日本HA、非同期コミットで西日本DR）
  • C. FCI（東日本のみ）+ バックアップを西日本にリストア
  • D. AG（全レプリカ同期コミット）で東日本・西日本の3ノード
✅ 正解: B — AG ハイブリッド構成

AG の読み取り可能セカンダリで①を満たし、非同期コミットの西日本レプリカで②を実現します。これが AG の典型的なHA+DR+読み取りオフロードの構成です。

なぜAは不正解か: 共有ストレージをリージョン間で延伸するのはほぼ不可能（レイテンシの問題）かつ非常に高コストです。
なぜDは不正解か: 全レプリカを同期コミットにすると、最も遠いレプリカへの書き込みを待つため、東西のレイテンシ分だけプライマリのレスポンスが遅くなります。DR拠点は非同期が適切です。
3

フェールオーバー時間の違い

FCI と AG のフェールオーバー時間が異なる根本的な理由として、最も正確なものはどれですか？

  • A. FCI は共有ストレージへのアクセス権移転に時間がかかるため
  • B. FCI はフェールオーバー先のノードで SQL Server の起動とすべての DB のクラッシュリカバリが必要なため。AG のセカンダリは SQL Server が稼働済みのため DB の昇格のみで完了する
  • C. AG はネットワーク経由でデータを同期しているためデータ適用が速いため
  • D. FCI はクラスターノード間の通信に余分な時間がかかるため
✅ 正解: B

FCI のフェールオーバーが30〜60秒かかる根本的な理由は、パッシブノードでは SQL Server が停止していることです。フェールオーバー時にSQL Serverを起動し、全データベースのクラッシュリカバリ（コミット済みトランザクションのロールフォワード）を実行する必要があります。

AG のセカンダリはすでに SQL Server が稼働しており、ログも継続的に適用されているため、プライマリへの昇格はDBをONLINE状態にするだけで完了します（秒単位〜30秒以内）。

なぜAは間違いか: ストレージ所有権の移転は比較的速く、ボトルネックはクラッシュリカバリです。
4

Contained AG（SQL Server 2022）

AGを使用していますが、フェールオーバー後に「セカンダリに SQL Server Agent ジョブが存在しない」「ログインが見つからない」という問題が発生しています。SQL Server 2022 でこの問題を根本解決する機能はどれですか？

  • A. 同期コミットモードに変更する
  • B. AG Listener を使用する
  • C. Contained Availability Group を使用する
  • D. FCI に移行する
✅ 正解: C — Contained Availability Group

通常の AG では、ログインや SQL Server Agent ジョブは「インスタンスレベルオブジェクト」のため AG のレプリケーション対象外です。各セカンダリに手動で同期する必要があります。

SQL Server 2022 の Contained AG では、master / msdb データベースが AG のスコープに含まれるため、ログイン・Agent Job・リンクサーバーなども自動でフェールオーバー先に複製されます。

なぜDは不正解か: FCI に移行すれば確かにインスタンス全体が一括で守られますが、読み取りレプリカや DR 機能を失います。Contained AG はAGを維持しながらこの問題を解決します。
5

FCI + AG 組み合わせの制限

Site A の FCI（Node1/Node2 + 共有ストレージ）を AG の Primary レプリカとして使用し、Site B のスタンドアロン SQL Server を Secondary レプリカとして AG を構成しました。この構成で「自動フェールオーバー」を設定しようとしています。この設定は可能ですか？

  • A. 可能。同期コミットに設定すれば自動フェールオーバーが機能する
  • B. FCI ノード上の AG レプリカは手動フェールオーバーのみ。自動フェールオーバーは設定できない
  • C. 可能。ただし WSFC のクォーラムを3ノードにする必要がある
  • D. 不可能。FCI と AG は組み合わせることができない

Microsoft の仕様として、FCI ノードがホストする AG レプリカは手動フェールオーバーのみに設定する必要があります。自動フェールオーバーはスタンドアロン SQL Server インスタンスがレプリカをホストする場合のみ機能します。

なぜDは不正解か: FCI と AG の組み合わせは完全に対応しています。FCI を Primary レプリカとして使いつつ、AG で別サイトに Secondary を追加することができます。ただし自動フェールオーバーの制限があります。
