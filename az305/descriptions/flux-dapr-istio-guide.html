🎓 AZ-305 | Container & Kubernetes

Flux・Dapr・Istio 完全解説

Kubernetes エコシステムの重要コンポーネント。それぞれの役割・できること・Azure との関係を整理します。

① 3つの役割の全体像と違い

3つはすべて「Kubernetes 上で使うツール」ですが、担当レイヤーがまったく異なります。競合ではなく共存して使うものです。

② Flux（GitOps）

一言：「Git が唯一の真実（Single Source of Truth）」
Git リポジトリに push したマニフェストを、Flux が自動的に Kubernetes クラスターへ適用します。kubectl コマンドを手動で叩く運用から脱却できます。

🔄 基本的な動作フロー（Pull 型）

👨‍💻 開発者コードをpush
→
📁 Git リポジトリYAML マニフェスト
←
🔄 Flux Controller定期的に差分チェック（Pull）
→
☸️ Kubernetes差分を自動適用
⚡ ポイント：Flux は「Push型」ではなく「Pull型」。クラスター側から Git を監視して引き取る構造のため、クラスターへの直接アクセス権が Git 側に不要でセキュア。

✅ できること

デプロイ自動化

  • Git push → 自動デプロイ（CD パイプライン）
  • 複数クラスターへの一括デプロイ管理
  • Helm Chart の自動アップグレード
  • Kustomize によるマニフェストの環境差分管理

ドリフト検出・自動修復

  • 手動で kubectl 変更した場合に Git の状態に戻す
  • 「あるべき状態」からのズレを自動検知・修正
  • 変更履歴はすべて Git に残る
  • 監査・コンプライアンスへの対応

AKS では Flux v2 がクラスター拡張機能として提供されています。Azure Portal または Azure CLI から有効化でき、Azure Policy で「全クラスターに Flux を必須化」することも可能です。これが AZ-305 で問われる GitOps with AKS の実装方法です。

⚠️ 試験頻出：Flux と ArgoCD の違い
  • どちらも GitOps ツールだが、Flux は AKS の公式クラスター拡張機能として統合されており Azure 環境での推奨ツール
  • ArgoCD は UI が充実しているが、Azure ネイティブの統合は Flux の方が深い
  • 試験では「AKS で GitOps を実現する」シナリオなら Flux が答えになることが多い

③ Dapr（Distributed Application Runtime）

一言：「分散システムの共通機能をアプリから切り離してサイドカーで提供する」
メッセージング・状態管理・サービス呼び出し・シークレット管理などの面倒な実装を、アプリから分離してサイドカーコンテナが肩代わりします。アプリ側は HTTP や gRPC で Dapr を呼ぶだけでよくなります。

☁️ Azure Container Apps（ACA）との深い統合

Azure Container Appsサーバーレスコンテナ
+
Dapr組み込みでサポート
→
有効化するだけでサイドカーが自動注入

Azure Container Apps は Dapr をファーストクラスでサポートしています。ACA のポータルで Dapr を有効にするだけでサイドカーが自動注入され、Service Bus・Cosmos DB との統合が設定ベースで完結します。AZ-305 では「マイクロサービスの通信・状態管理を簡略化したい」という要件で ACA + Dapr の組み合わせが頻出です。

# Dapr を有効にした Azure Container Apps のデプロイ例
az containerapp create \
  --name myapp \
  --resource-group myRG \
  --environment myEnv \
  --image myimage:latest \
  --dapr-enabled true \
  --dapr-app-id "myapp" \
  --dapr-app-port 8080
⚠️ 試験頻出：Dapr と Istio の違い
  • Dapr はアプリ開発者向け：ビジネスロジックの実装を支援する（状態管理・メッセージング等）
  • Istio はインフラ担当向け：通信の制御・監視をアプリ透過的に行う（mTLS・トラフィック管理等）
  • どちらもサイドカーを使うが目的が異なるため共存可能（実際に併用されるケースもある）
  • ACA 環境では Istio ではなく Dapr が推奨統合ツール

④ Istio（Service Mesh）

一言：「サービス間通信をアプリに触れずに制御・監視する透明なネットワーク層」
すべての Pod にサイドカー（Envoy Proxy）を自動注入し、アプリ間の通信を横断的にコントロールします。アプリのコード変更は一切不要です。

☁️ AKS での Istio 統合（AKS アドオン）

AKS クラスター
+
Istio アドオンaz aks mesh enable
→
マネージド IstioMicrosoft が管理・更新

AKS では Istio ベースのサービスメッシュアドオンが提供されています（2023年 GA）。自前で Istio をインストール・管理する手間なく、Azure が Istio の更新・管理を担います。AZ-305 では「AKS でサービスメッシュが必要」なシナリオでこのアドオンが答えになります。

⚠️ 試験頻出：Istio vs Linkerd vs Open Service Mesh（OSM）
  • Istio：最も機能が豊富だが複雑・重量級。AKS のアドオンとして正式サポート
  • Linkerd：軽量でシンプル。Rust 製で高パフォーマンス。AKS の公式アドオンではない
  • OSM（Open Service Mesh）：Microsoft が開発したが 2023年に非推奨。代替は Istio アドオン
  • 試験では「AKS でサービスメッシュ」= Istio アドオンが正解になるケースが多い

🎯 シナリオ別の選択指針

シナリオ採用すべきツール理由
「Git push で自動デプロイしたい」 Flux GitOps の実装。AKS 拡張機能で簡単に導入できる
「マイクロサービス間でイベント駆動通信したい」 Dapr Pub/Sub ビルディングブロックで Service Bus 等を抽象化できる
「サービス間通信を自動的に mTLS で暗号化したい」 Istio コード変更なしで全通信を mTLS 化できる
「新バージョンを段階的にリリース（カナリア）したい」 Istio VirtualService の重み付けルーティングで実現
「各サービスが Redis や Cosmos DB を使いたいが接続先を切り替えたい」 Dapr 状態管理 Component を差し替えるだけでバックエンドを変更できる
「サービス間の依存関係とレイテンシを可視化したい」 Istio Kiali・Jaeger 連携でサービスマップと分散トレーシングを提供
「複数環境（dev/staging/prod）を一元管理したい」 Flux Kustomize + パラメーター分離で環境差分を Git で管理
「Azure Container Apps でマイクロサービスを構築したい」 Dapr ACA は Dapr をネイティブサポート。設定だけで有効化できる
📌 AZ-305 最重要まとめ
  • Flux：「GitOps」「デプロイ自動化」「ドリフト検出」「AKS 拡張機能」がキーワード。ArgoCD との違いは Azure ネイティブ統合
  • Dapr：「Building Blocks」「サイドカー」「言語非依存」「ACA との統合」がキーワード。Istio との違いはアプリ機能の提供（コード変更あり）
  • Istio：「Service Mesh」「mTLS」「カナリアデプロイ」「可観測性」「AKS アドオン」がキーワード。OSM は非推奨で代替が Istio
  • 3つは競合ではなく共存・補完関係。実際のエンタープライズ環境では3つすべて使うケースも多い
