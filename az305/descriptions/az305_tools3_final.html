03 ネットワーク要件

必須ポート設定

  • SQL MI サブネットのNSG: Inbound port 5022 と 11000-11999 を SQL Server IPから許可
  • SQL MI サブネットのNSG: Outbound port 5022 を SQL Server IPへ許可
  • SQL Server 側でも port 5022 の受信を許可
Port 5022NSG必須パブリックEP不可

接続方式の推奨順

  • 同一VNetのAzure VM: 自動接続（最シンプル）

データ転送 — S3からAzureへのスクリプト自動化

AWS S3バケット（500GB）のデータをAzure Blob Storageに転送します。スクリプトで自動化でき、最もシンプルな方法はどれですか？

  • A. Storage ExplorerのS3接続機能を使ってDrag&Dropでコピーする
  • B. AzCopyのcopyコマンドでS3バケットURLとAzure Blob SAS URLを指定して実行する
  • C. Azure Data Factoryパイプラインを作成しS3コネクターを設定して実行する
  • D. Azure Import Jobを作成し物理HDDにコピーしてMicrosoftへ発送する
✅ 正解: B — AzCopy

S3→Azure直接コピー、CLI、無料という3点でAzCopyが最適。azcopy copy 's3://bucket/' 'https://acct.blob.core.windows.net/cont/?SAS' --recursive で完結します。

A が不正解: Storage ExplorerはGUIツールでスクリプト自動化不可。
C が不正解: ADFは「シンプル」に反する（パイプライン設計が必要）。ETL変換が必要な場合はADF。
D が不正解: 500GBはオフライン転送の対象外（Data Boxは数十TB〜PB向け）。

ファイルサーバー延命 — クラウドティアリング

東京本社のWindows Server 2019ファイルサーバー（300GB）が容量不足（総1TB）。既存のUNCパスを変えず、よく使うファイル（30日以内）だけローカルに残す構成は？

  • A. Azure MigrateでWindows ServerをAzure VMに移行し、Azure Filesをマウントする
  • B. Azure File SyncエージェントをインストールしてAzure Filesと同期、クラウドティアリング（日付ポリシー30日）を有効にする
  • C. AzCopyで全データをAzure Filesに移行し、ネットワークドライブとして割り当てる
  • D. Azure Backupで古いファイルをバックアップしてローカルから削除する
✅ 正解: B — Azure File Sync

「UNCパス変更なし」「容量拡張」「よく使うファイルのみローカル」= File Sync + クラウドティアリング（日付ポリシー）の組み合わせで完全に要件を満たします。

A が不正解: Azure MigrateはサーバーをAzureに移行して廃止するもの。「廃止せず延命」に反する。
C が不正解: ネットワークドライブは認証変更が必要でUNCパスを維持できない。またAzCopyは継続同期不可。
D が不正解: Azure BackupはDR/バックアップ用。クラウド容量拡張や透過的アクセスには使えない。

移行アセスメント — VMware150台

  • A. Azure Cost Managementでコスト試算し、依存関係は手動で文書化する
  • B. Azure Monitor AgentをすべてのVMにインストールしLog Analyticsで分析する
  • C. Azure MigrateをデプロイしてvSphere用ApplianceでDiscovery & Assessmentを実行する
  • D. Azure VMのSKU一覧を参照してオンプレVMの仕様と手動で対応させる

SQL移行 — Business Critical + フェイルバック

本番稼働中のSQL Server 2022をAzure SQL MI Business Criticalに移行。要件：①最小ダウンタイム②移行後問題時はオンプレに戻せる③移行中もアプリは通常稼働。最適な方法は？

  • A. Azure Database Migration Service（オンラインモード）でSQL Server 2022からSQL MIに移行する
  • B. SSMSでバックアップを取得し、Azure SQL MIにリストアする
  • C. Managed Instance Linkを使ってSQL Server 2022とSQL MIを同期し、準備後にフェイルオーバー。問題時はフェイルバックする
  • D. Azure MigrateでSQL Server 2022をAzure VMとして移行し後でSQL MIにアップグレードする
✅ 正解: C — Managed Instance Link

3要件（最小ダウンタイム・フェイルバック・移行中通常稼働）をすべて満たすのはMI Linkのみ。SQL 2022の双方向フェイルオーバーにより完全なフェイルバックが可能。

A が不正解（試験最頻出の引っかけ！）: Azure DMSのオンラインモードはSQL Server→SQL MIのGeneral Purposeには対応していますが、Business Critical tierへのオンライン移行には非対応。これがAZ-305で最も狙われるポイントです。
B が不正解: バックアップ・リストアは大きなダウンタイムが発生。「最小ダウンタイム」に反する。
D が不正解: VM→SQL MIの2段階移行はコスト・リスク・時間が増える。また「最小ダウンタイム」を満たせない。

DB管理ツール — Mac/Windows混在+PostgreSQL

  • B. Azure Data Studioを全員にインストールし、PostgreSQL拡張機能を追加する

A が不正解: SSMSはWindowsのみ。Mac2名は使用不可。PostgreSQL管理も不可。

テナント間データ共有 — コード不要・キー不要

自社（Tenant A）のADLS Gen2データをパートナー企業（Tenant B）に毎日自動共有。要件：①コーディング最小②毎日自動更新③パートナーにキー/シークレットを渡さない。最適な方法は？

  • A. ADLSのストレージアカウントキーをパートナーに共有する
  • B. AzCopyを使ってパートナーのAzureアカウントに毎日コピーするスクリプトをAzure Automationで実行する
  • C. Azure Data Shareでパートナーを招待し、スナップショットスケジュールを毎日に設定する
  • D. ADFパイプラインを作成してパートナーのAzureサブスクリプションにデータをコピーする
✅ 正解: C — Azure Data Share

テナント間共有・コード不要・毎日自動スナップショット・MSI認証（キー不要）の全要件をカバー。

A が不正解: ストレージキーの共有はセキュリティ上最悪。Full Access権限をパートナーに渡すことになる。

総合 — 異種DB移行+スキーマ変換

オンプレのOracle 19cデータベースをAzure SQL Database（互換レベル150）に移行します。スキーマ変換が必要で、PL/SQLコードのSQL Server T-SQLへの変換も含まれます。最適なツールは？

  • A. Azure Migrate（Database Migration機能）を使用して移行する
  • B. Azure Database Migration Service（オンラインモード）を使用してOracleから直接移行する
  • C. SSMA（SQL Server Migration Assistant for Oracle）を使用してスキーマ変換を実施後、DMSでデータ移行する
  • D. DMA（Data Migration Assistant）を使用してOracleからSQL Databaseに移行する
✅ 正解: C — SSMA → DMS の2段階

Oracle→SQL Serverの異種DB移行ではスキーマ変換が必要です。SSMA（SQL Server Migration Assistant for Oracle）がPL/SQL→T-SQLの変換を担当し、その後DMSでデータを移行する2段階アプローチが正解。

A が不正解: Azure Migrate（DMS）はOracle→SQL Serverの完全なスキーマ変換機能を持たない。
B が不正解: DMS単体ではOracleからSQL DatabaseへのT-SQLスキーマ変換ができない。データ移行は可能だがスキーマ変換は別ツールが必要。
D が不正解: DMA（Data Migration Assistant）はSQL Server→Azure SQL DBの評価・移行ツール。OracleなどSQL Server以外のソースには対応していない。OracleはSSMAの担当。
