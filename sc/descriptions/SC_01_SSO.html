SSO とは — 全体像と分類

シングルサインオン（SSO: Single Sign-On）とは、1回の認証で複数のシステム・サービスに連続的にアクセスできる仕組みです。認証の世界では「認証基盤レイヤー」に位置し、個々のサービスが持つ認証処理を集約・委譲することで、利便性とセキュリティの両立を実現します。

たとえるなら、会社の入館証（ICカード）で守衛所を一度通過すれば、社内の各部屋（サービス）にカードをかざすだけで入れる仕組みと同じです。各部屋が個別に「パスワードは？」と聞くことなく、守衛所が発行した「入館済みバッジ」を信頼します。

01

エージェント方式

エージェント方式は、各アプリケーションサーバにSSO用のエージェントモジュール（プラグイン）を組み込む方式です。たとえるなら、各部屋の扉に「鍵の代わりに共通のICカードを読むドアロック装置」を後付けするイメージです。どの部屋も同じ中央サーバに問い合わせて開錠の可否を判断します。

エージェント
各APサーバに組み込むモジュール。認証チェックとSSO認証サーバへの問い合わせを担当。
SSO認証サーバ
セッションCookieの発行と検証を一元管理。全エージェントからの問い合わせ先。
SSOトークン/Cookie
ドメイン共有Cookieでセッションを保持。エージェントはCookieを確認してアクセスを許可。
特徴
AP側の改修が必要。セキュリティポリシーの細かい制御が可能。エンタープライズでの実績が豊富。

シーケンス図 — エージェント方式 SSO

②③
エージェント（Agent）はAPサーバ内に組み込まれたモジュールです。リクエストを受けると最初にSSOセッションCookieの有無を確認し、なければSSO認証サーバへリダイレクトします。
⑤
認証成功後、SSO認証サーバはドメイン共有Cookieにセッション情報を書き込みます。このCookieが「入館済みバッジ」として全APサーバで通用します。
⑩
2つ目のAPへのアクセス時、ブラウザはCookieを自動送信するため、再ログインが不要になります。これがSSOの本質です。
!
限界：各APにエージェントモジュールを組み込む必要があるため、APの改修コストが発生します。非対応APや古いシステムへの適用が困難です。
02

リバースプロキシ方式

リバースプロキシ方式は、APサーバの前段にSSO機能を持つリバースプロキシサーバを配置する方式です。利用者からのすべてのリクエストはリバースプロキシを経由し、認証済みのリクエストのみが内部APへ転送されます。たとえるなら、マンションのオートロック（リバースプロキシ）を通らないと各部屋に到達できない構造です。

リバースプロキシ
前段でリクエストを受け付け、認証チェック後に内部APへ転送。APサーバはプロキシのみからの通信を受け付ける。
AP無改修
APサーバ側にエージェント不要。既存システムをそのままSSO化できる。レガシー統合に最適。
単一障害点
プロキシ障害でアクセス全断のリスク。冗長化（HA/負荷分散）が必須。
HTTPヘッダ転送
認証済みユーザ情報をHTTPヘッダ（X-Remote-User等）でAPに通知するケースが多い。

シーケンス図 — リバースプロキシ方式 SSO

⑧
プロキシはAPサーバへ転送する際に、HTTPヘッダ（例: X-Remote-User: alice）を付与します。APはこのヘッダを信頼してユーザを識別します。APは認証処理を行いません。
利点
APサーバ側の改修が一切不要なため、レガシーシステムのSSO化に最適です。認証ロジックがプロキシに集中するため管理が容易です。
!
単一障害点：リバースプロキシが停止するとすべてのAPへのアクセスが不能になります。必ず冗長構成（Active-Active 等）を取ることが必須です。
注意
ヘッダ偽装リスク：APサーバが内部ネットワークからの通信を前提としていない場合、攻撃者がHTTPヘッダを偽造してなりすましができます。APはプロキシ経由の通信のみを受け付けるアクセス制御が必要です。
03

代理認証方式

代理認証方式は、SSO基盤が利用者の認証情報（ID/パスワード等）を保管し、各APのログイン画面に代わりに入力・送信する方式です。APから見ると「利用者本人がログインした」ように見えます。たとえるなら、秘書がマスターパスワード帳を持ち、利用者の代わりにあらゆるサービスへのログインを代行するイメージです。

代理認証エージェント
ブラウザのクライアントソフトまたはサーバ側エージェントが、ID/PWを代わりに送信。
認証情報管理
各APのID/PWをSSO基盤で暗号化して保管。初回のみ利用者がAPへ手動ログインして記録。
AP改修不要
APは通常のフォーム認証のまま。ログイン画面がなくなるわけではなく、入力を代行するだけ。
リスク
SSO基盤に各APのID/PW（または暗号鍵）が集中するため、侵害時の影響が大きい。

シーケンス図 — 代理認証方式 SSO（フォーム代理入力型）

⑥
代理認証基盤は各APのログインフォームのID/PWフィールドを自動的に埋めて送信します。APは通常のフォーム認証を処理しているだけで、代理入力されていることを認識しません。
利点
APに全く手を加えずSSO化できます。特にレガシーシステムやWebフォーム認証のアプリに対して有効です。
危険
認証情報の集中リスク：SSO基盤が全APのID/PWを保持するため、SSO基盤が侵害されると全APへの不正アクセスが可能になります。認証情報の暗号化保管と厳重なアクセス制御が必須です。
04

Kerberos 認証方式

Kerberos認証は、KDC（Key Distribution Center）が発行するチケットを用いてSSOを実現するネットワーク認証プロトコルです。Active Directory（AD）のコアに採用されており、社内LAN環境での標準的なSSO方式です。たとえるなら、テーマパークの入場チケット（TGT）と各アトラクションの乗車券（ST）に例えられます。入場時に1回認証するだけで、個々のアトラクションでは乗車券を見せるだけで乗れます。

KDC
Key Distribution Center。AS（認証サービス）とTGS（チケット発行サービス）で構成。チケットの一元管理。
TGT
Ticket-Granting Ticket（チケット取得チケット）。初回認証後に取得。STを発行してもらうための「入場券」。
ST（サービスチケット）
Service Ticket。特定のサービスへのアクセス用チケット。TGTを使いTGSから発行してもらう。
レルム
Kerberosの管理ドメイン単位。複数レルム間をクロスレルム認証で連携可能（企業間SSO）。

シーケンス図 — Kerberos 認証（KDC / TGT / ST）

①②
AS Exchange：クライアントはASに自身のユーザ名と暗号化した認証子を送ります。ASは認証成功後にTGT（Ticket-Granting Ticket）を返却します。TGTはTGSの秘密鍵で暗号化されており、クライアントは中身を読めません。
③④
TGS Exchange：クライアントはTGTを使ってTGSに目的サービス用のST（サービスチケット）を要求します。TGTが有効期限内であればパスワード入力なしでSTが発行されます。
⑦⑧
別のサービスBにアクセスする場合、TGTを再利用してBのSTをTGSから取得します。この「TGT→各STの発行」という仕組みがSSOの核心です。
!
Pass-the-Ticket攻撃：攻撃者がTGTやSTを窃取すると、その有効期限内は正規ユーザとしてサービスにアクセスできます。またGolden Ticket攻撃（KRBTGTアカウントのハッシュ取得）も重大な脅威です。

核心ポイント

Kerberosの本質は「パスワードをネットワーク上に流さない」点にあります。認証にはタイムスタンプ付きの認証子（Authenticator）とセッション鍵を使うため、リプレイ攻撃にも強い設計です。ただし時刻同期（±5分以内）がKerberosの前提条件です。

05

SAML 2.0 認証方式

SAML（Security Assertion Markup Language）2.0は、XMLベースのアサーションを用いてインターネット越しにSSOを実現する標準プロトコルです。特に企業間のフェデレーション（異なる組織間のSSO）で広く使われます。たとえるなら、企業Aの「社員証（SAMLアサーション）」を持った社員が、企業Bの会議室（SP）に入るとき、企業A（IdP）が「この人は正規社員です」という証明書を発行し、企業Bがそれを信頼して入室を許可する仕組みです。

IdP
Identity Provider。ユーザを認証しSAMLアサーションを発行する。例: ADFS / Okta / Google。
SP
Service Provider。SAMLアサーションを受け取り検証してサービスを提供する。IdPを信頼する側。
SAMLアサーション
IdPがデジタル署名したXML文書。認証アサーション・属性アサーション・認可アサーションの3種。
バインディング
HTTP Redirect / HTTP POST / HTTP Artifact など、SAMLメッセージの転送方式。

シーケンス図 — SAML 2.0 SP-Initiated SSO（HTTP POST バインディング）

③
SAMLRequest（AuthnRequest）：SPがIdPに「この利用者を認証してください」と依頼するXMLメッセージです。Base64エンコードされてブラウザのリダイレクト（クエリパラメータ）またはPOSTで送られます。
⑧
SAMLアサーション：IdPが生成する署名付きXML文書で、「誰が（Subject）」「いつまで（Conditions）」「どのように認証されたか（AuthnStatement）」「どんな属性を持つか（AttributeStatement）」が記述されます。
⑩
SPはIdPの公開鍵でアサーションの署名を検証し、有効期限・受信者（SP URL）・NotBefore/NotOnOrAfterを確認します。すべて正当であればアクセスを許可します。
!
XML署名ラッピング攻撃（XSW）：SAMLアサーションのXML構造を細工し、署名検証をバイパスする攻撃です。XMLのSignedInfoの範囲外に不正な要素を挿入することで、正規署名は通過しながら内容を改ざんします。対策はXMLパーサーの厳格な設定とidempotentなアサーション処理です。
06

OAuth 2.0 — 認可委譲フロー

重要：OAuthは「認可」プロトコルであり「認証」プロトコルではありません。アクセストークンはリソースへのアクセス権を表しますが、「誰が認証されたか」という情報は含みません。認証にはOIDCを使います。

OAuth 2.0は、あるサービスが別サービスのリソースへのアクセス権限を、利用者の代わりに委譲してもらう仕組みです。たとえるなら、あなた（リソースオーナー）がホテルの部屋（リソース）の合鍵（アクセストークン）を、旅行代理店（クライアント）に期限付きで貸す仕組みです。代理店はあなたの本鍵（パスワード）を知る必要はありません。

リソースオーナー
保護されたリソースのオーナー（通常はエンドユーザ）。アクセス権委譲の同意を行う。
クライアント
リソースサーバへのアクセスを要求するアプリケーション。認可コードを受け取り、トークンに交換する。
認可サーバ
リソースオーナーの同意を得て、アクセストークンを発行する。Google / GitHub / Microsoft 等が担当。
スコープ
アクセス権の範囲を限定する文字列。例: read:profile write:posts 。最小権限の原則。

シーケンス図 — OAuth 2.0 認可コードフロー（Authorization Code Flow）

⑤
認可コード（Authorization Code）：フロントチャネル（ブラウザ）で取得する使い捨てのコードです。アクセストークンそのものではなく、トークンと交換するための短命な中間コードです。
⑦
PKCE（Proof Key for Code Exchange）：code_challenge（ランダム値のSHA-256）を事前に送り、トークン交換時にcode_verifierを提示することで、認可コードの横取り攻撃を防ぎます。
スコープ
アクセストークンにはスコープによる権限範囲が限定されます。read:profileしか許可していない場合、そのトークンでファイルの書き込みはできません。
!
OAuth2.0単独は認証に使えない：アクセストークンは「誰がどのリソースにアクセスできるか」を示すものです。「誰が認証されたか」は含まれません。認証にはOIDC（IDトークン）を重ねて使います。
07

OIDC（OpenID Connect）と JWT

OIDC（OpenID Connect）はOAuth 2.0の上に認証レイヤーを追加した仕様です。OAuth 2.0の認可コードフローに加えて、IDトークン（JWT形式）を発行することで「誰が認証されたか」の情報を提供します。たとえるなら、OAuth 2.0が「施設の入館証（アクセス権）」を発行する仕組みであれば、OIDCはさらに「入館した人物の身分証（IDトークン）」も同時に発行する仕組みです。

IDトークン（JWT）
OpenID Providerが署名したJWT。iss / sub / aud / exp / iat / nonce などのクレームを含む。認証結果の証明書。
OP
OpenID Provider（旧IdP）。ユーザ認証を行いIDトークンを発行する。SAMLのIdPに相当。
RP
Relying Party（旧SP）。OPが発行したIDトークンを受け取り検証するアプリケーション。
UserInfoエンドポイント
アクセストークンを使ってユーザの詳細プロファイル（メール・名前等）を取得するエンドポイント。

JWTの構造

JWT（JSON Web Token）の3パート構造

シーケンス図 — OIDC 認証フロー（Authorization Code Flow）

②
OIDCでは scope=openid を必須として指定します。これがOIDCとOAuth 2.0を区別するポイントです。追加で profile email などを指定することでユーザ属性も取得できます。
⑧
IDトークン（JWT）：iss（発行者）・sub（ユーザ識別子）・aud（受信者=RP）・exp（有効期限）・nonce（リプレイ攻撃防止）などのクレームが含まれます。
⑨⑩
RPはOPのJWKS URIから公開鍵を取得し、IDトークンの署名を検証します。JWKSはキャッシュ可能なため、毎回HTTPリクエストは不要です。
!
JWT改ざん：アルゴリズムをnoneに設定して署名なしで偽造する攻撃（Algorithm None Attack）があります。RPは必ず期待するアルゴリズム（RS256等）を明示的に検証し、noneを拒否する実装が必要です。

SAML vs OIDC — 試験頻出比較

SAML：XMLベース・エンタープライズ向け・SOAPとの親和性・企業間フェデレーション向け
OIDC：JSONベース（JWT）・モバイル/SPA向け・REST APIとの親和性・クラウドサービス向け
共通点：どちらもIdP（OP）によるSSO。SP（RP）はIdPを信頼して認証を委託。

08

SAML vs OAuth 2.0 vs OIDC — 徹底比較

この3つは「似ているようで目的が根本的に異なる」ため、試験でも実務でも混同しがちです。まず大前提として「SAML＝認証・フェデレーション、OAuth 2.0＝認可、OIDC＝OAuth 2.0の上に乗った認証」という立ち位置を押さえてください。

レイヤー構造図 — OAuth / OIDC / SAML の関係

試験で問われる「核心の違い」3点

重要
OAuth 2.0 は「認証」ではなく「認可」 — アクセストークンは「何ができるか（スコープ）」を示すものであり、「誰であるか」は含みません。OAuth 2.0 単独をログイン認証に使うのは設計上の誤りです（IDトークンがないため、誰が認可したか分からない）。
OIDC
OIDC = OAuth 2.0 ＋ IDトークン（scope=openid） — OIDCは OAuth 2.0 の上にscope=openidを追加し、IDトークン（JWT）を発行します。IDトークンにはsub（ユーザID）・iss（発行者）・nonce（リプレイ防止）が含まれ、「誰が認証されたか」を証明できます。
!
SAML は独立した認証プロトコル（OAuth/OIDCと無関係） — SAMLはXMLベースの独自設計であり、OAuthとは無関係に動作します。エンタープライズ（オンプレミス/企業間）向け、OIDCはモバイル・REST API・クラウドネイティブ向けというすみ分けが一般的です。

エンタープライズ適性 高い（AD/ADFS連携） 中 中〜高
代表的な脆弱性 XSW攻撃（XML署名迂回） CSRF（stateなし）/ PKCEなしの認可コード横取り Algorithm None Attack / nonce未検証

試験対策 — 三者の決め手フレーズ

「OAuthは鍵（アクセス権）の配布」「OIDCはOAuthに身分証（IDトークン）を追加」「SAMLは社員証（XML）で企業間を渡り歩く」

試験でよく問われるのは：①「OAuthは認証ではなく認可」②「OIDCはscope=openid を追加することでOAuthと区別される」③「SAMLはXMLベースでOAuthと無関係」④「IDトークンのnonceはリプレイ攻撃防止」⑤「XSW攻撃はSAMLの署名検証を迂回する」の5点です。

08

SSOに対する脅威・攻撃・対策

SSOは「1回の認証で複数サービスへのアクセス」を実現するため、SSO基盤が侵害されると全サービスへの不正アクセスが可能になる「Single Point of Risk（単一侵害点）」でもあります。

セッションハイジャック

SSOセッションCookieを盗み取ることで、認証なしに全サービスにアクセスできる。XSSやネットワーク盗聴が主な手法。

対策：Cookie の Secure / HttpOnly 属性・HTTPS必須・CSP設定・短いセッション有効期限

Pass-the-Ticket（Kerberos）

KerberosのTGTやSTを窃取し、有効期限内に正規ユーザとして各サービスに成り済ます攻撃。Mimikatzなどで実行可能。

対策：Credential Guard / チケット有効期限の短縮 / Protected Users グループ設定

Golden Ticket攻撃

KDCのKRBTGTアカウントのハッシュを取得し、任意ユーザ・有効期限のTGTを偽造する高度な攻撃。ドメイン全体を掌握可能。

対策：KRBTGTパスワードの定期変更（2回）/ ドメインコントローラの厳重保護 / SIEM監視

CSRF（OAuth CSRFを含む）

OAuthの認可コードフローで state パラメータを省略した場合、攻撃者が被害者のアカウントに自身のアクセス権を結びつけるアカウント乗っ取り攻撃が可能。

対策：state パラメータのランダム化・検証必須 / PKCE の導入

XML署名ラッピング（SAML XSW）

SAMLアサーションのXML構造を細工し、有効な署名を残しながら偽のアサーション要素を挿入。署名検証をバイパスしてなりすましを実現。

対策：SAMLライブラリの最新化 / XMLパーサーの厳格設定 / idの検証

JWT改ざん（Algorithm None等）

JWTのヘッダのalgを"none"にしてペイロードを改ざんしたトークンを送付。署名検証を無効化してなりすます攻撃。RS256→HS256の切替攻撃もある。

対策：サーバ側でalg"none"を明示拒否 / 許可アルゴリズムのホワイトリスト化

攻撃手法仕組み・概要主な対策

09

過去問スタイル 練習問題

情報処理安全確保支援士試験の出題傾向に沿った練習問題です。選択肢をクリックすると正誤と解説が表示されます。

Q1SSOのリバースプロキシ方式の特徴として、最も適切なものはどれか。
正解：イ
リバースプロキシ方式は、APサーバの前段に置いたプロキシが認証を一元管理する方式です。APサーバ側の改修は不要です。ア：エージェント方式の説明です。ウ：代理認証方式の説明です。エ：誤りです。認証処理を担います。
Q2Kerberos認証においてTGT（Ticket-Granting Ticket）の役割として、最も適切なものはどれか。
正解：ウ
TGTは初回ログイン後にAS（認証サービス）から取得するチケットです。このTGTをTGS（チケット発行サービス）に提示することで、パスワード再入力なしに各サービス用のST（サービスチケット）を取得できます。テーマパークの「フリーパス（入場チケット）」に例えられます。ア：STの説明です。
Q3OAuth 2.0について、最も適切な説明はどれか。
正解：イ
OAuthは「認可委譲」のプロトコルです。誰がアクセスを認可されているかを示しますが、誰が認証されたかという情報はありません。認証はOIDCが担当します。ウ：逆です。PKCEは認可コードフローに組み合わせて使います。エ：JWTは一形式であり、必須ではありません。
Q4SAML 2.0のXML署名ラッピング攻撃（XSW攻撃）に対する主な対策として、最も適切なものはどれか。
正解：ウ
XSW攻撃は、XMLの署名範囲外に不正な要素を挿入して署名検証をバイパスします。対策は、XMLパーサーが署名対象要素をIDで厳格に特定し、署名範囲外の要素を無視することです。SAMLライブラリの定期的な更新も重要です。ア：暗号化は機密性を守りますが、解析後の改ざんは防げません。
Q5OIDCのIDトークン（JWT）に含まれるnonceクレームの主な目的として、最も適切なものはどれか。
正解：ウ
nonceはRP（クライアント）が認証リクエスト時にランダムに生成し、IDトークンに同じ値が含まれていることを検証することで「このIDトークンが自分のリクエストへの応答である」ことを確認できます。これにより傍受したIDトークンを再送するリプレイ攻撃を防ぎます。ア：issクレームの説明。イ：expクレームの説明。エ：subクレームの説明。
Q6SSO基盤に対する「Golden Ticket攻撃」の説明として、最も適切なものはどれか。
正解：イ
Golden Ticket攻撃はKerberos特有の高度な攻撃です。KDCのKRBTGTアカウントのハッシュを入手すると、攻撃者は任意のユーザ名・グループ・有効期限でTGTを偽造できます。ドメイン管理者権限のTGTを偽造することでAD全体を掌握可能です。対策にはKRBTGTパスワードを短期間で2回変更する必要があります（古いチケットを無効化するため）。
Q7SAMLとOIDCの比較として、最も適切なものはどれか。
正解：ウ
SAMLはXMLベースでSOAP/ブラウザリダイレクト向き、企業間フェデレーション（特にオンプレとSaaS連携）に実績があります。OIDCはOAuth 2.0の上に認証レイヤーを追加したもので、JSONベース（JWT）・REST API・モバイルSPA向きです。ア：逆です。SAMLがXMLで、OIDCがJSONベースです。イ：OIDCはOAuth 2.0を拡張したプロトコルです。

試験対策 5つの鉄則

1. OAuthは「認可」、OIDCは「認証」 — アクセストークンに認証情報はない
2. Kerberosは「チケット方式」 — TGT→ST発行がSSOの核心、LAN内向け
3. SAMLは「XMLアサーション」、OIDCは「JWTトークン」
4. リバースプロキシ方式はAP無改修・単一障害点に注意
5. Golden Ticket = KRBTGTハッシュ奪取、XSW = XML署名の迂回
