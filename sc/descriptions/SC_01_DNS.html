01

DNSの基礎と全体像

DNS（Domain Name System）は、ドメイン名をIPアドレスに変換する分散型階層データベースです。設計当初にセキュリティが考慮されておらず、後付けでの対策が求められてきました。

分散・階層型
ルート→TLD→権威サーバの3層で世界のドメインを管理。単一障害点なし。
キャッシュ機構
リゾルバがTTL秒間回答をキャッシュ。高速化と負荷分散を実現。攻撃の標的にもなる。
UDP/53 使用
通常はUDP/53。コネクションレスで高速だが送信元IPの偽装（スプーフィング）が容易。
認証なし（設計上）
オリジナルDNSは応答の正当性を検証する仕組みを持たない。DNSSECが後付けで追加された。

TTL（Time To Live）: キャッシュの有効期間。長すぎると変更が反映されず、キャッシュ汚染時の被害が長時間継続する。

たとえ話：DNSは「インターネットの電話帳」です。キャッシュポイズニングは電話帳の番号を書き換えて詐欺グループへ誘導する攻撃、DNSアンプは電話帳に大量の返信要求を送り業務不能にする攻撃です。

03

DNSキャッシュポイズニング

フルサービスリゾルバのキャッシュに偽のDNS応答を注入し、正規ドメインへのアクセスを偽サイトへ誘導する攻撃です。TTL期間中は多数の利用者が被害を受け続けます。

たとえ話：電話帳（DNSキャッシュ）の「銀行A」の電話番号を詐欺グループの番号にこっそり書き換える攻撃。電話帳を参照した全員が詐欺グループに繋いでしまい、TTL期間が終わるまで書き換えが効き続けます。

核心
トランザクションID（TXID）の推測：DNS応答照合に使う16bitの識別子（65,536通り）。当時はランダム性が低く総当たりが現実的だった。
カミンスキー
2008年にDan Kaminskiが公開した実用的手法。ランダムなサブドメイン（例: x7f3k.bank.jp）を大量に問い合わせ、NSレコードごと書き換えを試みる。1問い合わせあたり65,536回の偽応答試行が可能。
即効対策
ソースポートランダム化：送信元UDPポート（16bit）× TXID（16bit）≒ 2の32乗通りに推測空間を拡大。統計的に実用的な攻撃が困難に。
04

キャッシュポイズニング対策

対策は複数レイヤーで実施されます。IDの推測困難化（ランダム化）と、応答の正当性を数学的に証明するDNSSECが二大柱です。

図 2 — キャッシュポイズニング対策の多層防御モデル

暗号・認証層（根本的解決） DNSSEC（署名検証）/ DoT（DNS over TLS）/ DoH（DNS over HTTPS）— 暗号的に正当性を保証
プロトコル層（推測困難化） ソースポートランダム化（カミンスキー対策）/ 0x20エンコード（大小文字ランダム化）/ TXIDランダム化
ネットワーク層（通信路保護） BCP38 / uRPFでIPスプーフィングを送出元で遮断 / ファイアウォールで外部からの偽応答をフィルタリング
運用・監視層 DNSログの異常監視 / TTLの適切設定 / リゾルバソフトウェアの最新化 / パッチ迅速適用
ソースポートランダム化
問い合わせごとにUDPポートをランダム化。TXID×ポート≒2の32乗通りに拡大。カミンスキー攻撃への即効対策。
0x20エンコード
クエリのドメイン大小文字をランダム化（wWw.BaNk.Jp）し応答が同じパターンかを検証。TXID以外の認証手段。
DNSSEC（根本対策）
デジタル署名で応答の正当性を暗号的に保証。偽応答は署名不一致で検出可能。
DoT / DoH
DNSクエリ・応答をTLS暗号化。通信路での盗聴・改ざんを防止。DNSSECと相補的。
05

DNSSEC（DNS Security Extensions）

DNSSECはDNSにデジタル署名を追加することで、応答データの完全性（改ざん検知）と真正性（正規ゾーン管理者からの応答）を保証する拡張仕様（RFC 4033〜4035）です。

たとえ話：DNSSECは「公証役場が押印した電話帳」です。誰かが電話帳を書き換えようとしても、公証役場の印鑑（デジタル署名）が変わってしまうため改ざんを検出できます。ただし電話帳の内容は暗号化されていない（中身は誰でも見える）点に注意。

DNSSECとDoT/DoHの違い（最頻出）

DNSSECは「応答が本物かどうかの署名検証」であり通信の暗号化ではない。クエリ内容の秘匿はDoT/DoHが担う。DNSSECは「正しい場所へ案内する」、DoT/DoHは「案内の会話を秘密にする」という役割分担。

DNSリフレクション攻撃

攻撃者が送信元IPアドレスを標的のIPに偽装してDNSサーバに問い合わせを送ることで、DNSサーバの応答を標的に集中させる攻撃です。

たとえ話：「差出人住所を被害者の住所にして」大量のアンケート葉書を各家庭（DNSサーバ）に送りつける攻撃。返信が全て被害者宅に殺到し、郵便受けが機能不全になります。

攻撃者ATTACKER

… × N 台
DNS応答が「標的IPアドレス」へ集中送信される
標的サーバVICTIM
帯域飽和
サービス停止
BCP38（RFC 2827）対策： ISP境界ルータでソースIPが自ASのプレフィックス外のパケットをフィルタリング（uRPF）。スプーフィングを送出元で抑止することでリフレクション攻撃の根本対策になる。
問題
オープンリゾルバ（Open Resolver）：外部の任意のホストからの再帰問い合わせに応じるDNSサーバ。本来は自組織内クライアントのみに応じるべき。インターネット上に無数に存在し踏み台として悪用される。
対策1
BCP38 / uRPF：ISPがネットワーク境界でIPソースアドレスを検証し、偽装パケットの送出を防ぐ。リフレクション攻撃の根本抑止。
対策2
オープンリゾルバの廃止：外部からの再帰問い合わせをACLで拒否。BINDの allow-recursion { 自組織アドレス; }; 設定。
対策3
RRL（レスポンスレートリミット）：同一宛先への応答を一定レートに制限。踏み台になった際のトラフィック増幅を抑制。
07

DNSアンプ攻撃（増幅型DDoS）

リフレクション攻撃の発展型で、小さな問い合わせに対して非常に大きな応答を返すDNSの特性を悪用して帯域を増幅させます。BAF（Bandwidth Amplification Factor）が高いほど効率的な攻撃が可能です。

08

DNS水攻め攻撃（ランダムサブドメイン攻撃）

ランダムに生成したサブドメイン（例: a1b2c3.example.jp）を大量に問い合わせ、対象ドメインの権威DNSサーバを応答処理で枯渇させる攻撃です。存在しないドメインはキャッシュに入らないため、リゾルバが毎回権威NSへ転送し二重の過負荷が生じます。

たとえ話：図書館（権威DNS）に「ランダムな書名の本を検索して」という問い合わせを無数に送る攻撃。そんな本は存在しない（NXDOMAIN）のですが、司書はその都度棚を探し回らなければならず業務が停滞します。キャッシュに入らないので翌日も同じ探索を繰り返します。

水攻めの特徴： IPスプーフィング不要 → BCP38は無効。正規IPのボットネットから大量送信するだけで成立。キャッシュが効かないためリゾルバと権威NSの双方に二重の負荷がかかる。
核心
キャッシュ無効化の連鎖：ランダムサブドメインはキャッシュに入らない → リゾルバが全クエリを権威NSへ転送 → 権威NSとリゾルバの両方が過負荷になる二重攻撃。
対策1
Negative キャッシュ（SOA MINIMUM値）：NXDOMAINにも一定期間のキャッシュを設定。同一ランダムドメインへの繰り返しを抑制（ランダムなので効果は限定的）。
対策2
RRL（レスポンスレートリミット）：同一クライアントIPへの応答レートを制限。ボットネットの集中攻撃を緩和。
対策3
DNS Firewall / RPZ（Response Policy Zone）：既知の悪意あるドメインパターンをポリシーゾーンで遮断。ボットネットのC&Cドメインへの問い合わせ遮断にも有効。

過去問スタイル 練習問題

情報処理安全確保支援士試験の出題傾向に沿った練習問題です。選択肢をクリックすると正誤と解説が表示されます。

Q1DNSキャッシュポイズニング攻撃の説明として最も適切なものはどれか。
正解：ウ
DNSキャッシュポイズニングはフルサービスリゾルバのキャッシュに偽応答を書き込み利用者を偽サイトへ誘導する攻撃です。
ア：DNS水攻め攻撃の説明です。イ：DNSリフレクション攻撃の説明です。
Q2カミンスキー攻撃への緊急対策として実装されたものはどれか。
正解：イ
カミンスキー攻撃（2008年）への緊急対策が「ソースポートランダム化」です。TXID（16bit）× 送信元ポート（16bit）≒ 2の32乗通りに推測空間を拡大し実用的な攻撃を困難にしました。ウのDNSSECが根本的解決策ですが、攻撃公表時点での即時対応はソースポートランダム化でした。
Q3DNSSECに関する記述として適切なものはどれか。
正解：イ
DNSSECの鍵構造の核心：ZSK→各RRsetに署名（RRSIG）、KSK→ZSKのDNSKEYに署名、KSKのハッシュを親ゾーンにDS登録で信頼チェーン確立。
ア：誤り。DNSSECは暗号化でなく「署名検証」。暗号化はDoT/DoH。ウ：誤り。DNSSECはアンプ攻撃対策にならず逆にRRSIGで応答増大の可能性。エ：誤り。DSレコードは「子ゾーンのKSKハッシュを親ゾーンに登録するレコード」。
Q4DNSアンプ攻撃を防止するために有効な対策の組合せとして最も適切なものはどれか。
正解：イ
DNSアンプ攻撃はIPスプーフィングを前提とするため、BCP38でスプーフィングを防ぐことが根本対策。オープンリゾルバ廃止で踏み台になることを防ぎます。
ア：DNSSECはアンプ攻撃対策にならない（逆に増幅増加）。エ：ソースポートランダム化はキャッシュポイズニング対策。
Q5DNS水攻め攻撃（ランダムサブドメイン攻撃）の特徴として最も適切なものはどれか。
正解：ウ
水攻め攻撃の本質は「ランダムなサブドメインはキャッシュに入らない」こと。全クエリが権威NSへ転送されるため二重の過負荷が発生します。
ア：水攻めはIPスプーフィング不要→BCP38は有効でない。これが最重要の区別ポイント。イ：キャッシュポイズニングの説明。エ：DNSアンプ攻撃の説明。
Q6DNS over TLS（DoT）を利用する主な目的として最も適切なものはどれか。
正解：ウ
DoT（RFC 7858）はTCPポート853を使用しDNSをTLS暗号化。通信路での盗聴・改ざん防止が主目的。
ア：これはDNSSECの説明。DoTは暗号化（秘匿）、DNSSECは署名（正当性検証）の役割分担を混同しないこと。

重要用語まとめ

フルサービスリゾルバ再帰問い合わせを行いキャッシュするDNSサーバ。ISP・企業内に設置。キャッシュポイズニングや水攻めの標的。
権威DNSサーバ特定ゾーンのDNSデータを管理・提供するサーバ。水攻め攻撃の直接の標的。
TTL（Time To Live）DNSキャッシュの有効期間。汚染時の被害継続時間に影響。
トランザクションIDDNSクエリ・応答を照合する16bitの識別子。カミンスキー攻撃の推測対象。
ソースポートランダム化カミンスキー攻撃対策。送信元UDPポートをランダム化し推測空間を約2の32乗に拡大。
0x20エンコードクエリのドメイン名大小文字をランダム化し応答の正当性を検証する技法。
DNSSECDNS Security Extensions。デジタル署名でDNS応答の完全性・真正性を保証。暗号化ではない。
KSK（鍵署名鍵）ZSKのDNSKEYに署名する鍵。長期間管理。親ゾーンにDSレコードを登録。
ZSK（ゾーン署名鍵）ゾーン内の各RRsetに署名する鍵。KSKより短期間でローテーション。
RRSIGリソースレコードセットに付与されたDNSSECの電子署名レコード。ZSKで生成。
DNSKEYDNSSECの公開鍵（KSK・ZSK）を格納するリソースレコード。
DS（Delegation Signer）子ゾーンのKSKハッシュを親ゾーンに登録するレコード。信頼チェーンの「継ぎ手」。
NSEC / NSEC3DNSSECの否定応答レコード。NSEC3はゾーン列挙攻撃対策でハッシュ化。
DoT（DNS over TLS）TCP 853でDNSをTLS暗号化。盗聴・通信路改ざん防止。DNSSECと相補的。
DoH（DNS over HTTPS）TCP 443でDNSをHTTPS暗号化。プライバシー保護とフィルタ回避の両面。
オープンリゾルバ外部からの再帰問い合わせに応じるDNSサーバ。リフレクション・アンプ攻撃の踏み台。廃止が基本対策。
BCP38（RFC 2827）ネットワークエッジでのソースIPフィルタリング標準。IPスプーフィングを防ぎリフレクション・アンプ攻撃の根本対策。
RRL（レスポンスレートリミット）DNSサーバが同一宛先への応答レートを制限する機能。アンプ・水攻め対策。
BAF（増幅係数）Bandwidth Amplification Factor。クエリサイズに対する応答サイズの比率。DNSアンプ攻撃の効率指標。
RPZ（Response Policy Zone）DNS Firewallの実装技術。ドメインベースのポリシーで悪意ある問い合わせを遮断。水攻め・マルウェアC&C対策。
uRPF（Unicast RPF）ルータでの逆経路確認によるソースIP検証。BCP38の実装手段の一つ。
RTBHRemotely Triggered Black Hole。大規模DDoS時にBGPで特定IPのルートを廃棄してトラフィックを遮断。

試験対策 6つの鉄則

1. キャッシュポイズニング ≠ DDoS — 前者は「誘導」、後者は「停止」が目的
2. DNSSEC は暗号化ではない — 署名検証（正当性確認）、通信秘匿は DoT/DoH
3. 水攻めはIPスプーフィング不要 — BCP38が有効でない唯一のDNS攻撃
4. アンプ攻撃にDNSSECは逆効果 — RRSIG等で応答サイズが増加する
5. KSKはZSKに署名、ZSKはRRsetに署名 — 二層構造を混同しない
6. カミンスキー対策はソースポートランダム化、根本対策はDNSSEC
