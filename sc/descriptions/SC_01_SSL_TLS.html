01

SSL/TLSの位置づけ — 全体像の中での役割

SSL（Secure Sockets Layer）/ TLS（Transport Layer Security）は、インターネット通信を暗号化し、盗聴・改ざん・なりすましから守るプロトコルです。SSL は古い名称（Netscape 社が1990年代に開発）で、現在の正式名称は TLS ですが、慣習的に「SSL/TLS」と呼ばれます。現在有効なバージョンは TLS 1.2 と TLS 1.3 のみで、それ以前のバージョンはすべて非推奨または廃止されています。

たとえ話：デジタル通信の「護衛艦」

インターネット上のデータ送信を「荷物を運ぶ輸送船」にたとえると、通常の HTTP 通信は甲板に荷物を無防備に置いたまま航行する船です。誰でも荷物を見たり、すり替えたり、偽の船に誘導したりできます。HTTPS（HTTP over TLS）は荷物を施錠したコンテナに入れ、護衛艦とともに航行する船です。

機密性
AES-256・ChaCha20等で通信内容を暗号化。第三者が盗聴しても解読不可能。
完全性
MAC / AEAD で改ざん検知。1ビットでも変更されれば接続が切断される。
真正性
サーバ証明書で接続先が本物と確認。フィッシングサイトへの誘導を防ぐ。
否認防止
デジタル署名により、通信の送受信を事後否認不可。法的証拠として有効。

重要：SSL/TLS はアプリケーション層とトランスポート層の間に位置する汎用セキュリティ層です。HTTP だけでなく SMTP, FTP, LDAP など任意のプロトコルに適用できます。HTTPS＝HTTP over TLS、SMTPS＝SMTP over TLS を意味します。

02

常時SSL化の必要性と HSTS

かつては「ログイン・決済ページだけ HTTPS」という部分SSL化が一般的でした。しかし現在はWebサイト全体を HTTPS 化する「常時SSL（Always-On SSL）」が標準であり、Google もランキングシグナルとして採用しています。

たとえ話：一部だけ守る城壁の問題

部分SSL化は「正門だけ鉄扉、裏門は木の扉、城壁の一部は柵」のようなものです。攻撃者は弱い部分から侵入します。常時SSL化は「城壁全体を石造りにしてすべての入口を鉄扉に統一」することです。

Cookie 盗聴防止
セッション ID を含む Cookie が HTTP で流れると、セッションハイジャックのリスク。全ページ HTTPS で防止。
中間者攻撃防止
公衆 Wi-Fi での HTTP 通信は盗聴・改ざん容易。常時 SSL で全ページを保護。
HTTP/2 対応
HTTP/2（多重化・ヘッダ圧縮で高速化）は HTTPS 上でのみ動作。性能向上にも HTTPS が必要。
SEO 向上
Google が HTTPS をランキングシグナルとして使用。同一コンテンツなら HTTPS サイトが上位表示。

HSTS（HTTP Strict Transport Security）

HSTS は 「このサイトへは今後必ず HTTPS でアクセスしなさい」 とブラウザに指示するレスポンスヘッダです。一度受信したブラウザは有効期間内の HTTP アクセスを自動的に HTTPS にリダイレクトします（SSL ストリッピング攻撃を防ぐ）。

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
# max-age : 有効期間（秒）。31536000 ≒ 1年
# includeSubDomains : サブドメインにも適用
# preload : ブラウザのHSTSプリロードリストに登録申請

常時 SSL の本質

「鎖の強度は最も弱い環で決まる」原則と同様に、平文 HTTP の経路が一つでも残れば、そこが攻撃の糸口になります。全ページを暗号化して初めて安全になります。HSTS の preload でブラウザ初回アクセスからの HTTP 接続さえ防ぐのが最高水準です。

TLS 1.2 ハンドシェイクのシーケンス

TLS 1.2 のハンドシェイクは2-RTT（2往復）で暗号化パラメータを合意します。「Hello 交換 → サーバ認証 → 鍵交換 → 暗号化開始」の 4 フェーズに分かれます。たとえ話では「新幹線の乗車前確認」のようなものです。改札口（サーバ証明書確認）を通過し、指定席を決め（暗号スイート合意）、座席番号を共有し（鍵交換）、乗車（暗号化通信開始）します。

TLS 1.3 ハンドシェイク — 何が変わったか

TLS 1.3（RFC 8446, 2018年）は1-RTT（1往復）を実現し、速度・セキュリティの両面で大幅に改善されました。RSA 鍵交換・静的 DH・古い暗号を全廃し、PFS（Perfect Forward Secrecy）を強制します。

サーバWEB SERVER
① ClientHello
暗号スイートリスト, Client Random
+ key_share 拡張：ECDHE 一時公開鍵を先送り（RTT削減の核心）
クライアントの key_share を受信
→ 即座に鍵交換完了・セッション鍵導出
② ServerHello
+ key_share 拡張：サーバ ECDHE 一時公開鍵を返送
ここから下はすべて暗号化（ServerHello 直後から！）
③ {EncryptedExtensions}ENC
TLS 拡張（ALPN 等）を暗号化して送信（1.2 では平文）
④ {Certificate}ENC

⑤ {CertificateVerify}ENC

TLS 1.3 の革新ポイント

TLS 1.3 の核心は ClientHello に ECDHE 公開鍵（key_share 拡張）を先送りすることです。これによりサーバは ClientHello 受信と同時に鍵交換を完了できるため、ServerHello 以降をすべて暗号化できます。往復が 1 回で済むだけでなく、証明書まで暗号化されることでプライバシーも向上します。

暗号スイートと鍵交換アルゴリズム

暗号スイート（Cipher Suite）は「どの鍵交換・認証・暗号化・ハッシュアルゴリズムを組み合わせるか」を一括指定する文字列です。TLS 接続のネゴシエーションで双方が共通してサポートする最も優先度の高いスイートが選ばれます。

TLS 1.2 暗号スイートの読み方

TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
ECDHE
鍵交換：Elliptic Curve DH Ephemeral — 楕円曲線 DH の一時鍵。PFS 対応。毎回異なる鍵ペアを生成して破棄。
RSA
認証：サーバ証明書の署名アルゴリズム。RSA か ECDSA か。
AES_256_GCM
暗号化：AES 256bit, GCM モード（AEAD）。暗号化と完全性保護を同時実行。
SHA384
PRF/MAC ハッシュ：鍵導出・Finished メッセージの HMAC に使用。

TLS 1.3 の暗号スイート（5 種類のみ）

TLS_AES_128_GCM_SHA256
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
TLS_AES_128_CCM_SHA256
TLS_AES_128_CCM_8_SHA256

TLS 1.3 では鍵交換アルゴリズム（ECDHE/DHE）が暗号スイートから切り離されました。鍵交換は拡張（key_share / supported_groups）で別途ネゴシエーションされます。暗号スイートはAEAD暗号とHKDFハッシュの組み合わせのみを指定します。

Perfect Forward Secrecy（PFS）のたとえ話

RSA 鍵交換（TLS 1.2 まで）は「マスターキー（サーバ秘密鍵）で南京錠を開けて荷物を配達」する方式です。マスターキーが盗まれると、過去にキャプチャした通信もすべて解読可能になります。ECDHE による PFS は「配達のたびに使い捨ての南京錠を使う」方式です。マスターキーが漏洩しても、過去の通信には影響しません。

×
RSA 鍵交換（TLS 1.2 以前）：Pre-Master Secret をサーバ公開鍵で暗号化して送信 → サーバ秘密鍵が漏れると過去の録音通信がすべて復号可能。TLS 1.3 で廃止。
○
ECDHE（Diffie-Hellman Ephemeral）：セッションごとに一時鍵ペアを生成・使用後破棄 → 秘密鍵漏洩でも過去通信は復号不可。TLS 1.3 で必須化。

Web ブラウザによるサーバ証明書の検証プロセス

ブラウザはサーバから受け取った X.509 証明書を6 ステップで検証します。1 ステップでも失敗すると「証明書エラー」が表示され、接続がブロックされます。

証明書検証の 6 ステップ

①
信頼チェーン（Chain of Trust）検証：
サーバ証明書の署名者（中間CA）→ 中間CAの署名者（ルートCA）と辿り、ブラウザが信頼するルートCA証明書ストアに到達するか確認。たとえ話：「身分証の発行元が政府機関か」を確認するようなもの。
②
署名の検証：
上位CA の公開鍵で証明書内のデジタル署名を復号し、証明書の内容ハッシュと一致するか確認。改ざん検知。
③
有効期限の確認：
証明書の notBefore（開始日時）と notAfter（終了日時）が現在時刻を含むか確認。有効期限切れは即エラー。
④
失効確認（OCSP / CRL）：
OCSP（リアルタイム照会）または CRL（失効リスト参照）で証明書が失効していないか確認。秘密鍵漏洩後に失効された証明書の不正使用を防ぐ。
⑤
ドメイン名の一致確認（CN / SANの検証）：
証明書の Subject Alternative Names（SAN） または CN（Common Name） が、アクセスしている URL のホスト名と一致するか確認。ワイルドカード（*.example.com）も照合。
⑥
鍵使用用途の確認（Key Usage）：
証明書の Key Usage / Extended Key Usage 拡張に「TLS Web Server Authentication」が含まれるか確認。

ブラウザの証明書エラーと原因

NET::ERR_CERT_AUTHORITY_INVALID信頼チェーン失敗（検証ステップ①②）自己署名証明書、プライベートCA

TLS 拡張仕様 — SNI・ALPN と 0-RTT

TLS には ClientHello / ServerHello に追加情報を載せる「拡張（Extensions）」機能があります。SNI と ALPN は特に試験頻出の重要拡張です。

SNI（Server Name Indication）

1 つの IP アドレスで複数の HTTPS サービス（バーチャルホスト）を運用するための拡張です。TLS ハンドシェイクの開始時（ClientHello）にアクセス先ホスト名をサーバへ通知し、サーバはそれに対応する証明書を選択して提示します。

たとえ話：マンションの「玄関ロック」にたとえると、建物（IP アドレス）は一つですが、何号室か（ドメイン名）を最初に言うことで、そのドメインの住人が出てくる仕組みです。SNI 以前は「建物に 1 枚の証明書」しか貼れませんでした。

シーケンス図 3 — SNI を使った複数ドメインホスティング

ブラウザCLIENT
サーバ 203.0.113.501つのIPで複数ドメインをホスト
ClientHello
SNI 拡張: server_name = "shop.example.com"
ハンドシェイク開始時にホスト名を平文で通知（！）
SNI を確認 → "shop.example.com" 用の証明書を選択
（同じ IP で "blog.example.com" 用も別途保有）
ServerHello + Certificate（shop.example.com 用）

プライバシー上の注意：SNI は ClientHello で平文送信されるため、ネットワーク上の第三者が「どのドメインにアクセスしているか」を観測できます。これを暗号化するECH（Encrypted Client Hello）が TLS 1.3 の拡張として標準化中です。

session_ticket前回のセッションパラメータをチケットとして保存・再利用し、フルハンドシェイクを省略TLS 1.2 でのセッション再利用。TLS 1.3 は PSK（Pre-Shared Key）方式。

TLS トンネリング（HTTP CONNECT）

プロキシサーバを経由して HTTPS 通信を行う際に使用される仕組みです。クライアントは HTTP CONNECT メソッドを使ってプロキシにトンネルの確立を依頼し、その後 TLS ハンドシェイクを行います。

たとえ話：プロキシは「交換局」のようなものです。CONNECT によって「XX さん宛の不透明な封筒を中継してほしい」と依頼します。交換局（プロキシ）は封筒の中身（TLS 暗号化データ）を開けられないまま転送します。

シーケンス図 4 — プロキシ経由 TLS トンネリング（HTTP CONNECT）

クライアントBROWSER
プロキシHTTP PROXY
宛先サーバHTTPS SERVER
① CONNECT www.example.com:443 HTTP/1.1
プロキシに「このホスト:ポートへのトンネルを開けてほしい」と要求
② プロキシが宛先サーバへ TCP 接続確立
③ HTTP/1.1 200 Connection Established
プロキシがトンネル確立を通知。以後プロキシは中身を見ずに転送するだけ。
④ クライアント〜宛先サーバ間で TLS ハンドシェイク（プロキシは不透明に中継）
⑤ 暗号化された HTTPS 通信（プロキシは中身を解読できない）

SSL インスペクション（SSL Inspection / HTTPS Inspection）：企業のセキュリティ機器（Next-Gen Firewall 等）が CONNECT トンネルを「中断」し、サーバになりすまして独自証明書を提示する手法。クライアントには企業 CA が発行した証明書が提示されます。通信内容の検査や DLP（情報漏洩防止）に使用されますが、プライバシーへの影響と管理体制の整備が必要です。

TLS クライアント認証（相互 TLS / mTLS）

通常の TLS は「クライアントがサーバを認証」する一方向認証ですが、TLS クライアント認証（mTLS : Mutual TLS）では「サーバもクライアントを証明書で認証」する双方向認証です。企業 VPN・API ゲートウェイ・金融 API・電子申告（e-Tax）等で使用されます。

たとえ話：通常の TLS は「居酒屋の看板（サーバ証明書）を確認してから入店」するようなものです。mTLS は「入店時にお互いが社員証を見せ合う」クローズドな VIP ルームのような仕組みです。

シーケンス図 5 — TLS クライアント認証（mTLS）ハンドシェイク

クライアントクライアント証明書あり
サーバクライアント証明書を要求
① ClientHello
② ServerHello + Certificate + ServerKeyExchange
+ CertificateRequest（クライアント証明書を要求！）
+ ServerHelloDone
③ Certificate（クライアント証明書送信）
+ ClientKeyExchange
+ CertificateVerify（クライアント秘密鍵による署名）
クライアント証明書を検証
（信頼チェーン・有効期限・失効・署名）
→ クライアントの身元確認完了
④ ChangeCipherSpec + Finished（暗号化）
⑤ ChangeCipherSpec + Finished（暗号化）
双方向認証完了 — クライアント・サーバ相互に本人確認済みで暗号化通信開始
!
CertificateRequest：通常の TLS にはない、サーバがクライアントに証明書提出を要求するメッセージです。受信側クライアントは証明書を持っていなければ接続できません。
!
CertificateVerify：クライアントが「このハンドシェイク全体の内容を自分の秘密鍵で署名した」メッセージです。サーバはクライアント証明書の公開鍵でこれを検証し、本人確認を完了します。
用途
企業 VPN 接続（クライアント証明書で端末認証）、API ゲートウェイ間のサービス間認証（mTLS）、電子申告・電子入札システム、クライアント証明書配布によるゼロトラストアクセス制御。

TLS に対する主な脅威と攻撃手法

SSL/TLS の歴史は脆弱性の発見と対応の繰り返しです。試験では攻撃名・原理・対策をセットで覚えることが重要です。

POODLE（2014）

SSL 3.0 の CBC モードパディング脆弱性。256 リクエストで 1 バイトを復号。攻撃者がダウングレードを強制（POODLE ATTACK）。

対策：SSL 3.0 の完全無効化（TLS_FALLBACK_SCSV / TLS 1.3 でダウングレード防止）

Heartbleed（2014）

OpenSSL の Heartbeat 拡張実装バグ。境界チェック不備でサーバメモリから秘密鍵・パスワードを 64KB ずつ窃取可能。

対策：OpenSSL 1.0.1g 以降へ更新・証明書再生成・秘密鍵入替

CRIME（2012）

TLS 圧縮機能の悪用。圧縮後のサイズ変化から Cookie や認証トークンを推測するサイドチャネル攻撃。

対策：TLS 圧縮の無効化（TLS 1.3 では廃止済み）

ダウングレード攻撃

中間者が ClientHello を改ざんし、古い TLS バージョンや脆弱な暗号スイートへの使用を強制する。BEAST・POODLE でも使われた手法。

対策：TLS_FALLBACK_SCSV 拡張・最低バージョン制限（TLS 1.2 以上）

中間者攻撃（MITM）

偽 CA が発行した証明書や PIN バイパスにより通信を傍受・改ざん。SSL インスペクション機能の悪用も含む。

対策：証明書の厳格な検証・HSTS preload・公開鍵ピンニング（HPKP）・CT（Certificate Transparency）

SSL ストリッピング

HTTPS→HTTP へリダイレクトする通信を途中で書き換え、クライアントを平文 HTTP 通信に留まらせる攻撃（Moxie Marlinspike, 2009年）。

対策：HSTS（HTTP Strict Transport Security）+ preload リスト登録

過去問スタイル 練習問題

情報処理安全確保支援士試験の出題傾向に沿った練習問題です。選択肢をクリックすると正誤と解説が表示されます。

Q1TLS 1.3 での主な改善点として、最も適切なものはどれか。
正解：ウ
TLS 1.3 はRSA鍵交換・静的DH を廃止し、ECDHE/DHEのみとすることで Perfect Forward Secrecy を必須化しました。また往復数は「2-RTT → 1-RTT」の短縮です（ア は「4往復→2往復」と書いているため誤りです）。ChangeCipherSpec は TLS 1.3 で廃止されました（エは誤り）。
Q2SNI（Server Name Indication）拡張の説明として、最も適切なものはどれか。
正解：ウ
SNI は ClientHello 内でアクセス先ホスト名を送信する拡張で、1 つの IP アドレスで複数ドメインをホスト（バーチャルホスティング）可能にします。ア は key_share 拡張、イ は OCSP Stapling、エ は ALPN 拡張の説明です。
Q3TLS の通信においてサーバ証明書の有効性確認として行われる処理の組み合わせとして、最も適切なものはどれか。
正解：イ
証明書検証は①信頼チェーン、②署名検証、③有効期限、④失効確認（OCSP/CRL）、⑤ドメイン名一致（SAN/CN）、⑥Key Usage の 6 ステップで構成されます。1 ステップのみでは不十分です。
Q4Perfect Forward Secrecy（PFS）を実現する仕組みとして、最も適切なものはどれか。
正解：エ
PFS の核心は「一時鍵（Ephemeral Key）」の使用です。ECDHE によりセッションごとに異なる鍵ペアを生成して使用後破棄することで、将来サーバの長期秘密鍵が漏洩しても、過去の通信は復号できません。
Q5SSL ストリッピング攻撃への対策として最も有効なものはどれか。
正解：ウ
SSL ストリッピングは HTTPS を HTTP に書き換えてクライアントを平文通信に誘導する攻撃です。HSTS（HTTP Strict Transport Security）を設定すれば、ブラウザは「このサイトへは必ず HTTPS でアクセス」を学習し、HTTP へのダウングレードを拒否します。preload リストに登録すれば初回アクセス前から有効です。
Q6TLS クライアント認証（mTLS）の特徴として最も適切なものはどれか。
正解：ウ
TLS クライアント認証では、サーバが CertificateRequest を送信してクライアントの証明書を要求し、クライアントは自分の X.509 証明書と CertificateVerify（自分の秘密鍵による署名）を送信します。サーバがこれを検証することで、クライアントの本人確認（相互認証）が完了します。

重要用語まとめ

試験頻出キーワード

TLS / SSLTransport Layer Security / Secure Sockets Layer。TCP 上でアプリデータを暗号化するプロトコル。現行は TLS 1.2 / 1.3 のみ有効。
ハンドシェイクTLS 接続確立時の暗号スイート合意・証明書交換・鍵交換のプロセス。TLS 1.2 は 2-RTT、TLS 1.3 は 1-RTT。
暗号スイート鍵交換・認証・暗号化・ハッシュの組み合わせ文字列。例：TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
ECDHEElliptic Curve Diffie-Hellman Ephemeral。楕円曲線上の一時 DH 鍵交換。PFS を実現。TLS 1.3 では必須。
PFS (Perfect Forward Secrecy)サーバ秘密鍵の漏洩が過去の通信を復号できない性質。一時鍵（ECDHE/DHE）の使用と使用後破棄で実現。
AEADAuthenticated Encryption with Associated Data。暗号化と完全性認証を同時実行。AES-GCM, ChaCha20-Poly1305。TLS 1.3 必須。
X.509 証明書公開鍵証明書の標準フォーマット。Subject, Issuer, SAN, 有効期限, 公開鍵, CA署名を含む。
信頼チェーンエンドエンティティ証明書 → 中間 CA → ルート CA へと辿る検証経路。ルートCA をブラウザの信頼ストアに含む必要。
OCSPOnline Certificate Status Protocol。証明書の失効状態をリアルタイムで確認するプロトコル。
OCSP Staplingサーバが事前に OCSP レスポンスを取得し、TLS ハンドシェイクに添付する。クライアントの問い合わせ不要。
常時SSL / HTTPS化Web サイト全体を HTTPS 化すること。部分 SSL 化の問題を解消。
HSTSHTTP Strict Transport Security。ブラウザに「このサイトは常に HTTPS でアクセスせよ」と指示するヘッダ。SSL ストリッピング対策。
SNIServer Name Indication。ClientHello でホスト名を送信する拡張。1 IP で複数 HTTPS ドメインを運用可能。
ALPNApplication-Layer Protocol Negotiation。使用するアプリプロトコル（HTTP/2 等）を TLS ハンドシェイク内でネゴシエーション。
0-RTT (Early Data)TLS 1.3 の PSK 再接続機能。初回メッセージをハンドシェイクと同時送信。リプレイ攻撃リスクあり。
TLS レコードプロトコルTLS の最下層。Handshake / ChangeCipherSpec / Alert / Application Data の 4 サブプロトコルのデータを運搬・暗号化。
HTTP CONNECTプロキシに「このホスト:ポートへのトンネルを確立せよ」と要求する HTTP メソッド。HTTPS のプロキシ中継に使用。
mTLS / クライアント認証Mutual TLS。サーバ・クライアント双方が証明書で相互認証。CertificateRequest / CertificateVerify が追加される。
POODLESSL 3.0 の CBC パディング脆弱性を悪用した攻撃。対策：SSL 3.0 廃止、TLS_FALLBACK_SCSV。
HeartbleedOpenSSL Heartbeat 実装バグ。サーバメモリから秘密鍵等を窃取可能。対策：OpenSSL 更新・証明書再生成。
SSL ストリッピングHTTPS を HTTP に書き換えてダウングレードさせる中間者攻撃。対策：HSTS。

試験対策 7 つの鉄則

1. TLS 1.3 の核心は「RSA 鍵交換廃止 + PFS 必須 + 1-RTT + 証明書暗号化」
2. ハンドシェイクの 4 フェーズ：Hello → 認証 → 鍵交換 → 暗号化開始
3. 証明書検証は 6 ステップ：信頼チェーン・署名・有効期限・失効・ドメイン・KeyUsage
4. PFS は「一時鍵（ECDHE）を毎回生成・破棄」で実現
5. SNI = 1 IP 複数ドメイン / ALPN = HTTP/2 ネゴシエーション
6. HSTS = SSL ストリッピング対策 / 常時 SSL の仕上げ
7. 攻撃：POODLE=SSL 3.0, Heartbleed=実装バグ, CRIME=圧縮, BEAST=CBC
