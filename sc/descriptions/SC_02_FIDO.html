01

FIDOの全体像

FIDO（Fast IDentity Online）は、パスワードに依存しない強力な認証標準を策定する業界団体「FIDOアライアンス」が定めた規格群です。2012年設立で、Google・Microsoft・Apple・PayPalなどが参加しています。パスワードの根本的な問題（フィッシング・使い回し・漏洩）を、公開鍵暗号方式とデバイス内での本人確認で解決します。

FIDOアライアンス
2012年設立の業界標準化団体。Google・Microsoft・Apple 等が参加し、パスワード不要の認証規格を策定。
秘密鍵非送信
秘密鍵はデバイスのTEE/SE/TPM内に封印。ネットワーク越しに送信されることは絶対にない。
チャレンジ応答
毎回異なる乱数（チャレンジ）に署名して返送。傍受・再送によるリプレイ攻撃を構造的に無効化。
Origin紐付け
鍵ペアはドメイン（Origin）に紐付いて生成。偽サイトには対応する秘密鍵がなくフィッシング不成立。

認証器の3つのタイプ

FIDOで使われる認証器は大きく3種類に分類されます。用途・環境に応じて使い分けます。

Platform
スマートフォンやPCに内蔵された認証器。Face ID・Windows Hello・Touch ID など。
Roaming
USB/NFC/BLEで接続するセキュリティキー。YubiKey等が代表例。可搬性が特徴。
Hybrid
スマートフォンをBluetooth/QR経由でPCの認証器に。Passkeys連携で急速に普及。

FIDO2の構成：FIDO2は WebAuthn（W3Cが標準化したブラウザAPI仕様）と CTAP2（Client to Authenticator Protocol 2：ブラウザ↔認証器間の通信プロトコル）の2層で構成されます。

02

UAF・U2F・FIDO2 の比較

FIDOアライアンスは段階的にプロトコルを策定してきました。UAFとU2Fは2014年に同時策定された第一世代で、FIDO2はその両方を統合した現行世代です。

試験頻出：UAFは「パスワードレス（1要素で完結）」、U2Fは「パスワード＋第2要素（2FA）」と役割が明確に異なります。FIDO2はその両方を統合した最新版です。

プロトコル詳細

UAF
Universal Authentication Framework — 2014年

役割：パスワードを完全に排除。スマートフォンの生体認証（指紋・顔・虹彩）またはデバイスPINのみで認証を完結。

認証器：スマートフォン（生体センサー搭載）。TEE内で処理し、生体テンプレートも外に出ない。

U2F
Universal Second Factor — 2014年

役割：既存パスワードに強力な第2要素を追加。セキュリティキーをUSB接続、物理ボタン押下（User Presence）で認証。

認証器：セキュリティキー（USB / BLE / NFC）。ローミング型認証器の典型例。

FIDO2
WebAuthn + CTAP2 — 2018年〜 現行規格

役割：UAF・U2Fを統合した現行規格。W3C標準の WebAuthn API で全主要ブラウザで使用可能。

構成：WebAuthn（ブラウザAPI）＋ CTAP2（認証器通信プロトコル）の2層構造。

Passkeys
マルチデバイスFIDO認証情報 — 2022年〜

役割：FIDO2の発展形。秘密鍵を iCloud Keychain / Google Password Manager に同期し、複数デバイスで同一パスキーを使用可能に。

注意：クラウドバックアップによりセキュリティモデルが変化。クラウドアカウント侵害リスクを考慮する必要あり。

上記の3つを踏まえた上で、以下にFIDOの核心である公開鍵暗号の仕組みを整理します。デバイスがRP（Relying Party：サービス提供者）ごとに鍵ペアを生成し、秘密鍵はデバイス内のセキュアエリアに保管、公開鍵のみをサーバに登録します。

Fig. 02 — チャレンジ応答の全ステップ詳細
登録
デバイスがRPごとに秘密鍵・公開鍵ペアを新規生成。秘密鍵はTEE/SE等のセキュアエリアに格納。公開鍵とCredential IDをサーバに登録します。
認証
サーバが毎回異なるチャレンジ（乱数）を発行。デバイスが秘密鍵でチャレンジに署名して返送。サーバは登録済み公開鍵で署名を検証します。
核心
秘密鍵は一切ネットワークを流れません。サーバには公開鍵しか存在しないため、サーバが侵害されても認証情報は漏洩しません。

Origin紐付けによるフィッシング耐性

FIDO鍵ペアは登録時のドメイン（Origin）に紐付いて生成されます。偽サイトでは対応する秘密鍵が存在しないため、署名処理そのものが成立しません。

FIDO2の登録（Registration）は初回のみ実施するフローです。ユーザーはデバイス上で生体認証やPINを実施し、生成された公開鍵をRPサーバに登録します。

シーケンス図 1 — FIDO2 Registration

③
RPサーバが challenge（乱数）・rpId・userId・pubKeyCredParams（対応アルゴリズムリスト）をブラウザへ返します。
⑤⑥
認証器がユーザーに生体認証またはPINの入力を要求。これを User Verification（UV） と呼びます。
⑦
認証器内部で鍵ペアを生成。秘密鍵はTEE/SEに格納し、公開鍵・Credential ID・Attestation（認証器の正当性証明）をブラウザへ返します。
!
Attestationとは：認証器が正規デバイスであることをメーカー証明書で証明する情報。RPサーバは証明書チェーンを検証して認証器の信頼性を確認します。
05

FIDO2 認証シーケンス

登録後の認証（Authentication）フローです。サーバが発行したチャレンジを秘密鍵で署名して返送し、サーバが公開鍵で検証します。signCount（署名カウンター）により認証器クローンやリプレイ攻撃も検知します。

シーケンス図 2 — FIDO2 Authentication

③
RPサーバが毎回新しいチャレンジを生成。allowCredentials に登録済み Credential ID リストが含まれ、対応する認証器のみが応答できます。
⑦
認証器内部で秘密鍵によりチャレンジに署名し、signCountをインクリメントして返します。
⑨
RPサーバは ①公開鍵で署名検証 ②signCount が保存値より大きいかの2点を検証。逆転していれば認証器クローンまたはリプレイ攻撃として拒否します。

核心ポイント

FIDO2認証の本質は「秘密鍵を送らずに、秘密鍵を持っていることを証明する」点にあります。毎回異なるチャレンジを使うことでリプレイ攻撃を無効化し、Origin紐付けでフィッシングを構造的に排除します。

06

UAF シーケンス（パスワードレス）

UAF（Universal Authentication Framework）はパスワードを完全に排除するプロトコルです。スマートフォンの生体認証が主要な認証手段となり、その結果を公開鍵署名でサーバに証明します。

シーケンス図 3 — UAF 登録・認証フロー

③④
UAFはパスワードなしに生体認証のみでユーザー確認を行います。指紋・顔・虹彩など、デバイスのセキュアエリアで照合が完結します。
⑪
認証時、署名された {signature, KeyID} を受け取ったサーバは、登録時に保存した公開鍵で署名を検証します。パスワードは一切使用・送信されません。
07

U2F シーケンス（第2要素認証）

U2F（Universal Second Factor）は既存のパスワード認証に強力な第2要素を追加するプロトコルです。セキュリティキー（YubiKey等）をUSBやNFCで接続し、物理ボタンを押すだけで認証を完了します。

シーケンス図 4 — U2F 第2要素認証

④⑤
U2F固有の確認として User Presence（UP）があります。ユーザーが物理ボタンを押したことで「意図的な操作」を証明し、マルウェアによる自動的な悪用を防ぎます。
⑦
RPサーバは ①署名検証 ②counter が保存値より大きいかの2点を確認します。counterが逆転していれば認証器クローンの可能性として認証を拒否します。
!
UAFとの違い：U2Fでは第1要素のパスワード認証は引き続き必要です。セキュリティキーはあくまで第2要素の強化です。

③ 主要対策のビジュアル解説

Origin 紐付け
登録時のドメインに鍵ペアを厳密バインド。偽サイト（evil.example）からのチャレンジでは、対応する秘密鍵が認証器内に存在せず、署名プロセスが物理的に走らない。
ワンタイム・チャレンジ
サーバが毎リクエストで異なる乱数を発行。傍受した署名値を翌回再送しても別チャレンジには対応せず、検証失敗。リプレイ攻撃を構造的に封じる。
秘密鍵のデバイス封印
秘密鍵は TEE / Secure Enclave / TPM 内でのみ生成・使用され、ネットワークにもOSにも露出しない。サーバが侵害されても漏れるのは公開鍵のみ。
生体認証 / PIN（UV）
デバイスを盗まれても、指紋・顔・PINが最後の防壁。生体テンプレートはTEE内で処理され外部に出ない。紛失時はCredentialをサーバ側で失効できる。
signCount（オドメーター）
認証のたび値が単調増加。クローン器が古い値で認証すると逆転を検知してサーバが拒否。走行距離計を改竄しない限り複製を暴ける。
Attestation 検証
登録時、認証器メーカー発行の証明書で正規デバイスであることを検証。MDS（Metadata Service）と照合し、既知の脆弱デバイスを排除できる。
認証器の紛失・盗難

スマートフォンやセキュリティキーが盗まれた場合、生体認証やPINが第2の防壁となる。ただし強制解除の可能性もゼロではない。

対策：生体認証の必須化・Credential IDのサーバ側無効化・紛失時の即時失効手順

認証器クローン

TEE/SEからの秘密鍵抽出による認証器の複製。物理的攻撃が必要で非常に困難だが、理論上はゼロではない。

対策：signCountの監視（逆転で検知）・FIDO認定デバイスの使用

マルウェアによる認証乗っ取り

ユーザーのデバイスにマルウェアが感染し、FIDOの認証セッション確立後にブラウザ操作を乗っ取る（Session Hijacking）。

対策：エンドポイントセキュリティ強化・セッション管理の堅牢化・異常ログイン検知

ソーシャルエンジニアリング

ユーザーを騙して意図しない認証器登録・認証を実行させる。例えばサポートを装い不正な登録操作を誘導する。

対策：登録・認証操作の明示的な意思確認UI・セキュリティ教育・不審登録の通知

RPサーバの侵害

サーバに保存されているのは公開鍵のみであるため、サーバが侵害されてもパスワードのような認証情報は流出しない。

対策：公開鍵DBのアクセス制御・HSMによるサーバ秘密鍵管理・ログ監査

フォールバック認証の脆弱性

認証器紛失時のアカウント回復フロー（メール・電話番号等）が攻撃の標的になる。

対策：回復コードの安全な管理・フォールバック強化・SIMスワップ対策

類似技術との比較 — 混同しやすいポイントの整理

試験では「FIDO と TOTP の違い」「UAF と U2F の違い」「Passkeys とは何か」が頻出です。下のたとえ話と比較表で各技術の位置づけを確実に整理してください。

たとえ話：認証技術を「合言葉と証明書」で理解する

認証方式ごとのたとえ — 郵便局で「本人確認」するシーン
パスワード

「山田です」と名乗るだけで本人確認完了。なりすましが容易で、毎回同じ合言葉を使い回す。フィッシングサイトで合言葉を伝えると即漏洩。

TOTP（ワンタイムパスワード）

「今この瞬間だけ有効な暗証番号」を毎回変えて伝える。30秒で失効するので使い回しには強いが、偽の窓口に教えてしまえばリアルタイムで悪用される（フィッシングに弱い）。

FIDO（公開鍵署名）

印鑑（秘密鍵）を窓口に渡さず自分で書類に押印して渡す。偽の窓口に行っても「bank.co.jp の印鑑ではないので署名できない」と認証器が拒否。構造的にフィッシング不成立。

FIDO vs TOTP / HOTP — 試験最頻出の比較

比較項目TOTP（RFC 6238）HOTP（RFC 4226）FIDO2 / UAF
認証の仕組み時刻＋共有秘密鍵でOTPを生成カウンタ＋共有秘密鍵でOTPを生成チャレンジに秘密鍵で署名
サーバに何を保存共有秘密鍵（Seed）共有秘密鍵（Seed）公開鍵のみ（秘密鍵はデバイス内）
フィッシング耐性低（リアルタイム転送で悪用可）低（転送して悪用可）高（Origin紐付けで構造的に防止）
リプレイ攻撃耐性有効期間内は危険（30秒）カウンタ同期ずれで危険チャレンジ使い捨てで完全防止
サーバ漏洩時の影響Seed漏洩→全OTP再現可能Seed漏洩→全OTP再現可能公開鍵のみ→秘密鍵は再現不可
追加ハードウェア認証アプリのみハードウェアトークン等認証器（スマホ/セキュリティキー）

混同注意：TOTP はフィッシングを「防がない」
TOTPは「リプレイ攻撃」には強いですが、攻撃者がリアルタイムで偽サイトを中継（AiTM：Adversary-in-The-Middle）すればOTPを横取りできます。FIDOのフィッシング耐性は「そもそも偽サイトでは署名が生成されない」という構造的なものです。

UAF / U2F / FIDO2 / Passkeys の位置づけ

規格策定時期主な用途パスワードレス第2要素クロスデバイス
UAF2014年モバイルアプリのパスワードレス認証可主目的ではないデバイス固定
U2F2014年Webのセキュリティキーによる2FA不可主目的キー持ち歩き
FIDO22019年WebAuthn対応のWeb認証（UAF+U2F統合）可可クロスデバイス対応
Passkeys2022年〜FIDO2鍵をクラウド同期で複数デバイス利用可可iCloud/Google同期

WebAuthn と FIDO2 の関係

FIDO2
FIDO2 = FIDO Alliance の規格セット全体。WebAuthn（W3C規格）と CTAP（Client-to-Authenticator Protocol）の2つで構成されます。
WebAuthn
WebAuthn = ブラウザとRPサーバ間のAPIおよびプロトコル。W3Cが標準化。navigator.credentials.create()/get()がWebAuthn APIです。FIDO2の「上位レイヤー」です。
CTAP
CTAP（CTAP1/CTAP2） = ブラウザと認証器（スマホ・セキュリティキー）間のプロトコル。USB/NFC/BLE経由で通信します。CTAP1は旧U2Fとの互換、CTAP2はFIDO2新規機能です。

試験対策まとめ

FIDO vs TOTP：TOTPは共有秘密鍵をサーバが持つ→漏洩リスク。FIDOは公開鍵のみ→漏洩しても偽造不可。
フィッシング耐性：TOTPはAiTMで突破される。FIDOはOrigin紐付けで構造的に突破不可。
FIDO2 = WebAuthn + CTAP。 Passkeys = FIDO2鍵のクラウド同期による利便性向上版。
UAF = パスワードレス専用、U2F = 第2要素専用、FIDO2 = 両対応。

過去問スタイル 練習問題

情報処理安全確保支援士試験の出題傾向に沿った練習問題です。選択肢をクリックすると正誤と解説が表示されます。

Q1FIDO UAFに関する説明として、最も適切なものはどれか。
正解：ウ
UAF（Universal Authentication Framework）はパスワードを完全に排除したパスワードレス認証規格です。生体認証やPINはデバイス内のTEE/SEで照合され、サーバには一切送信されません。アはU2Fの説明、イは誤り（生体情報はデバイス外に出ない）、エはFIDOの仕組みとは異なります。
Q2FIDO2認証においてリプレイ攻撃を防止する主な仕組みとして、最も適切なものはどれか。
正解：イ
リプレイ攻撃とは「正規の署名をコピーして再送信する攻撃」です。FIDOでは毎回新規のチャレンジに対して署名するため、過去の署名を再送しても「このチャレンジへの署名ではない」として拒否されます。ウは秘密鍵の保護（盗難防止）、エはクローン検知の仕組みです。
Q3FIDO2がフィッシング攻撃に対して高い耐性を持つ根本的な理由として、最も適切なものはどれか。
正解：イ
FIDOの鍵ペアは登録時の正規サイトのOrigin（https://bank.co.jp 等）に紐付けられます。偽サイト（https://bank.evil.com 等）でログインを試みても、認証器は「対応する秘密鍵が存在しない」として署名を拒否します。ユーザが偽サイトにアクセスしても認証が物理的に成立しない点がTOTPと本質的に異なります。
Q4FIDO2の構成要素に関する記述のうち、誤っているものはどれか。
正解：ウ（誤りはウ）
FIDO2では秘密鍵はデバイスのTEE/SE内にのみ保管され、RPサーバには一切送信・保管されません。RPサーバが保管するのは公開鍵です。これがFIDOのセキュリティの核心であり、サーバが侵害されても秘密鍵は漏洩しません。
Q5FIDO2認証において、受信した signCount の値がRPサーバ保存値以下であった場合、RPサーバが取るべき対応として最も適切なものはどれか。
正解：エ
signCountは認証のたびに単調増加します。受信値がサーバ保存値以下であることは「同じ認証器が2回使われた」（クローン）または「過去の署名が再送された」（リプレイ）を示します。WebAuthn仕様ではこの場合の認証拒否を推奨しています。
Q6FIDO2認証とTOTPの違いについて、最も適切な説明はどれか。
正解：イ
TOTPはサーバとクライアントが同一の共有秘密鍵（Seed）を持ちます。サーバが侵害されるとSeedが漏洩し、攻撃者が任意のOTPを生成できます。FIDOではサーバに公開鍵のみ保管し、秘密鍵はデバイス内に閉じているため漏洩しても偽造不可です。
Q7U2F認証でセキュリティキーの物理ボタン押下を必須とする主な目的として、最も適切なものはどれか。
正解：ウ
U2FのUser Presence確認は「物理的にキーが手元にある人間が操作した」という事実を保証します。マルウェアがPCを乗っ取っても、物理ボタンを押す操作はリモートでは実行できません。これにより「PCが感染していても認証器を物理的に持っていなければ認証不可」という防御層が加わります。
Q8Passkeys（パスキー）の説明として最も適切なものはどれか。
正解：ウ
PasskeysはFIDO2の鍵ペアをiCloud Keychain・Google Password Manager・Windows Hello等でデバイス間同期するエコシステムです。技術的にはFIDO2/WebAuthnと完全互換です。従来のFIDO2はデバイスに鍵を閉じ込めたため「デバイス紛失＝ロックアウト」でしたが、Passkeysはクラウド同期で利便性と可用性を向上させます。
Q9TEE（Trusted Execution Environment）のFIDO認証における役割として、最も適切なものはどれか。
正解：イ
TEE（Trusted Execution Environment）はメインOSから完全に分離された安全な実行環境です。FIDO認証では秘密鍵の生成・保管・署名処理がすべてTEE内で完結します。メインOS上のマルウェアやroot権限を持った攻撃者でも、TEE内の秘密鍵を読み出すことはできません。SE（Secure Element）はさらに物理的に分離されたハードウェアチップです。
Q10FIDO2のAttestation（アテステーション）の目的として、最も適切なものはどれか。
正解：イ
Attestationは「この公開鍵はFIDO認定の正規認証器で生成された」ことを証明する仕組みです。認証器メーカーが発行したAttestation証明書チェーンをRPサーバが検証することで、ソフトウェアで偽装した仮想認証器や非認定デバイスを排除できます。企業のセキュリティポリシーとして「特定メーカーの認定デバイスのみ登録可」といった制御が可能になります。

重要用語まとめ

試験頻出キーワード

FIDO AllianceFast IDentity Online Alliance。FIDOの標準化団体。Google・Apple・Microsoft・主要銀行等が参加。
FIDO UAFUniversal Authentication Framework。パスワードレス認証規格（2014年）。生体認証・PINのみでログイン。
FIDO U2FUniversal 2nd Factor。セキュリティキーによる第2要素認証規格（2014年）。パスワード＋キーの2要素。
FIDO2WebAuthn（W3C）＋CTAP（FIDO Alliance）で構成されるWeb認証規格（2019年）。UAF・U2Fを統合し両対応。
WebAuthnWeb Authentication API。W3C標準。ブラウザ〜RPサーバ間のFIDO2プロトコル。navigator.credentials.create/get()が主要API。
CTAPClient-to-Authenticator Protocol。ブラウザ〜認証器間のプロトコル。CTAP1（旧U2F互換）とCTAP2（FIDO2）がある。
Relying Party（RP）FIDOを利用するWebサービス・アプリ。登録時に公開鍵を保管し、認証時に署名検証を行う。
rpIdRelying Party ID。ドメイン名（例：bank.co.jp）。鍵ペアはこのrpIdに紐付けられ、フィッシング耐性の根拠となる。
Originスキーム＋ホスト＋ポートの組合せ（例：https://bank.co.jp）。WebAuthnはOriginを自動で検証する。
Authenticator（認証器）FIDO鍵ペアを生成・保管・署名する装置。スマートフォン（TEE/SE使用）やハードウェアセキュリティキーが該当。
TEETrusted Execution Environment。メインOSから隔離された安全な実行環境。ARM TrustZone等。秘密鍵の保管・署名処理を担う。
SESecure Element。物理的に分離されたセキュアなICチップ。TEEより強固。一部のスマホやセキュリティキーに内蔵。
credentialId認証器が生成する鍵ペアの識別子。RPサーバに登録され、認証時にどの鍵ペアを使うかを指定するために使用する。
challenge（チャレンジ）RPサーバが認証のたびに生成する使い捨て乱数（32バイト）。同じ値は2度使われないため、リプレイ攻撃を防止する。
signCount認証器が署名のたびに+1するカウンタ。RPサーバが受信値と保存値を比較し、逆転があればクローン検知・リプレイ拒否に利用する。
Attestation認証器が正規のFIDO認定デバイスであることをメーカー証明書チェーンで証明する仕組み。登録時にRPサーバが検証する。
User Verification（UV）デバイス上での本人確認（生体認証・PIN）。UVは認証器内でのみ実施され、結果のみがRPに通知される。
User Presence（UP）ユーザが物理的にデバイスに触れていること（U2Fの物理ボタン押下等）。リモート攻撃を防ぐ。UVより低い保証レベル。
keyHandle / credentialIdU2F用語ではkeyHandle、WebAuthn用語ではcredentialId。特定の鍵ペアを識別するバイト列。
PasskeysFIDO2の鍵ペアをOSベンダーのクラウドで同期する仕組み。Apple iCloud/Google Password Manager/Windows Hello等で実現。
AiTM攻撃Adversary-in-The-Middle。攻撃者が正規サイトとユーザの間でリアルタイム中継する攻撃。TOTPを突破できるがFIDOは構造的に無効化する。
TOTPTime-based One-Time Password（RFC 6238）。時刻＋共有秘密鍵でOTPを生成。有効期間30秒。サーバに共有秘密鍵を保管するため漏洩リスクあり。
HOTPHMAC-based One-Time Password（RFC 4226）。カウンタ＋共有秘密鍵でOTPを生成。ハードウェアトークン等で使用。
authData認証器情報。rpIdHash・フラグ（UV/UP等）・signCount・AAGUIDを含むバイト列。署名対象に含まれ改ざん検知に使われる。
clientDataJSONブラウザが生成する認証リクエスト情報（type・challenge・origin等）。署名対象に含まれOriginの検証に使われる。
AAGUIDAuthenticator Attestation GUID。認証器の機種・モデルを識別するID。企業がデバイスポリシーを適用する際に使用する。
公開鍵ペア（登録時）FIDO登録時にrpIdごとに新規生成される秘密鍵・公開鍵ペア。秘密鍵はTEE/SE内に保管、公開鍵のみRPに送信・登録される。
署名検証（認証時）RPサーバが登録済み公開鍵を使い、認証器の署名値を検証する処理。Verify(sig, pubKey, clientDataHash + authData)。

試験対策 7つの鉄則

1. 秘密鍵はデバイスのTEE/SE外に出ない — サーバ・ネットワークに一切送信されない
2. チャレンジは毎回新規の使い捨て乱数 — リプレイ攻撃を無効化する核心
3. Origin紐付け = フィッシング耐性の根拠 — 偽サイトでは対応する秘密鍵がなく署名不成立
4. signCount逆転 → クローン/リプレイとして拒否 — 単調増加の保証
5. TOTP vs FIDO：共有秘密鍵か公開鍵か — サーバ漏洩時のリスクが本質的に異なる
6. UAF=パスワードレス / U2F=第2要素 / FIDO2=両対応
7. Passkeys = FIDO2鍵のクラウド同期 — 技術的にFIDO2/WebAuthnと完全互換
