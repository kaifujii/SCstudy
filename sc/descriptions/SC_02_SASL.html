01

SASLの立ち位置

SASL（Simple Authentication and Security Layer）は、アプリケーションプロトコルと認証メカニズムを分離するためのフレームワーク仕様（RFC 4422）です。SASL自身は認証ロジックを持たず、どのメカニズムを使うかを決めるネゴシエーション層として機能します。

たとえ話で理解する SASL
たとえ話：コンセント規格
コンセントの口（規格）
プラグ（家電ごとに形は違う）
電力（流れる電気自体）
家電（ドライヤー、炊飯器など）
⇄
実際の技術対応
SASL（統一の「認証接続口」）
各メカニズム（SCRAM、PLAIN…）
認証の成否（接続可否の判断）
SMTP/IMAP/LDAP（使う機器）

核心：SASLは「認証しない」。SASLはどのメカニズムで認証するかを取り決めるだけです。「SASLで認証した」という表現は技術的に誤りで、「SASL上のSCRAM-SHA-256で認証した」が正確です。

02

同じ「認証フレームワーク」レイヤーとの比較

SASLと同じ「認証統合レイヤー」に位置する方式・プロトコルを比較します。役割の違いが試験のポイントです。

アクセス権限を委譲		 Web API・クラウドサービス OAUTHBEARERとしてSASLに採用

核心ポイント

OAuth 2.0は本来「認可（誰に何を許可するか）」の仕組みであり、認証ではありません。OAUTHBEARERはOAuth 2.0のトークンをSASLのメカニズムとして使うための仕様です。「OAuth 2.0 ＝ 認証方式」と書かれた選択肢は誤りです。

CRAM-MD5
非推奨 — 移行推奨
MD5（脆弱） 相互認証なし 辞書攻撃に脆弱 1ラウンドのみ
HMAC-MD5を使ったチャレンジ応答方式。パスワードを直接送らない点はSCRAMと同様ですが、MD5の衝突脆弱性・相互認証なし・辞書攻撃への脆弱性から非推奨です。現在はSCRAM-SHA-256への移行が推奨されています。
たとえ話：「合言葉を決めて確認する」という仕組みは正しいが、使っている暗号が古い（MD5）。そして店員（サーバー）は身分証を見せないため、偽の店舗かどうか確認できない。仕組みは良くても素材が古すぎる。
問題点の整理
CRAM-MD5の弱点
MD5の衝突耐性が低く偽造の余地あり
サーバーがクライアントを証明しない（相互認証なし）
オフライン辞書攻撃が有効
SCRAM-SHA-256への移行ポイント
SHA-256 + Salt + 相互認証 の3点強化。設定変更のみで移行可能なサーバー実装が多い。

05

脅威と攻撃手法

SASL認証に対する攻撃を4つのカテゴリに分類します。カテゴリボタンで絞り込めます。

盗聴（スニッフィング）

盗聴・傍受
たとえ：封筒なしのはがきで秘密を送るようなもの。通信路が見えていれば内容が丸見え。

PLAINやLOGINをTLSなしで使うと、ネットワーク上のBase64文字列をデコードするだけでパスワードを取得できます。Wiresharkなど一般的なツールで誰でも傍受可能です。

対策：PLAIN使用時は必ずSTARTTLSまたはTLS接続（SMTPS等）上で使用する
✎

ダウングレード攻撃

改ざん・操作
たとえ：「本日の特別メニューはコースのみ」と書いた看板を「アラカルト可」に書き換えて、客に安いメニューを選ばせる偽の店員。

中間者がSASLネゴシエーション時のメカニズム一覧を改ざんし、クライアントに意図的に弱いメカニズム（PLAINなど）を選択させます。

対策：STARTTLS完了後にAUTHを実行。ネゴシエーション自体をTLSで保護する

リプレイ攻撃

盗聴・傍受
たとえ：録音した合言葉を再生して入場しようとする。nonce（毎回変わる合言葉）があればこれを防げる。

過去の認証トランザクションを傍受し、そのまま再送して正規ユーザーとして認証させます。nonceがない方式では有効な攻撃になります。

対策：チャレンジ応答のnonce（毎回異なる乱数）を使用する方式（SCRAM等）を採用する

辞書攻撃 / 総当たり

総当たり・解析
たとえ：暗証番号が4桁だとわかっていれば0000〜9999を試すだけ。Saltと反復ハッシュで「試す時間」を増やして現実的でなくする。

CRAM-MD5など旧来の方式では、傍受したチャレンジ・レスポンスのペアからオフラインで辞書攻撃が有効です。MD5の速さが仇となります。

対策：SCRAM-SHA-256のSalt+PBKDF2でオフライン攻撃コストを大幅に増加させる

MD5衝突悪用

総当たり・解析
たとえ：同じ外見（ハッシュ値）を持つ偽物を作れる技術。「見た目が同じ」なら本物として通過できてしまう。

CRAM-MD5・DIGEST-MD5はMD5の衝突脆弱性（異なる入力が同一ハッシュになる）を利用した偽造が理論上成立します。実用攻撃への道は広がっています。

対策：MD5系メカニズムを廃止しSCRAM-SHA-256に完全移行する

フィッシング（偽サーバー）

なりすまし
たとえ：本物そっくりの偽店舗を作って客の個人情報を盗む。相互認証は「店が本物の営業許可証を持っているか確認する」行為。

偽のSMTPサーバーを立てて正規のSASL認証を行わせ、認証情報を詐取します。CRAM-MD5は相互認証がないためクライアントから偽サーバーを検知できません。

対策：SCRAM-SHA-256の相互認証を使用し、クライアントがサーバーの正当性を検証する

中間者攻撃（MITM）

改ざん・操作
たとえ：郵便局員になりすまして手紙を横取りし、内容を読み・書き換えてから届ける。TLSは封蝋と封筒で「開封されていないか」確認できる仕組み。

攻撃者がクライアントとサーバーの間に入り、通信の傍受・改ざん・セッション乗っ取りを行います。TLSなしのSASLは完全にこの攻撃に無防備です。

対策：TLSで通信路を保護し、証明書検証を必須とする。HSTS等を組み合わせる
06

試験で問われやすいポイント・間違いやすいポイント

間違いやすいポイント

誤
「SASLで認証した」は誤り。SASLはフレームワークであり認証ロジックを持たない。正確には「SASL上のSCRAM-SHA-256で認証した」。
誤
「PLAINはパスワードを暗号化している」は誤り。Base64はエンコード（可逆変換）であり暗号化ではない。base64_decode()で即座に元に戻せる。
誤
「OAuth 2.0はSASLの認証方式」は誤り。OAuth 2.0は認可フレームワーク。SASLで使われるのはOAUTHBEARERメカニズム（OAuth 2.0のトークンを使う）。
誤
「SCRAM-SHA-256ならTLS不要」は誤り。SCRAMはパスワード平文を送らないが、通信路の暗号化はTLSの別の仕事。中間者攻撃には無防備。
!
CRAM-MD5とDIGEST-MD5の違い：CRAM-MD5は相互認証なし（一方向のみ）。DIGEST-MD5は相互認証に部分対応。両者ともMD5の脆弱性により廃止勧告。混同しやすいので要注意。
!
GSSAPIとKerberosの関係：GSSAPIはSASLのメカニズム名。実体はKerberos V5。「GSSAPIで認証＝Kerberosチケットを使ってSSOを実現」と覚える。Active Directory環境での標準方式。

試験対策 5つの鉄則

1. SASLはフレームワーク — 認証はメカニズムが行う。「SASL自体が認証する」は誤り
2. Base64はエンコード、暗号化ではない — PLAIN使用時はTLS必須
3. リプレイ防止にはnonce（毎回異なる乱数） — チャレンジ応答の本質
4. 相互認証はSCRAMとGSSAPIのみ — PLAINやCRAM-MD5にはない
5. OAuth 2.0は認可、認証ではない — OAUTHBEARERはそのトークンをSASLで使う仕様

重要用語まとめ

SASLSimple Authentication and Security Layer。アプリ層に認証を追加するフレームワーク（RFC 4422）。認証処理はメカニズムが担う。
ネゴシエーションSASLの最初のフェーズ。サーバーが対応メカニズム一覧を通知し、クライアントが一つを選択する。
nonceNumber used once。毎回異なるランダム値。チャレンジ応答に使うことでリプレイ攻撃を防ぐ。
SCRAM-SHA-256Salted Challenge Response Authentication Mechanism。相互認証・平文不保存・SHA-256の3点を持つ現在の推奨方式（RFC 7677）。
GSSAPIKerberosなどをSASLから呼び出すためのメカニズム名。Active Directory環境のSSO認証で使われる。
OAUTHBEAREROAuth 2.0のBearerトークンをSASL認証に使用するメカニズム（RFC 7628）。クラウドメールで拡大中。
PLAINユーザー名+パスワードをBase64エンコードして送る方式。TLS必須。Base64は可逆変換のため単体では危険。
DIGEST-MD5MD5ハッシュを用いたチャレンジ応答方式。RFC 6331で廃止勧告。
CRAM-MD5HMAC-MD5を使った1ラウンドのチャレンジ応答。相互認証なし・辞書攻撃に脆弱。SCRAM系への移行を推奨。
相互認証クライアント↔サーバー双方向の認証。SCRAM・GSSAPIが対応。偽サーバー検知に有効。
ダウングレード攻撃ネゴシエーション段階でメカニズム一覧を改ざんし、クライアントに弱い方式を選ばせる中間者攻撃。
STARTTLS平文接続を途中でTLSに切り替えるコマンド。SASL AUTH の前に実行することでネゴシエーション自体を保護できる。

試験対策まとめ

1. SASLは認証しない — メカニズムを「選ぶ」だけのフレームワーク
2. Base64 ≠ 暗号化 — PLAINには必ずTLSが必要
3. リプレイ防止 ＝ nonce — チャレンジ応答の本質
4. GSSAPIの実体はKerberos — AD環境のSSOの仕組み
5. OAuth 2.0は認可 — OAUTHBEARERはそのトークンをSASLで使う仕様
