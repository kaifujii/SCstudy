01

SSL/TLSの位置づけ — 全体像の中での役割

SSL（Secure Sockets Layer）/ TLS（Transport Layer Security）は、インターネット通信を暗号化し、盗聴・改ざん・なりすましから守るプロトコルです。現在有効なバージョンは TLS 1.2 と TLS 1.3 のみです。

たとえ話：輸送船と護衛艦 本題との紐づけ ▶
HTTP（平文）
甲板に荷物を無防備に積んだ船
誰でも荷物をのぞき見できる（盗聴）
荷物をすり替えられる（改ざん）
偽の船に誘導される（なりすまし）
HTTPS（TLS暗号化）
施錠コンテナ＋護衛艦付きの船
暗号化で解読不能（機密性）
MAC/AEADで改ざん即検知（完全性）
証明書で本物確認（真正性）
たとえと本題の対応：「施錠コンテナ」＝AES暗号化、「護衛艦」＝TLSプロトコル本体、「荷物の封印シール」＝MAC/AEAD（改ざん検知）、「入港許可証」＝X.509サーバ証明書
機密性
暗号化で盗聴不可能に。AES-256やChaCha20でデータを変換。鍵なしでは解読不可能。サードパーティはランダムなビット列しか見えない。
完全性
1ビット改ざんでも検知。MACまたはAEADが送信データの指紋（ハッシュ）を計算・検証。不一致なら即接続切断。
真正性
相手が本物かを証明。X.509証明書でサーバのドメインと公開鍵を束ねてCAが署名。偽サイトへの誘導を防止。
否認防止
「送っていない」と言えない。デジタル署名（秘密鍵）で通信を紐づけ。法的証拠として事後否認を不可能にする。

# includeSubDomains: サブドメインにも適用
# preload : ブラウザのHSTSプリロードリストに登録申請

TLS 1.3 ハンドシェイク — 何が変わったか

TLS 1.3（RFC 8446, 2018年）は1-RTT（1往復）を実現し、PFSを強制します。

たとえ話：TLS 1.2 vs 1.3 — 入館手続きの違い
TLS 1.2 — 当日受付
1「来ましたよ。何語が使えますか？」→往路1
2「これで話しましょう。身分証です」←復路1
3「合言葉お渡しします」→往路2
4「確認できました。どうぞ」←復路2
計 2往復（2-RTT）遅い！
TLS 1.3 — 事前予約＋顔パス
1「来ました。これが暗号鍵（key_share）です」→往路1
2「鍵受け取り。身分証も暗号化してお渡し」←復路1
3（もうここから暗号化通信開始！）
計 1往復（1-RTT）高速！証明書も暗号化！
たとえと本題の対応：「鍵（key_share）を最初に渡す」＝ClientHelloにECDHE公開鍵を同梱、「身分証も暗号化」＝Certificate暗号化送信（TLS1.3新機能）

暗号スイートと鍵交換アルゴリズム

暗号スイート（Cipher Suite）は鍵交換・認証・暗号化・ハッシュの組み合わせを一括指定する文字列です。

暗号スイートの読み方

TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
ECDHE
鍵交換：Elliptic Curve DH Ephemeral — 楕円曲線DHの一時鍵。PFS対応。毎回異なる鍵ペアを生成して破棄。
RSA
認証：サーバ証明書の署名アルゴリズム。RSAかECDSAか。
AES_256_GCM
暗号化：AES 256bit, GCMモード（AEAD）。暗号化と完全性保護を同時実行。
SHA384
PRF/MACハッシュ：鍵導出・Finishedメッセージ検証に使用。
たとえ話：PFS（Perfect Forward Secrecy）— 使い捨て南京錠
RSA鍵交換（PFS無し）

マスターキー（サーバ秘密鍵）で共通の南京錠を開けて荷物を配達。マスターキーが盗まれると過去に記録した全通信も復号可能に。

マスターキー漏洩 → 過去の全通信が復号される
ECDHE（PFS有り）

配達のたびに使い捨ての南京錠を使う。使用後は鍵を破棄。マスターキーが盗まれても過去通信には影響なし。

使い捨て鍵を毎回破棄 → 過去通信は安全
対応：「マスターキー」＝サーバの長期秘密鍵、「使い捨て南京錠」＝ECDHEの一時鍵ペア、「破棄」＝メモリからの鍵消去。TLS 1.3ではECDHEが必須なので常にPFS。
07

Webブラウザによるサーバ証明書の検証

たとえ話：証明書検証 ＝ 免許証の確認手順

ブラウザが証明書を受け取ったとき、警備員が免許証を確認するのと同じ手順を踏みます：

① 発行元確認警察庁（ルートCA）が発行した機関（中間CA）が発行した証明書か？
② 偽造確認ホログラム（CA署名）が本物か？改ざんされていないか？
③ 有効期限免許証の有効期限内か？（notBefore〜notAfter）
④ 失効確認失効（返納済み）していないか？（OCSP/CRL）
⑤ 氏名確認免許証の氏名とアクセス先のドメイン名が一致するか？（SAN/CN）
⑥ 用途確認この証明書はTLSサーバ用か？（Key Usage: TLS Web Server Authentication）
対応：「警察庁」＝ルートCA、「発行機関」＝中間CA、「免許証本体」＝X.509証明書、「ホログラム」＝CAのデジタル署名、「氏名欄」＝Subject Alternative Name(SAN)

証明書検証の 6 ステップ（クリックで詳細展開）

①
信頼チェーン（Chain of Trust）検証 ▼

サーバ証明書の署名者（中間CA）→ 中間CAの署名者（ルートCA）と辿り、ブラウザのルートCA証明書ストアに到達するか確認。

たとえ：「この証明書を発行したのはGlobalSign。GlobalSignはブラウザが信頼するルートCAに連なる正規機関か？」という確認。信頼の連鎖が切れたら即エラー。
②
署名の検証 ▼

上位CAの公開鍵で証明書内のデジタル署名を復号し、証明書内容ハッシュと一致するか確認。改ざん検知。

③
有効期限の確認 ▼

証明書の notBefore（開始日時）と notAfter（終了日時）が現在時刻を含むか確認。有効期限切れは即エラー。

④
失効確認（OCSP / CRL） ▼

OCSP（リアルタイム照会）またはCRL（失効リスト参照）で証明書が失効していないか確認。秘密鍵漏洩後に失効させた証明書の不正使用を防ぐ。

OCSP Stapling：サーバが事前にOCSPレスポンスを取得し証明書と一緒に提示。クライアントの問い合わせ不要で高速。
⑤
ドメイン名の一致確認（SAN / CN） ▼

証明書の Subject Alternative Names（SAN）またはCNが、アクセス先URLのホスト名と一致するか確認。ワイルドカード（*.example.com）も照合。

⑥
鍵使用用途の確認（Key Usage） ▼

証明書の Key Usage / Extended Key Usage拡張に「TLS Web Server Authentication」が含まれるか確認。

08

TLS 拡張仕様 — SNI・ALPN と 0-RTT

たとえ話：SNI ＝ マンションの「何号室ですか？」

建物（IPアドレス）は一つでも、何号室（ドメイン）に用があるかを最初に言うことで、その部屋の住人（証明書）が出てきます。SNI以前は「建物に1枚の証明書」しか貼れませんでした。

対応：「建物（マンション）」＝IPアドレス、「号室」＝ドメイン名、「玄関での一言」＝ClientHelloのSNI拡張（平文送信）、「SNI → ECH」＝暗号化で号室も隠す次世代技術
拡張名用途ポイント
SNIServer Name Indication — ClientHelloでアクセス先ホスト名を通知1 IPで複数HTTPSドメイン運用可能。平文送信（ECHで暗号化予定）。
ALPNApplication-Layer Protocol Negotiation — HTTP/2等のネゴシエーションHTTP/2利用に必須。TLSハンドシェイク内で確定。
key_shareECDHE公開鍵をClientHelloに同梱TLS 1.3の1-RTTの核心。必須拡張。
0-RTT Early Data再接続時にハンドシェイクと同時にデータ送信リプレイ攻撃リスク。冪等なGETに限定推奨。
OCSP Staplingサーバが事前取得したOCSPレスポンスを添付クライアントの失効確認負荷を低減。
09

TLS トンネリング（HTTP CONNECT）

たとえ話：プロキシ ＝ 中身を開けない郵便局員

「XX宛の不透明な封筒を中継してほしい」（CONNECT）→ 郵便局員は封筒の中身（暗号化データ）を開けられないまま転送します。

対応：「郵便局員」＝プロキシサーバ、「不透明封筒」＝TLS暗号化パケット、「CONNECT」＝「XX宛のトンネルを開けてほしい」というHTTPメソッド

TLS クライアント認証（相互 TLS / mTLS）

たとえ話：通常TLS vs mTLS — 居酒屋 vs VIPルーム
通常TLS（一方向認証）

居酒屋の看板（サーバ証明書）を確認してから入店。お客（クライアント）は誰でも入れる。

看板確認 → 入店OK（顧客の身元不問）
mTLS（双方向認証）

入店時にお互いが社員証を見せ合う。認証済み会員のみ入室できるVIPルーム。

双方向で証明書確認 → 完全認証
対応：「VIPルーム」＝企業VPN/APIゲートウェイ、「社員証」＝クライアント証明書、「照合」＝CertificateVerifyメッセージ（クライアント秘密鍵署名）
追加
CertificateRequest：通常のTLSにはないメッセージ。サーバがクライアントに証明書提出を要求。受信クライアントは証明書がなければ接続不可。
追加
CertificateVerify：クライアントが「このハンドシェイク全体の内容を自分の秘密鍵で署名した」メッセージ。サーバがクライアント証明書の公開鍵で検証し本人確認完了。
用途
企業VPN（端末認証）、APIゲートウェイのサービス間認証、電子申告・電子入札、ゼロトラストアクセス制御。

TLS に対する主な脅威と攻撃手法

SSL/TLSの歴史は脆弱性の発見と対応の繰り返しです。攻撃を3つの分類で整理して覚えましょう。クリックで詳細を展開できます。

攻撃の3分類 — クリックで詳細を確認

① バージョン・ネゴシエーション
ダウングレード系攻撃
仕組み：中間者がClientHelloを改ざんし、古いTLSバージョンや脆弱な暗号スイートへ誘導。
対策：TLS_FALLBACK_SCSV拡張・最低バージョン制限（TLS 1.2以上）
対象：SSL 3.0のCBCモード
仕組み：攻撃者がSSL 3.0へのダウングレードを強制→CBCパディング脆弱性を悪用→256リクエストで1バイト復号
対策：SSL 3.0の完全無効化
対象：輸出規制暗号（RSA_EXPORT）
仕組み：512bit RSAへのダウングレード→因数分解攻撃で鍵解読
対策：輸出暗号の無効化
対象：DHE 512bit（輸出グレード）
仕組み：弱いDHパラメータへのダウングレード→事前計算で解読
対策：DHE 2048bit以上、ECDHE推奨
② 暗号化データへの攻撃
暗号文解読・サイドチャネル系
対象：TLS 1.0のCBCモード
仕組み：IV予測可能性を悪用した既知平文攻撃→HTTPS Cookie盗聴
対策：TLS 1.1以上、AEADへの移行
対象：TLS圧縮機能
仕組み：圧縮後のサイズ変化を観測→CookieやCSRFトークンを1文字ずつ推測
対策：TLS圧縮の無効化（TLS 1.3で廃止済み）
対象：HTTPレスポンスのgzip圧縮
仕組み：攻撃者がリクエストを細工→レスポンスの圧縮サイズ変化でシークレット推測
対策：CSRFトークンのランダム化、圧縮無効化
③ 実装・証明書・中間者
バグ悪用・なりすまし系
対象：OpenSSL 1.0.1〜1.0.1f
仕組み：Heartbeat拡張の境界チェック不備→メモリから秘密鍵・パスワード・セッションデータを64KBずつ漏洩
対策：OpenSSL 1.0.1g以降へ更新・証明書再生成・秘密鍵入替
仕組み：偽CA発行証明書や証明書ピンニング回避により通信を傍受・改ざん
対策：証明書の厳格な検証・HSTS preload・CT（Certificate Transparency）
仕組み：HTTP→HTTPSリダイレクトを書き換えクライアントを平文に留める（Moxie Marlinspike, 2009）
対策：HSTS + preloadリスト登録

Q1TLS 1.3 での主な改善点として最も適切なものはどれか。
正解：ウ
TLS 1.3はRSA鍵交換・静的DHを廃止し、ECDHE/DHEのみとすることでPFSを必須化しました。往復数は「2-RTT → 1-RTT」の短縮（4往復→2往復ではない）。ChangeCipherSpecはTLS 1.3で廃止されました。
Q2SNI（Server Name Indication）拡張の説明として最も適切なものはどれか。
正解：ウ
SNIはClientHello内でアクセス先ホスト名を送信する拡張。1 IPアドレスで複数ドメインをホスト（バーチャルホスティング）可能にします。ア=key_share、イ=OCSP Stapling、エ=ALPN。
Q3Perfect Forward Secrecyを実現する仕組みとして最も適切なものはどれか。
正解：エ
PFSの核心は「一時鍵（Ephemeral Key）」の使用。ECDHEによりセッションごとに異なる鍵ペアを生成して使用後破棄することで、将来サーバの長期秘密鍵が漏洩しても過去通信は復号できません。
Q4SSLストリッピング攻撃への対策として最も有効なものはどれか。
正解：ウ
SSLストリッピングはHTTPSをHTTPに書き換えてクライアントを平文通信に誘導する攻撃。HSTSを設定すればブラウザが「このサイトへは必ずHTTPS」を学習しHTTPへのダウングレードを拒否。preloadリスト登録で初回アクセスから有効。
Q5次のうち「暗号化データへの攻撃」に分類されるものはどれか。
正解：イ（CRIME）
CRIMEはTLS圧縮を利用し暗号化後のサイズ変化を観察してCookieを推測する「暗号化データへの攻撃」。SSLストリッピング・Heartbleedは③実装/なりすまし系、FREAKは①ネゴシエーション系。

重要用語まとめ

試験頻出キーワード

TLS / SSLTransport Layer Security / Secure Sockets Layer。TCP上でアプリデータを暗号化。現行はTLS 1.2/1.3のみ有効。
ハンドシェイクTLS接続確立時の暗号スイート合意・証明書交換・鍵交換のプロセス。TLS 1.2は2-RTT、TLS 1.3は1-RTT。
暗号スイート鍵交換・認証・暗号化・ハッシュの組み合わせ文字列。例：TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
ECDHEElliptic Curve Diffie-Hellman Ephemeral。楕円曲線上の一時DH鍵交換。PFSを実現。TLS 1.3では必須。
PFSPerfect Forward Secrecy。サーバ秘密鍵の漏洩が過去の通信を復号できない性質。一時鍵の使用後破棄で実現。
AEADAuthenticated Encryption with Associated Data。暗号化と完全性認証を同時実行。TLS 1.3必須。
None X.509証明書Subject, Issuer, SAN, 有効期限, 公開鍵, CA署名を含む公開鍵証明書の標準フォーマット。
信頼チェーンエンドエンティティ証明書 → 中間CA → ルートCAへと辿る検証経路。
OCSPOnline Certificate Status Protocol。証明書の失効状態をリアルタイムで確認するプロトコル。
常時SSL/HTTPS化Webサイト全体をHTTPS化すること。部分SSL化の問題を解消。
HSTSHTTP Strict Transport Security。ブラウザに常時HTTPS強制を指示するヘッダ。SSLストリッピング対策。
SNIServer Name Indication。ClientHelloでホスト名を送信する拡張。1 IPで複数HTTPSドメイン運用可能。
ALPNApplication-Layer Protocol Negotiation。HTTP/2等をTLSハンドシェイク内でネゴシエーション。
0-RTTTLS 1.3のPSK再接続機能。初回メッセージをハンドシェイクと同時送信。リプレイ攻撃リスクあり。
HTTP CONNECTプロキシにトンネル確立を要求するHTTPメソッド。HTTPSのプロキシ中継に使用。
mTLSMutual TLS。双方向認証。CertificateRequest/CertificateVerifyが追加される。
POODLESSL 3.0のCBCパディング脆弱性攻撃。対策：SSL 3.0廃止、TLS_FALLBACK_SCSV。
HeartbleedOpenSSL Heartbeat実装バグ。メモリから秘密鍵等を窃取可能。対策：OpenSSL更新・証明書再生成。
SSLストリッピングHTTPSをHTTPに書き換えてダウングレードさせる中間者攻撃。対策：HSTS。
CRIMETLS圧縮サイズ変化でCookieを推測するサイドチャネル攻撃。対策：TLS圧縮無効化。

試験対策 7つの鉄則

1. TLS 1.3の核心は「RSA鍵交換廃止 + PFS必須 + 1-RTT + 証明書暗号化」
2. ハンドシェイク4フェーズ：Hello → 認証 → 鍵交換 → 暗号化開始
3. 証明書検証は6ステップ：信頼チェーン・署名・有効期限・失効・ドメイン・KeyUsage
4. PFSは「一時鍵（ECDHE）を毎回生成・破棄」で実現
5. SNI = 1 IP複数ドメイン / ALPN = HTTP/2ネゴシエーション
6. HSTS = SSLストリッピング対策 / 常時SSLの仕上げ
7. 攻撃分類：①ネゴシエーション系（POODLE/FREAK）、②暗号解読系（BEAST/CRIME）、③実装/なりすまし系（Heartbleed/MITM）
