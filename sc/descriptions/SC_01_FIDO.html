01

FIDOの全体像

FIDO（Fast IDentity Online）は、パスワードに依存しない強力な認証標準を策定する業界団体「FIDOアライアンス」が定めた規格群です。2012年設立で、Google・Microsoft・Apple・PayPalなどが参加しています。

パスワード認証の根本的な問題（フィッシング・使い回し・漏洩）を解決するため、公開鍵暗号方式とデバイス上での本人確認を組み合わせた構造を採用しています。たとえるならば、パスワードは「合言葉を口頭で教える」のに対し、FIDOは「本物の印鑑と印鑑証明で本人確認する」ようなものです。秘密鍵という印鑑はデバイスの外には出ず、公開鍵という印鑑証明だけをサーバに渡します。

FIDOアライアンス
2012年設立の業界標準化団体。Google・Microsoft・Apple等が参加し、パスワード不要の認証規格を策定。
秘密鍵非送信
秘密鍵はデバイスのTEE/SE/TPM内に格納され、ネットワーク越しに送信されることは絶対にない。
チャレンジ応答
毎回異なる乱数（チャレンジ）に署名して返送。傍受・再送によるリプレイ攻撃を構造的に無効化。
Origin紐付け
鍵ペアはドメイン（Origin）に紐付いて生成。偽サイトには対応する秘密鍵がないためフィッシング不成立。

認証エコシステム内でのFIDOの位置づけ

認証方式はその要素数と技術方式によって大きく分類されます。FIDOは「所持（デバイス）＋生体 or PIN」による2要素認証を、サーバにパスワードを送らずに実現する点で既存方式と本質的に異なります。

図 1 — 認証方式の全体分類とFIDOの位置づけ

FIDO2の構成：FIDO2は WebAuthn（W3Cが標準化したブラウザAPI仕様）と CTAP2（Client to Authenticator Protocol 2：ブラウザ↔認証器間の通信プロトコル）の2つで構成されます。

02

UAF・U2F・FIDO2 の比較

FIDOアライアンスは段階的にプロトコルを策定してきました。UAFとU2Fは2014年に同時策定された第一世代で、FIDO2はその両機能を統合した現行世代です。

比較項目 UAF U2F FIDO2（WebAuthn）
正式名称 Universal Authentication Framework Universal Second Factor WebAuthn + CTAP2
策定時期 2014年 2014年 2018年〜（現行）
パスワードレス 対応（1要素） 非対応 対応
第2要素（2FA） 非対応 対応 対応
主な認証器 スマートフォン（生体認証） セキュリティキー（USB/NFC） スマートフォン・PC・セキュリティキー
ブラウザAPI標準 なし 一部のみ WebAuthn API
フィッシング耐性 高 高 高
秘密鍵のサーバ送信 なし（安全） なし（安全） なし（安全）
後継・発展 → FIDO2に統合 Passkeys（パスキー）へ発展

試験頻出：UAFは「パスワードレス（1要素で完結）」、U2Fは「パスワード＋第2要素（2FA）」と役割が明確に異なります。FIDO2はその両方を統合した最新版であることを押さえてください。

03

公開鍵暗号の仕組みとFIDOへの適用

FIDOの核心は公開鍵暗号方式にあります。デバイスがRP（Relying Party：サービス提供者）ごとに鍵ペアを生成し、秘密鍵はデバイス内のセキュアエリアに保管、公開鍵のみをサーバに登録します。

図 2 — 公開鍵暗号によるFIDO認証の原理

登録
デバイスがRPごとに秘密鍵・公開鍵ペアを新規生成。秘密鍵はTEE/SE等のセキュアエリアに格納。公開鍵とCredential IDをサーバに登録します。
認証
サーバが毎回異なるチャレンジ（乱数）を発行。デバイスが秘密鍵でチャレンジに署名して返送。サーバは登録済み公開鍵で署名を検証します。
核心
秘密鍵は一切ネットワークを流れません。サーバには公開鍵しか存在しないため、サーバが侵害されても認証情報は漏洩しません。
04

FIDO2 登録シーケンス

FIDO2の登録（Registration）は初回のみ実施するフローです。ユーザーはデバイス上で生体認証やPINを実施し、生成された公開鍵をRPサーバに登録します。

シーケンス図 1 — FIDO2 登録（sd FIDO2 Registration）

③
RPサーバが challenge（乱数）・rpId・userId・pubKeyCredParams（対応アルゴリズムリスト）をブラウザへ返します。
⑤⑥
認証器がユーザーに生体認証またはPINの入力を要求します。これを User Verification（UV） と呼びます。UAFでは主要認証手段、FIDO2では必要に応じて要求します。
⑦
認証器内部で鍵ペアを生成。秘密鍵はTEE/SEに格納し、公開鍵・Credential ID・Attestation（認証器の正当性証明）をブラウザへ返します。
!
Attestationとは：認証器が正規のデバイスであることをメーカーの証明書で証明する情報です。RPサーバはAttestation証明書チェーンを検証して認証器の信頼性を確認します。
05

FIDO2 認証シーケンス

登録後の認証（Authentication）フローです。サーバが発行したチャレンジを秘密鍵で署名して返送し、サーバが公開鍵で検証します。signCount（署名カウンター）により認証器クローンやリプレイ攻撃も検知します。

シーケンス図 2 — FIDO2 認証（sd FIDO2 Authentication）

③
RPサーバが毎回新しいチャレンジ（乱数）を生成して送信します。allowCredentials には登録済み Credential ID リストが含まれ、対応する認証器のみが応答できます。
⑦
認証器内部で秘密鍵によりチャレンジに署名し、signCountをインクリメントして返します。チャレンジはOriginも含むため偽サイトでは署名対象が異なります。
⑨
RPサーバは ①公開鍵で署名検証 ②signCount が保存値より大きいか確認 の2点を検証します。signCountが逆転していれば認証器クローンまたはリプレイ攻撃として認証を拒否します。

核心ポイント

FIDO2認証の本質は「秘密鍵を送らずに、秘密鍵を持っていることを証明する」点にあります。毎回異なるチャレンジを使うことでリプレイ攻撃を無効化し、Origin紐付けでフィッシングを構造的に排除します。

06

UAF シーケンス（パスワードレス）

UAF（Universal Authentication Framework）はパスワードを完全に排除するプロトコルです。スマートフォンの生体認証が主要な認証手段となり、その成果を公開鍵署名でサーバに証明します。たとえるならば、「顔パス」で入館する仕組みを、デジタル証明書で厳密化したものです。

シーケンス図 3 — UAF 登録・認証フロー（sd UAF Authentication）

③④
UAFはパスワードなしに生体認証のみでユーザー確認を行います。指紋・顔・虹彩など、デバイスのセキュアエリアで照合が完結します。
⑫
認証時、署名された {signature, KeyID} を受け取ったサーバは、登録時に保存した公開鍵で署名を検証します。パスワードは一切使用・送信されません。
07

U2F シーケンス（第2要素認証）

U2F（Universal Second Factor）は既存のパスワード認証に強力な第2要素を追加するプロトコルです。セキュリティキー（YubiKey等）をUSBやNFCで接続し、物理ボタンを押すだけで認証を完了します。パスワードは引き続き使用しますが、フィッシング耐性が大幅に向上します。

シーケンス図 4 — U2F 第2要素認証（sd U2F Authentication）

⑤⑥
U2F固有の確認として User Presence（UP）があります。ユーザーが物理ボタンを押したことで「意図的な操作」を証明します。これによりマルウェアによる自動的な悪用を防ぎます。
⑧
RPサーバは ①署名検証 ②counter が保存値より大きいかの2点を確認します。counterが逆転していれば認証器クローンの可能性として認証を拒否します。
!
UAFとの違い：U2Fでは第1要素のパスワード認証は引き続き必要です。セキュリティキーはあくまで第2要素の強化であり、パスワードを置き換えるものではありません。
08

FIDO認証への脅威と対策

FIDO認証はパスワード認証と比較して格段に安全ですが、実装・運用上の脅威は存在します。以下に代表的な脅威と対策を整理します。

認証器の紛失・盗難

スマートフォンやセキュリティキーが盗まれた場合、生体認証やPINが第2の防壁となる。ただし強制解除の可能性もゼロではない。

対策：生体認証の必須化・Credential IDのサーバ側無効化・デバイス紛失時の即時失効手順

認証器クローン

TEE/SEからの秘密鍵抽出による認証器の複製。物理的攻撃が必要で非常に困難だが、理論上はゼロではない。

対策：signCountの監視（逆転で検知）・TEE/SE搭載の認証器の採用・FIDO認定デバイスの使用

マルウェアによる認証の乗っ取り

ユーザーのデバイスにマルウェアが感染し、FIDOの認証セッション確立後にブラウザ操作を乗っ取る（Session Hijacking）。

対策：エンドポイントセキュリティの強化・セッション管理の堅牢化・異常ログインの検知

ソーシャルエンジニアリング

ユーザーを騙して意図しない認証器登録・認証を実行させる。例えばサポートを装い不正な登録操作を誘導する。

対策：登録・認証操作の明示的な意思確認UIの実装・セキュリティ教育・不審な登録の通知

RPサーバの侵害

サーバに保存されているのは公開鍵のみであるため、サーバが侵害されてもパスワードのような認証情報は流出しない。ただしサービス停止リスクはある。

対策：公開鍵DBのアクセス制御・HSMによるサーバ秘密鍵管理・多重署名・ログ監査

フォールバック認証の脆弱性

認証器紛失時のアカウント回復フローとして設けられたフォールバック認証（メール・電話番号等）が攻撃の標的になる。

対策：回復コードの安全な管理・フォールバック認証の強化・SIMスワップ対策

過去問スタイル 練習問題

情報処理安全確保支援士試験の出題傾向に沿った練習問題です。選択肢をクリックすると正誤と解説が表示されます。

Q1 FIDO UAFに関する説明として、最も適切なものはどれか。
正解：イ
UAF（Universal Authentication Framework）はパスワードを完全に排除するプロトコルです。生体認証（指紋・顔認証）やPINをデバイス上で実施し、その結果を公開鍵署名でサーバに証明します。
ア：これはU2Fの説明です。
ウ：これはWebAuthn（FIDO2の構成要素）の説明です。
エ：TOTPはFIDOとは無関係のOTP規格（RFC 6238）です。
Q2 FIDO2認証においてリプレイ攻撃を防止する主な仕組みとして、最も適切なものはどれか。
正解：ウ
FIDO2はチャレンジ&レスポンス方式を採用しています。サーバが毎回異なるチャレンジ（乱数）を生成し、認証器がそれに秘密鍵で署名します。署名はチャレンジに紐付くため、過去の署名を再送しても別のチャレンジには対応できません（リプレイ攻撃不可）。さらにsignCountの増加チェックで認証器クローンも検知できます。
ア：鍵ペアは登録時に1回生成し、認証のたびに変えるものではありません。
エ：IPアドレスはFIDOの仕組みではなく、モバイル環境では毎回変化するため実用的でもありません。
Q3 FIDO2がフィッシング攻撃に対して高い耐性を持つ根本的な理由として、最も適切なものはどれか。
正解：イ
FIDOのフィッシング耐性の核心は「鍵ペアがRP ID（Originのドメイン）に紐付いている」ことです。例えば https://bank.com に登録した鍵は https://evil-bank.com では使用できません。認証器がOriginを検証し、登録時のドメインと一致しない場合は署名処理を実行しないためです。
ア：FIDOはサーバに秘密鍵を送らないため、この観点は異なります。
ウ：SMSによるOTPはFIDOとは無関係です。
エ：SSL証明書の種類による制限はFIDOの仕組みではありません。
Q4 FIDO2の構成要素に関する記述のうち、誤っているものはどれか。
正解（誤り）：エ
FIDOの重要な設計原則として、認証器はRPごとに異なる鍵ペアを生成します。同一の鍵を複数サービスで使うと、各サービスがユーザーを横断的に追跡（名寄せ）できてしまいプライバシーの問題が生じます。RP別に独立した鍵ペアを持つことがFIDO設計上の必須要件です。
ア：正しい。WebAuthnはW3C標準でブラウザのJavaScript APIとして組み込まれています。
イ：正しい。CTAPはブラウザと外部認証器の通信規格です。
ウ：正しい。RPサーバは登録時に公開鍵とCredential IDを保管します。
Q5 FIDO2認証において、受信した signCount の値がRPサーバに保存されている値以下であった場合、RPサーバが取るべき対応として最も適切なものはどれか。
正解：ウ
signCountは認証のたびに単調増加する設計です。受信値がサーバ保存値以下であれば以下のシナリオが考えられます：
1. リプレイ攻撃：以前傍受した認証レスポンスを再送している
2. 認証器のクローン：秘密鍵がコピーされた偽の認証器が存在し、古い状態から使い始めた

WebAuthn仕様書（W3C）では、この場合は認証を失敗させ、インシデントとして扱うことが求められています。ネットワーク遅延やバッテリー切れはカウンターの逆転を引き起こしません。
Q6 FIDO2認証とTOTP（Time-based One-Time Password）の違いについて、最も適切な説明はどれか。
正解：ウ
TOTPはリアルタイムフィッシング（本物サイトへ転送する中間者サイト）への耐性がありません。攻撃者が偽サイトでOTPコードを取得し即座に本物サイトへ転送すれば認証を突破できます。
一方FIDO2は鍵ペアがOrigin（ドメイン）に紐付いているため、偽サイトのドメインに対応する秘密鍵が存在せず、そもそも署名が成立しません。
ア：誤り。サーバに秘密鍵を送らないFIDO2の方がサーバ侵害時のリスクは低い（公開鍵のみ）。
イ：逆です。TOTPのコードこそネットワーク経由で送信されます。

User Verification（UV）ユーザーの本人確認。生体認証またはPINによる確認。UAFでは必須、U2Fでは任意。
User Presence（UP）ユーザーがその場にいることの確認。U2Fでのボタン押下がこれに相当。

Originスキーム・ホスト・ポートの組み合わせ（例：https://example.com）。FIDO2はOriginと鍵ペアを紐付けてフィッシングを防ぐ。
Passkeys（パスキー）FIDO2の発展形。Credential IDと秘密鍵をクラウド同期可能にしたもの。Apple・Google・Microsoftが実装。
AppID（UAF/U2F）UAF/U2Fでのサービス識別子。FIDO2ではRP IDに相当。

試験対策 5つの鉄則

1. 秘密鍵はデバイス外に出ない — 署名処理はTEE/SE内で完結し、ネットワーク越しに送信されない
2. UAF＝パスワードレス、U2F＝第2要素追加 — FIDO2はその両方を統合した現行規格
3. フィッシング耐性の理由はOrigin紐付け — 偽サイトのドメインには対応する秘密鍵がない
4. リプレイ防止はチャレンジ（乱数）＋signCount — 毎回異なるチャレンジ＋単調増加カウンター
5. signCount逆転は即座に認証拒否 — クローン認証器またはリプレイ攻撃のインシデントとして扱う
