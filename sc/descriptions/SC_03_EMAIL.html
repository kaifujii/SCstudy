02

電子メールの構造

電子メールはエンベロープ（外側の封筒）とメッセージ（中の手紙）の2層構造です。メッセージはさらにヘッダとボディに分かれます。この3つの区別は試験で最頻出です。

電子メール 3層構造
エンベロープ
MAIL FROM:sender@example.com ← SMTPの実際の送信者（Return-Path）
RCPT TO:recipient@example.jp ← SMTPの実際の宛先（配送先）
SMTP通信中のみ存在。最終的には Return-Path: ヘッダに残る。メール本文（ヘッダ・ボディ）とは独立。SPFはここを検証する。
ヘッダ
From:"山田 太郎" <taro@example.com> ← 表示用差出人（なりすまし可能）
To:user@example.jp
Subject:=?UTF-8?B?5LuL5ZCN?= ← Base64エンコードされた件名
Date:Mon, 15 Apr 2026 09:30:00 +0900
Message-ID:<unique-id@example.com>
Received:転送の痕跡（MTAが追記・最新が先頭）
MIME-Version:1.0
Content-Type:multipart/mixed; boundary="---_Part"
ヘッダとボディの区切りは 空行1行（CRLF×2）。DKIMはヘッダ＋ボディを署名対象にする。
ボディ
text/plainプレーンテキスト本文
text/htmlHTML形式本文（MIMEマルチパートで併送可）
application/pdf添付ファイル（Base64エンコード）

混同注意：エンベロープ From と ヘッダ From は別物
エンベロープの MAIL FROM:（SMTPコマンド）とヘッダの From:（表示差出人）は独立しています。フィッシングメールはヘッダの From: だけを正規ドメインに偽装し、エンベロープの MAIL FROM: は別ドメインにすることがあります。SPFはエンベロープFrom、DMARCはヘッダFromとの整合性をチェックします。

MIME とエンコード

元々SMTPはASCIIテキストしか扱えませんでした。MIMEにより日本語・添付ファイル・HTML形式のメールが可能になりました。

MIME
MIME（Multipurpose Internet Mail Extensions）：メールに Content-Type / Content-Transfer-Encoding などのヘッダを追加し、テキスト以外のデータを扱う拡張規格（RFC 2045〜2049）。マルチパート構造（本文＋添付ファイル）を実現します。
B64
Base64：バイナリデータを64種類の印刷可能ASCII文字（A–Z, a–z, 0–9, +, /）に変換するエンコード方式。3バイト→4文字に変換し、データが約4/3倍になります。暗号化ではありません。鍵なしで誰でもデコード可能です。添付ファイルや証明書データの転送に使用されます。
QP
Quoted-Printable：非ASCII文字を =E3=81=82 形式（=＋16進数2桁）でエンコードする方式。ASCII文字はそのまま残るため、英文メインのテキストを人間が読みやすい形で保ちながら国際化文字を扱えます。

電子メールプロトコル比較

メール関連プロトコルは役割・方向・ポートを組み合わせて整理します。「送信 = SMTP」「受信 = POP3 or IMAP4」「形式拡張 = MIME」「暗号化 = S/MIME」が大きな分類です。

MIME 形式拡張 —（プロトコルではなく形式） — ASCII以外のデータ（日本語・添付ファイル・HTML）をメールで扱うための拡張仕様。RFC 2045〜2049。

06

認証セキュリティ（SMTP-AUTH / POP before SMTP / S/MIME / PGP）

「誰がメールを送れるか」を制御するアクセス制御技術と、「メール内容の機密性・真正性」を守るコンテンツ暗号化技術の2軸があります。

送信者アクセス制御

SMTP-AUTH
SMTP-AUTH（SASL認証）：MUAがメールをMSA/MTAに送信する際にユーザIDとパスワードで認証する仕組み（RFC 4954）。EHLOに続きAUTHコマンドを使用。送信Port 587（Submission）と組み合わせて使用します。現在の標準的な送信者認証方式。必ずTLS（STARTTLS）と併用すること。
認証メカニズムとして AUTH PLAIN / AUTH LOGIN / AUTH CRAM-MD5 等があります。
POP
before
SMTP
POP before SMTP（旧式方式）：「まずPOP3でメール受信して認証する」→「認証成功したIPアドレスからのSMTP送信を一定時間許可する」という回避策的な仕組みです。SMTPプロトコル自体に認証機能がなかった時代の暫定策であり、現在はSMTP-AUTHに置き換えられ廃止傾向にあります。
問題点：IPアドレスベースのため、同一NATの別ユーザが使えてしまう・時間切れまで第三者も送信できるリスクがある。

コンテンツ暗号化・署名（S/MIME vs PGP）

比較項目S/MIMEPGP / OpenPGP
信頼モデルPKI（認証局CAが証明書を発行）Web of Trust（ユーザ間で相互署名）
証明書管理CAからの証明書取得が必要（有償の場合あり）自己生成のキーペアで即使用可能
企業利用企業向け（CA管理・集中管理しやすい）個人・コミュニティ向け
標準化RFC 8551（S/MIME 4.0）RFC 4880（OpenPGP）
暗号化受信者の公開鍵で暗号化（エンドツーエンド）受信者の公開鍵で暗号化（エンドツーエンド）
デジタル署名送信者の秘密鍵で署名 → 否認防止送信者の秘密鍵で署名 → 否認防止
メールサーバの関与エンドツーエンド（サーバは中身を見られない）エンドツーエンド（サーバは中身を見られない）

核心ポイント

S/MIME と PGP はいずれもエンドツーエンド暗号化です。メールサーバを経由しても内容は保護されます。一方、SMTP over TLS（STARTTLS）は転送路の暗号化に過ぎず、サーバ上では平文となります。この違いが試験頻出です。

メールヘッダの解析

メールヘッダには送信経路・認証結果・送信者情報など多くの情報が含まれます。インシデント対応やフィッシングメール調査で必須のスキルです。

1
Received ヘッダの読み方：最新の転送情報が先頭に追記されます。下（古い）→ 上（新しい）の順に読むことで転送経路が把握できます。送信元IPアドレスの確認に使用。ただし最初の数エントリは偽造されている可能性があります。
2

4

5

アクター間のやり取り — 詳細シーケンス図

送信から受信までの流れの中で、各技術がどのアクター間でいつ・何をしているかを3本のシーケンスで示します。

SPF — Sender Policy Framework
「このIPアドレスは example.com を名乗って送信してよいか？」を DNS で確認する
SPFのポイント：受信MTAがMAIL FROM:のドメインでDNSを引き、送信元IPが許可リスト内かを照合。DNSクエリは受信側が行う。送信側はDNSに登録するだけ。
DKIM — DomainKeys Identified Mail
送信ドメインの秘密鍵で署名し、受信側がDNSの公開鍵で検証する
DKIMのポイント：送信側が秘密鍵でメール本文とヘッダの署名を生成しDKIM-Signatureヘッダに添付。受信側はDNSから公開鍵を取得して検証。改ざん検知とドメイン認証を同時に実現。
DMARC — Domain-based Message Authentication
SPF/DKIMの結果＋ヘッダFromとのアライメントを検証し、失敗時のポリシーを適用する
DMARCのポイント：SPF・DKIMの認証ドメインがFrom:ヘッダのドメインと一致するかを検証（アライメント）。不一致ならnone/quarantine/rejectを適用。失敗状況を送信ドメイン管理者にレポート。

各技術「どこの何に対してどんな目的の仕組み」か — 完全整理

各技術が「どの通信経路で、どの脅威に対して、何を達成するか」を体系的に整理します。技術の目的が曖昧だと問題文で誤答しやすい項目です。

S/MIME MUA（エンドユーザ）間のメール本文 メール内容の盗聴・改ざん・なりすまし エンドツーエンドの機密性（暗号化）・完全性・送信者認証・否認防止（デジタル署名）

OP25B 一般ユーザ端末 → 外部MTA（Port 25・外向き） マルウェア感染PCによる直接スパム大量送信 一般ユーザからの外向きPort 25をISPがブロック。正規送信はPort 587へ誘導

DMARC 受信サーバでの総合判定（ヘッダFromとSPF/DKIMの整合性） SPF/DKIMを回避したヘッダFrom詐称（フィッシング・BEC対策の最終防衛ライン） SPF/DKIMにアライメント検証を加えたポリシー統合（none/quarantine/reject）と可視化（レポート）

試験対策 全体俯瞰

転送路の暗号化（SMTP over TLS）とコンテンツの暗号化（S/MIME / PGP）は別物。サーバ上では平文か否かが違いの核心。
SPF＝IP照合（エンベロープFrom） / DKIM＝署名検証（本文＋ヘッダ） / DMARC＝ポリシー統合（ヘッダFromとの整合＋アライメント）。
OP25B＝送信側が送れなくする（ISP） / IP25B＝受信側が受け取らない（受信サーバ）。
SMTP-AUTHは「誰が送信するか」のアクセス制御、SPF/DKIM/DMARCは「どのドメインから送られたか」の認証。

過去問スタイル 練習問題

情報処理安全確保支援士試験の出題傾向に沿った練習問題です。選択肢をクリックすると正誤と解説が表示されます。

Q1電子メールのエンベロープとヘッダの From について、最も適切な説明はどれか。
正解：ウ
エンベロープの MAIL FROM（Return-Path）はSMTP通信で実際に使用される送信者情報で、メール配送・バウンス処理に使います。ヘッダの From はメーラに表示される差出人です。両者は独立しており、フィッシングメールではヘッダ From だけを正規ドメインに見せかけ、MAIL FROM は別ドメインにすることがあります。DMARCのアライメントはこの乖離を検知します。
Q2OP25B（Outbound Port 25 Blocking）の説明として最も適切なものはどれか。
正解：イ
OP25B は Outbound（外向き）Port 25 Blocking の略です。ISP が自ネットワーク内の一般ユーザからインターネット上の外部 MTA への Port 25 通信を遮断します。感染PCが直接スパムを送れなくなります。正規の送信はPort 587（Submission + SMTP-AUTH）を使います。
アは IP25B（Inbound）の説明です。
Q3DKIM（DomainKeys Identified Mail）の説明として最も適切なものはどれか。
正解：エ
DKIMは送信MTAがメールに DKIM-Signature ヘッダを付与し（秘密鍵で署名）、受信側がDNSのTXTレコードから公開鍵を取得して署名検証します。メール本文の改ざん検知と送信ドメインの認証を同時に達成します。
アはSPFの説明。イはDMARCの説明。ウはSMTP-AUTHの説明です。
Q4DMARC が実施する「アライメント検証」とは何か。最も適切なものはどれか。
正解：ウ
DMARCのアライメントは「SPF または DKIM の認証ドメインが、ユーザに表示されるヘッダ From: のドメインと整合しているか」を確認します。これにより「SPF は pass だが MAIL FROM は別ドメイン」というなりすましを検出できます。SPF・DKIMの両方が失敗してもどちらかがアライメント付きで pass なら DMARC は pass です。
Q5S/MIME と PGP の比較について最も適切な説明はどれか。
正解：エ
S/MIME と PGP はいずれもエンドユーザ間（MUA同士）のエンドツーエンド暗号化・デジタル署名を実現します。違いは信頼モデルのみです。S/MIME はCA発行のX.509証明書（PKIベース）、PGP はユーザ同士が署名し合うWeb of Trustを採用します。
Base64はエンコード（符号化）であり暗号化ではないため、デコードで平文に戻せます。
Q6メールヘッダの Received フィールドについて正しいものはどれか。
正解：イ
Received ヘッダはメールを中継した各 MTA が追記するフィールドです。最後に転送した MTA が先頭に追記するため、先頭が最新・末尾が最古になります。下から上（古い順）に読むと送信経路を追跡できます。フォレンジックやスパム調査で重要な情報源です。ただし最初の（送信者に近い側の）Received は偽造されている可能性もあります。

試験対策 6つの鉄則

1. エンベロープ From ≠ ヘッダ From — SPFはエンベロープ、DMARCはヘッダFromとの整合を最終判定に使う
2. Base64 は暗号化ではない — エンコード（符号化）であり誰でもデコード可能
3. OP25B=送信側ISPが遮断 / IP25B=受信側サーバが拒否 — Outbound / Inbound の方向で覚える
4. S/MIME・PGP はエンドツーエンド / STARTTLS は転送路のみ — サーバ上では平文か否か
5. SPF=IP照合 / DKIM=署名検証 / DMARC=ポリシー統合＋アライメント — 3つの役割は異なる
6. Received ヘッダは下から上（古い→新しい） — 最上段が最終MTA、最下段が最初のMTA
