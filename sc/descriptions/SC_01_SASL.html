01

SASLの立ち位置

SASL（Simple Authentication and Security Layer）は、アプリケーションプロトコルと認証メカニズムを分離するためのフレームワーク仕様（RFC 4422）です。SASL自身は認証ロジックを持たず、どのメカニズムを使うかを決めるネゴシエーション層として機能します。

例えるなら「コンセント規格」：コンセント（SASL）はどんな電化製品（メカニズム）でも差し込める統一口を提供します。プラグの形状（認証アルゴリズム）が変わっても、コンセント自体は交換不要です。

プロトコルスタックにおける位置づけ

アプリ層
SMTP IMAP LDAP XMPP MongoDB ← SASLを呼び出すプロトコル群
SASL層
SASL フレームワーク（RFC 4422） ← メカニズムを選ぶだけ・認証はしない
ここがポイント：SASLは「どの方式で認証するか」を決める仲介役。実際に認証するのは下のメカニズム。
メカニズム層
SCRAM-SHA-256 GSSAPI OAUTHBEARER PLAIN CRAM-MD5 ※非推奨
トランスポート層
TLS / STARTTLS ← 通信路の暗号化（SASLとは独立した別の仕事）

よくある誤解：SASLはTLSの代替ではありません。SASLは「誰か」を確認する認証を担い、TLSは「通信路を保護する」暗号化を担います。両者は独立して組み合わせて使います。

02

同じ「認証フレームワーク」レイヤーとの比較

SASLと同じ「認証統合レイヤー」に位置する方式・プロトコルを比較します。それぞれが担う役割が異なる点が試験のポイントです。

方式・規格 主な役割 主な用途 SASLとの関係
SASL 認証フレームワーク SMTP / IMAP / LDAP / XMPP —（本体）
OAuth 2.0 認可フレームワーク
アクセス権限を委譲する仕組み		 Web API・クラウドサービス OAUTHBEARERとしてSASLメカニズムに採用
Kerberos ネットワーク認証プロトコル
チケットでSSOを実現		 企業内ネットワーク・AD GSSAPIとしてSASLメカニズムに採用
PAM OS認証プラグイン機構
アプリとOS認証を切り離す		 Linux ログイン・SSH SASLのバックエンドとして連携可
RADIUS AAAプロトコル
認証・認可・課金を集中管理		 VPN・無線LAN認証 異なるレイヤー。直接競合しない
HTTP Basic / Digest HTTP固有の認証方式
DigestはMD5依存のCR型		 ブラウザ・REST API HTTP専用。SASLとは別体系

核心ポイント

OAuth 2.0は本来「認可（誰に何を許可するか）」の仕組みであり、認証ではありません。メール認証に使われるOAUTHBEARERはOAuth 2.0のトークンをSASLのメカニズムとして使うための仕様です。試験では「OAuth 2.0 ＝ 認証」と書かれた選択肢は誤りです。

03

チャレンジ応答認証フロー

SASLのネゴシエーションから認証完了までの流れです。矢印の色でメッセージの方向を区別しています。

シーケンス図 — SASL チャレンジ応答（SCRAM-SHA-256）

1
メカニズム通知：サーバーが対応メカニズム一覧を送信。クライアントはここから一つを選択します。この段階をネゴシエーションと呼びます。
3
チャレンジ（nonce）：毎回異なるランダム値を送ることで、過去の認証トランザクションを再送するリプレイ攻撃を無効化します。
4
レスポンス：クライアントはパスワード平文を送らず、nonceと組み合わせたHMAC-SHA256ハッシュ値を返します。パスワードはネットワークに流れません。
5
相互認証（SCRAM専用）：サーバーも自身の署名をクライアントに返します。クライアントがサーバーを検証できるためフィッシングサイトへの誤認証を防止できます。
!
PLAINの注意点：チャレンジ応答なし。base64_decode()で即座に復元できるためTLSなしでは平文と同等のリスクがあります。

試験で頻出のメカニズムを安全性・特徴・現在の推奨状況で比較します。

メカニズム名安全性CR方式相互認証TLS現状
SCRAM-SHA-256強ありあり推奨推奨（RFC 7677）
SCRAM-SHA-1中ありあり推奨SHA-256への移行推奨
GSSAPI強チケット型あり任意企業AD環境で標準
OAUTHBEARER強トークン型条件による必須クラウドで拡大中

CRAM-MD5低ありなし推奨非推奨・移行推奨
LOGIN低なしなし必須非標準・レガシー
ANONYMOUSなしなしなし任意限定用途のみ
05

脅威と攻撃手法

SASL認証に対する代表的な攻撃手法と対策を整理します。

攻撃手法仕組み主な対策
ダウングレード攻撃中間者がネゴシエーション時のメカニズム一覧を改ざんし、クライアントに意図的に弱いメカニズム（PLAINなど）を選ばせる。SASLネゴシエーション自体をTLSで保護する（STARTTLS完了後にAUTH）
盗聴（スニッフィング）PLAINやLOGINをTLSなしで使うと、Base64デコードのみで認証情報を取得できる。PLAIN使用時は必ずSTARTTLSまたはTLS上で使用する
リプレイ攻撃傍受した認証レスポンスを後から再送し、正規ユーザーとして認証させる。チャレンジ応答のnonce（毎回異なる乱数）を使用する（SCRAM等）
辞書攻撃 / 総当たりCRAM-MD5など旧来の方式ではオフライン辞書攻撃が有効。SCRAM-SHA-256のsalt+stretchingでオフライン攻撃コストを増加させる
フィッシング（偽サーバー）偽サーバーへのSASL認証で認証情報を詐取する。CRAM-MD5は相互認証がないため検知できない。SCRAM-SHA-256の相互認証を使用し、サーバーの正当性をクライアントが検証する
MD5衝突を悪用した偽造CRAM-MD5・DIGEST-MD5はMD5の衝突脆弱性を利用した攻撃が理論上成立する。MD5系メカニズムを廃止しSCRAM-SHA-256に移行する
06

試験で問われやすいポイント・間違いやすいポイント

間違いやすいポイント

誤
「SASLで認証した」は誤り。SASLはフレームワークであり認証ロジックを持たない。正確には「SASL上のSCRAM-SHA-256で認証した」。
誤
「PLAINはパスワードを暗号化している」は誤り。Base64はエンコード（可逆変換）であり暗号化ではない。base64_decode()で即座に元に戻せる。
誤
「OAuth 2.0はSASLの認証方式」は誤り。OAuth 2.0は認可フレームワーク。SASLで使われるのはOAUTHBEARERメカニズム。
誤
「SCRAM-SHA-256ならTLS不要」は誤り。SCRAMはパスワード平文を送らないが、通信路の暗号化はTLSの別の仕事。
!
CRAM-MD5とDIGEST-MD5の違い：CRAM-MD5は相互認証なし（一方向のみ）。DIGEST-MD5は相互認証に部分対応。両者ともMD5の脆弱性により廃止勧告。混同しやすいので要注意。
!
GSSAPIとKerberosの関係：GSSAPIはSASLのメカニズム名。実体はKerberos V5。「GSSAPIで認証＝Kerberosチケットを使ってSSOを実現」と覚える。

試験対策 5つの鉄則

1. SASLはフレームワーク — 認証はメカニズムが行う。「SASL自体が認証する」は誤り
2. Base64はエンコード、暗号化ではない — PLAIN使用時はTLS必須
3. リプレイ防止にはnonce（毎回異なる乱数） — チャレンジ応答の本質
4. 相互認証はSCRAMとGSSAPIのみ — PLAINやCRAM-MD5にはない
5. OAuth 2.0は認可、認証ではない — OAUTHBEARERはそのトークンをSASLで使う仕様

08

重要用語まとめ

試験頻出キーワード

SASLSimple Authentication and Security Layer。アプリ層に認証を追加するフレームワーク（RFC 4422）。認証処理はメカニズムが担う。
ネゴシエーションSASLの最初のフェーズ。サーバーが対応メカニズム一覧を通知し、クライアントが一つを選択する。
チャレンジ応答サーバーがランダムな値（nonce）を送り、クライアントがそれを使って計算した値を返す認証方式。リプレイ攻撃を防ぐ。
nonceNumber used once。毎回異なるランダム値。同じチャレンジが繰り返されないため、傍受した応答の再送が無効になる。
SCRAM-SHA-256Salted Challenge Response Authentication Mechanism。相互認証・平文不保存・SHA-256の3点を持つ現在の推奨方式（RFC 7677）。
GSSAPIGeneric Security Services API。KerberosなどをSASLから呼び出すためのメカニズム名。Active Directory環境のSSO認証で使われる。
OAUTHBEAREROAuth 2.0のBearerトークンをSASL認証に使用するメカニズム（RFC 7628）。クラウドメールサービスで拡大中。
PLAINユーザー名+パスワードをBase64エンコードして送る最シンプルな方式。TLS必須。Base64は可逆変換のためTLSなしでは危険。
DIGEST-MD5MD5ハッシュを用いたチャレンジ応答方式。MD5の脆弱性によりRFC 6331で廃止勧告。
CRAM-MD5HMAC-MD5を使った1ラウンドのチャレンジ応答。相互認証なし・辞書攻撃に脆弱。SCRAM系への移行を推奨。
相互認証クライアントがサーバーを認証し、サーバーがクライアントを認証する双方向の認証。SCRAM・GSSAPIが対応。偽サーバー検知に有効。
ダウングレード攻撃ネゴシエーション段階でメカニズム一覧を改ざんし、クライアントに意図的に弱い認証方式を選ばせる中間者攻撃。
STARTTLS平文接続を途中でTLSに切り替えるコマンド。SASL AUTH の前に実行することでネゴシエーション自体を保護できる。

試験対策まとめ

1. SASLは認証しない — メカニズムを「選ぶ」だけのフレームワーク
2. Base64 ≠ 暗号化 — PLAINには必ずTLSが必要
3. リプレイ防止 ＝ nonce — チャレンジ応答の本質
4. GSSAPIの実体はKerberos — AD環境のSSOの仕組み
5. OAuth 2.0は認可 — OAUTHBEARERはそのトークンをSASLで使う仕様
