01

SASLの立ち位置

SASL（Simple Authentication and Security Layer）は、アプリケーションプロトコルと認証メカニズムを分離するためのフレームワーク仕様（RFC 4422）です。SASL自身は認証ロジックを持たず、どのメカニズムを使うかを決めるネゴシエーション層として機能します。

たとえ 「コンセント規格」 — SASLとメカニズムの関係
口の形を規格化すれば、中身の家電（メカニズム）は自由に差し替えられる

核心：SASLは「認証しない」。SASLはどのメカニズムで認証するかを取り決めるだけです。「SASLで認証した」という表現は技術的に誤りで、「SASL上のSCRAM-SHA-256で認証した」が正確です。

SASLは「B（ネゴシエーション）」だけを担当するのが最大の特徴です。C（資格）とD（検証）は選ばれたメカニズムに完全に委譲します。OAuthは「C + D（トークン経由）」、Kerberosは「C〜E」、HTTP Basicは「A〜E全部」を1方式でこなします。カバー範囲の広さ＝複雑さ・柔軟性のトレードオフです。

PLAIN の場合はステップ2だけ（チャレンジなし）。AUTH PLAIN [user]\0[user]\0[password] を Base64 で一度送るだけです。Base64は可逆変換 → 通信を見れば平文パスワードが得られるため、TLS が前提になります。

Base64は「暗号化」ではない — 体感デモ
入力テキスト（例: ユーザー名\0パスワード）
Base64エンコード結果

Base64エンコードは誰でも即座に元のテキストへ戻せる可逆変換です。鍵も共有秘密も使っていません。TLSを張らずにPLAINを使うと、傍受した攻撃者はその場でパスワードを復元できます。

3

4

5

CRAM-MD5
非推奨 — 移行推奨
MD5（脆弱） 相互認証なし 辞書攻撃に脆弱 1ラウンド
HMAC-MD5 を使ったチャレンジ応答方式。パスワードを直接送らない点は SCRAM と同じだが、MD5の衝突脆弱性・相互認証なし・辞書攻撃への脆弱性 から非推奨。現在は SCRAM-SHA-256 への移行が推奨。
たとえ話：「合言葉で確認する」仕組み自体は正しいが、使っている暗号が古い（MD5）。そして店員（サーバー）は身分証を見せないので偽店舗かどうかを客（クライアント）は判別できない。仕組みは良くても素材が古すぎる。
問題点の整理
CRAM-MD5 の弱点
・MD5 の衝突耐性が低く、偽造の余地あり
・サーバーがクライアントを証明しない（相互認証なし）
・オフライン辞書攻撃が有効
SCRAM-SHA-256 への移行ポイント
SHA-256 + Salt + 相互認証 の3点強化。設定変更のみで移行可能なサーバー実装が多い。

05

脅威と攻撃手法

SASL認証に対する攻撃を 4カテゴリ に分類します。カテゴリボタンで絞り込み可能です。

盗聴（スニッフィング）

INTERCEPT
たとえ：封筒なしのはがきで秘密を送るようなもの。通信路が見えていれば内容が丸見え。

PLAINやLOGINをTLSなしで使うと、ネットワーク上のBase64文字列をデコードするだけでパスワードを取得できます。Wireshark等の一般的ツールで誰でも傍受可能です。

対策：PLAIN使用時は必ず STARTTLS または TLS接続（SMTPS等）上で使用する。

ダウングレード攻撃

MANIPULATION
たとえ：「本日の特別メニューはコースのみ」の看板を「アラカルト可」に書き換えて、客に安いメニューを選ばせる偽店員。

中間者が SASL ネゴシエーション時のメカニズム一覧を改ざんし、クライアントに意図的に弱いメカニズム（PLAINなど）を選択させます。

対策：STARTTLS完了後にAUTHを実行。ネゴシエーション自体をTLSで保護する。

リプレイ攻撃

INTERCEPT
たとえ：録音した合言葉を再生して入場しようとする。nonce（毎回変わる合言葉）があればこれを防げる。

過去の認証トランザクションを傍受し、そのまま再送して正規ユーザーとして認証させます。nonceがない方式では有効な攻撃になります。

対策：チャレンジ応答の nonce（毎回異なる乱数）を使う SCRAM 等を採用。

辞書攻撃 / 総当たり

BRUTE FORCE
たとえ：暗証番号が4桁だとわかっていれば0000〜9999を試すだけ。Saltと反復ハッシュで「試す時間」を増やして現実的でなくする。

CRAM-MD5 など旧来の方式では、傍受したチャレンジ・レスポンスのペアからオフラインで辞書攻撃が有効。MD5 の速さが仇になります。

対策：SCRAM-SHA-256 の Salt+PBKDF2 でオフライン攻撃コストを大幅に増加させる。

MD5衝突悪用

BRUTE FORCE
たとえ：同じ外見（ハッシュ値）を持つ偽物を作れる技術。「見た目が同じ」なら本物として通過できてしまう。

CRAM-MD5・DIGEST-MD5 は MD5 の衝突脆弱性（異なる入力が同一ハッシュになる）を利用した偽造が理論上成立。実用攻撃への道は徐々に広がっています。

対策：MD5系メカニズムを廃止し SCRAM-SHA-256 に完全移行する。

フィッシング（偽サーバー）

SOCIAL
たとえ：本物そっくりの偽店舗を作って客の個人情報を盗む。相互認証は「店が本物の営業許可証を持っているか確認する」行為。

偽の SMTP サーバーを立てて正規の SASL 認証を行わせ、認証情報を詐取します。CRAM-MD5 は相互認証がないため、クライアントから偽サーバーを検知できません。

対策：SCRAM-SHA-256 の相互認証を使い、クライアント側でサーバーの正当性を検証する。

中間者攻撃（MITM）

MANIPULATION
たとえ：郵便局員になりすまして手紙を横取りし、内容を読み・書き換えてから届ける。TLSは封蝋と封筒で「開封されていないか」確認できる仕組み。

攻撃者がクライアントとサーバーの間に入り、通信の傍受・改ざん・セッション乗っ取りを行います。TLSなしの SASL は完全にこの攻撃に無防備です。

対策：TLSで通信路を保護し、証明書検証を必須とする。HSTS等を組み合わせる。
06

試験で問われやすい・間違いやすいポイント

誤解されがちな論点

誤
「SASLで認証した」は誤り。SASLはフレームワークであり認証ロジックを持たない。正確には「SASL上の SCRAM-SHA-256 で認証した」。
誤
「PLAINはパスワードを暗号化している」は誤り。Base64は エンコード（可逆変換） であり暗号化ではない。base64_decode() で即座に元に戻せる。
誤
「OAuth 2.0はSASLの認証方式」は誤り。OAuth 2.0は 認可 フレームワーク。SASLで使われるのは OAUTHBEARER メカニズム（OAuth 2.0 のトークンを使う仕様）。
誤
「SCRAM-SHA-256ならTLS不要」は誤り。SCRAMはパスワード平文を送らないが、通信路の暗号化はTLSの別の仕事。中間者攻撃には無防備。
注
CRAM-MD5 と DIGEST-MD5 の違い：CRAM-MD5 は相互認証なし（一方向のみ）。DIGEST-MD5 は相互認証に部分対応。両者ともMD5の脆弱性で廃止勧告。混同しやすいので要注意。
注
GSSAPI と Kerberos の関係：GSSAPIはSASLのメカニズム名。実体は Kerberos V5。「GSSAPIで認証＝Kerberosチケットを使ってSSOを実現」と覚える。AD環境での標準方式。

試験対策 5つの鉄則

① SASLはフレームワーク — 認証はメカニズムが行う。「SASL自体が認証する」は誤り。
② Base64はエンコード、暗号化ではない — PLAIN使用時はTLS必須。
③ リプレイ防止には nonce（毎回異なる乱数） — チャレンジ応答の本質。
④ 相互認証は SCRAM と GSSAPI のみ — PLAIN や CRAM-MD5 にはない。
⑤ OAuth 2.0 は認可、認証ではない — OAUTHBEARER はそのトークンをSASLで使う仕様。

重要用語まとめ

SASLSimple Authentication and Security Layer。アプリ層に認証を追加するフレームワーク（RFC 4422）。認証処理自体はメカニズムが担う。
ネゴシエーションSASLの最初のフェーズ。サーバーが対応メカニズム一覧を通知し、クライアントが一つを選択する。
nonceNumber used ONCE。毎回異なるランダム値。チャレンジ応答に使うことでリプレイ攻撃を防ぐ。
SCRAM-SHA-256Salted Challenge Response Authentication Mechanism。相互認証・平文不保存・SHA-256 の3点を持つ現在の推奨方式（RFC 7677）。
GSSAPIKerberos などを SASL から呼び出すためのメカニズム名。Active Directory 環境の SSO 認証で使われる。
OAUTHBEAREROAuth 2.0 の Bearer トークンを SASL 認証に使用するメカニズム（RFC 7628）。クラウドメールで拡大中。
PLAINユーザー名+パスワードを Base64 エンコードして送る方式。TLS 必須。Base64 は可逆変換のため単体では危険。
DIGEST-MD5MD5 ハッシュを用いたチャレンジ応答方式。RFC 6331 で廃止勧告。
CRAM-MD5HMAC-MD5 を使った1ラウンドのチャレンジ応答。相互認証なし・辞書攻撃に脆弱。SCRAM 系への移行を推奨。
相互認証クライアント ↔ サーバー双方向の認証。SCRAM・GSSAPI が対応。偽サーバー検知に有効。
ダウングレード攻撃ネゴシエーション段階でメカニズム一覧を改ざんし、クライアントに弱い方式を選ばせる中間者攻撃。
STARTTLS平文接続を途中で TLS に切り替えるコマンド。SASL AUTH の前に実行することでネゴシエーション自体を保護できる。

試験対策 最終まとめ

① SASL は認証しない — メカニズムを「選ぶ」だけのフレームワーク
② Base64 ≠ 暗号化 — PLAIN には必ず TLS が必要
③ リプレイ防止 ＝ nonce — チャレンジ応答の本質
④ GSSAPI の実体は Kerberos — AD 環境の SSO の仕組み
⑤ OAuth 2.0 は認可 — OAUTHBEARER はそのトークンを SASL で使う仕様
