核心ポイント — なぜKerberosはSSOになるのか

パスワード入力は AS_REQ の1回だけ。発行されたTGTを使ってTGSから各サービスのSTを取得でき、STを使って複数サービスに認証できます。TGTの有効期限（通常8〜10時間）内は再認証不要というのがSSOの仕組みです。また、パスワードをネットワーク上に流さず、タイムスタンプ付き認証子を使うため盗聴・リプレイ攻撃に強い設計です。

SAML 2.0の3アクター

ブラウザ
USER AGENT
IdPとSPの間をリダイレクトで橋渡しする。SAMLメッセージをBase64エンコードして転送する「郵便配達員」。
IdP
Identity Provider
ユーザを認証しSAMLアサーション（XML署名済み）を発行する。ADFS・Okta・Googleが例。
SP
Service Provider
SAMLアサーションをIdPの公開鍵で署名検証し、正当なら認証済みとしてサービスを提供する。

SAMLアサーションの3種類

認証
認証アサーション（Authentication Statement）：「誰が」「いつ」「どの方法で」認証されたかを記述。最も基本的なアサーション。
属性
属性アサーション（Attribute Statement）：「名前」「メール」「所属部署」「ロール」などのユーザ属性を含む。SPがアクセス制御に利用する。
認可
認可アサーション（Authorization Decision Statement）：「特定のリソースへのアクセスが認可されているか」を記述。（実際には認証・属性アサーションが多用される）

XML署名ラッピング攻撃（XSW: XML Signature Wrapping）：XMLの署名範囲外に不正な要素を挿入して署名検証をバイパスする攻撃です。正規署名は通過しますが、実際に処理される内容は改ざんされています。対策はXMLパーサーのID参照ベースの厳格な検証とSAMLライブラリの最新化です。

認可コードフロー（最も安全な標準フロー）

認可コードフロー — 全ステップ

① 利用者 → 認可サーバ：「クライアントAにカレンダーの読取りを許可してもいいですか？」（認可リクエスト）
② 利用者 → 認可サーバ：「許可します」（同意画面でOK）
③ 認可サーバ → クライアント：「認可コード」（短命・1回使い切り）を発行
④ クライアント → 認可サーバ：「認可コード」+「クライアントシークレット」を送りアクセストークンに交換（バックチャンネル通信）
⑤ クライアント → リソースサーバ：アクセストークンを提示してAPIを呼び出す
なぜ認可コードをワンクッション挟むのか？
アクセストークンをブラウザリダイレクト（フロントチャンネル）で直接渡すと、ブラウザ履歴やリファラに漏洩するリスクがあります。認可コードを経由し、バックエンドのサーバ間通信（バックチャンネル）でトークン交換することで、アクセストークンをブラウザから隠します。

PKCE（Proof Key for Code Exchange）：SPAやモバイルアプリなど、クライアントシークレットを安全に保管できない環境での認可コードフロー補強策。code_verifierとcode_challengeを使い、認可コードの傍受・横取り攻撃を防ぎます。

攻撃の仕組み
KDCの KRBTGTアカウントのパスワードハッシュを奪取すると、攻撃者は任意のユーザ名・グループ・有効期限でTGTを偽造できます。ドメイン管理者権限のTGTを作成することでAD全体を掌握可能です。

チケット/トークン窃取系
Pass-the-Ticket / Pass-the-Hash攻撃
Kerberos / 有効期限内のTGT・STを横取り → ターゲット: クライアントメモリ
攻撃の仕組み
攻撃者がメモリ（lsass.exe）からTGTやSTを窃取し、その有効期限内に正規ユーザとしてサービスを利用します。パスワードを知らなくても攻撃可能です。
対策

プロトコル悪用系
XML署名ラッピング攻撃（XSW）

攻撃の仕組み

対策
SAMLライブラリを常に最新化。XMLパーサーをIDリファレンス（id属性）ベースで厳格に処理。署名範囲外要素の完全無視。opensamlなど実績あるライブラリ使用。
プロトコル悪用系
OAuth CSRF攻撃
OAuth 2.0 / stateパラメータ欠如 → ターゲット: 認可コードフロー
攻撃の仕組み
攻撃者が自分のアカウントで取得した認可コードを被害者に踏ませ、被害者のセッションに攻撃者のアカウントを紐付ける攻撃。被害者が「攻撃者アカウント」でログインした状態になり、入力したデータが攻撃者に見えます。
対策
stateパラメータ（CSRF対策トークン）を認可リクエストに必ず含め、コールバック時に検証する。PKCE（Proof Key for Code Exchange）の使用。
フィッシング/なりすまし系
セッションCookieハイジャック
エージェント/プロキシ方式 / XSSによるCookie窃取 → ターゲット: ブラウザCookie
攻撃の仕組み
XSSを利用してSSOセッションCookieを窃取し、攻撃者が正規ユーザになりすましてSSOで保護されている全サービスにアクセスします。Cookieが1つ取られると全サービスが侵害されるのがSSOの集中リスクです。
対策
CookieにHttpOnly・Secure・SameSite属性を設定。XSSを防ぐCSP（Content Security Policy）。セッション異常検知（IP変化・UA変化）。セッション有効期限の短縮。MFA（多要素認証）の導入。
プロトコル悪用系
JWTアルゴリズム改ざん攻撃（Algorithm None Attack）

攻撃の仕組み
JWTヘッダの "alg":"RS256" を "alg":"none" に改ざんし、署名なしのJWTを作成します。脆弱なJWTライブラリはこれを有効として処理し、任意のsub（ユーザID）を持つトークンが通過します。
対策
RPは受け入れるアルゴリズムをホワイトリストで明示指定。noneを明示的に拒否。JWTライブラリは常に最新版を使用。

過去問スタイル 練習問題

Q1Kerberos認証においてTGT（Ticket Granting Ticket）の説明として最も適切なものはどれか。
正解：ウ
TGTは「チケット発行のためのチケット」です。AS_REQ/AS_REPでASから取得し、TGSへのアクセスに使います。TGTを使って各サービスのST（Service Ticket）を取得できるため、1回の認証（パスワード入力）で複数サービスにアクセスできるSSOが実現します。ア：STの説明。ネットワーク上にパスワードを流さないのがKerberosの特徴です。
Q2リバースプロキシ方式のSSOで「ヘッダ偽装攻撃」が成立する条件として最も適切なものはどれか。
正解：イ
リバースプロキシ方式では、APサーバは「X-Remote-User: alice」などのHTTPヘッダでユーザを識別します。APサーバがリバースプロキシ以外の任意のホストからこのヘッダを信頼すると、攻撃者が直接APサーバへ偽ヘッダを送ってなりすます「ヘッダ偽装攻撃」が成立します。対策はAPサーバへのアクセスをリバースプロキシのIPのみに制限することです。
Q3OAuth 2.0とOIDCの関係として最も適切なものはどれか。
正解：ウ
OIDCはOAuth 2.0の上に構築された認証レイヤーです。OAuth 2.0に「scope=openid」を追加し、アクセストークンに加えて「IDトークン（JWT）」を発行することで、「誰が認証されたか」という情報を取得できます。OAuth 2.0単体では認可（何ができるか）のみで認証情報は含まれません。
Q4SAML 2.0のXML署名ラッピング攻撃（XSW）に対する最も適切な対策はどれか。
正解：ウ
XSW攻撃の本質は「署名が正規部分を対象としているが、実際に処理される要素が別の不正なもの」という点にあります。対策はXMLパーサーが署名されたIDを持つ要素のみを処理し、署名範囲外の要素を完全に無視することです。暗号化（ア）は機密性を守りますが、XMLを処理した後は通常の状態になるため XSW を防げません。
Q5OIDCのIDトークン（JWT）に含まれるnonceクレームの主な目的として最も適切なものはどれか。
正解：ウ
nonceはRP（クライアント）が認証リクエスト時にランダムに生成し、IDトークン内に同じ値が含まれていることを検証することで「このIDトークンが自分のリクエストへの応答」を確認できます。これにより傍受したIDトークンを再送するリプレイ攻撃を防ぎます。ア：issクレームの説明。イ：expクレームの説明。エ：subクレームの説明。
Q6SSO基盤に対するGolden Ticket攻撃の説明として最も適切なものはどれか。
正解：イ
Golden Ticket攻撃はKerberos特有の高度な攻撃です。KDCのKRBTGTアカウントのハッシュを入手すると、攻撃者は任意のユーザ名・グループ・有効期限でTGTを偽造できます。ドメイン管理者権限のTGTを偽造することでAD全体を掌握可能です。対策にはKRBTGTパスワードを短期間で2回変更することが必要です（古いチケットを無効化するため）。
Q7SAMLとOIDCの比較として最も適切なものはどれか。
正解：ウ
SAMLはXMLベースでSOAP/ブラウザリダイレクト向き、企業間フェデレーションに実績があります。OIDCはOAuth 2.0の上にJSONベース（JWT）の認証レイヤーを追加したもので、REST API・モバイルSPA向きです。ア：逆です。SAMLがXML、OIDCがJSONベースです。イ：OIDCはOAuth 2.0を拡張したプロトコルです。エ：OIDCはOAuth 2.0の認可機能も備えています。

重要用語まとめ

SSOSingle Sign-On。1回の認証で複数サービスに認証なしでアクセスできる仕組み。
IdPIdentity Provider。ユーザを認証しアサーション/トークンを発行する。SAMLではIdP、OIDCではOP（OpenID Provider）と呼ぶ。
SPService Provider。SAMLでIdPのアサーションを信頼してサービスを提供する側。
RPRelying Party。OIDCでIdトークンを受け取り認証するアプリ。SPに相当。
KDCKey Distribution Center。KerberosのAS+TGSを含む認証の中心サーバ。ADのドメインコントローラが担当。
TGTTicket Granting Ticket。ASから発行される「フリーパス」。TGSへのアクセスに使い、STを取得する。
STService Ticket。TGSから取得する「入場券」。個々のサービスへのアクセスに使う。
SAMLアサーションIdPがデジタル署名したXML文書。認証・属性・認可の3種がある。SPに送ってSSO認可に使う。
JWTJSON Web Token。Header.Payload.Signatureの3部構成。OIDCのIDトークンはJWT形式。Base64URLエンコードされており暗号化ではない。
IDトークンOIDCで発行されるJWT。iss/sub/aud/exp/nonceなどのクレームを含み「誰が認証されたか」を証明する。
アクセストークンOAuth 2.0で発行されるトークン。「何ができるか（権限）」を表す。認証情報は含まない。
認可コードOAuth 2.0の認可コードフローで発行される短命・1回使い切りのコード。バックエンドでアクセストークンに交換する。
PKCEProof Key for Code Exchange。SPAやモバイルアプリでの認可コードフロー補強策。code_verifier/code_challengeで認可コード横取りを防ぐ。
フェデレーション異なる組織間の認証情報を相互に信頼する仕組み。SAMLが典型例。
Golden Ticket攻撃KerberosのKRBTGTハッシュを奪取して任意ユーザのTGTを偽造する攻撃。AD全体の掌握が可能。
XSW攻撃XML Signature Wrapping。SAMLアサーションの署名範囲外に不正要素を挿入して署名検証をバイパスする攻撃。
nonceJWTに含まれるランダム値。RPが生成し、IDトークンに同値が入ることを確認することでリプレイ攻撃を防ぐ。
stateOAuth 2.0の認可リクエストに含めるCSRFトークン。コールバック時に検証することでOAuth CSRFを防ぐ。
JWKSJSON Web Key Set。OPが公開する公開鍵セット。RPはこれを使ってJWT署名を検証する。

試験対策 6つの鉄則

1. OAuthは「認可」のみ、OIDCは「認証＋認可」 — アクセストークンに認証情報はない
2. Kerberosは「TGT→ST発行がSSOの核心」 — パスワードはネットワーク上を流れない、時刻同期±5分が前提
3. SAMLは「XMLアサーション」、OIDCは「JWTトークン」 — 企業間 vs クラウド/モバイル
4. リバースプロキシは「AP無改修・単一障害点・ヘッダ偽装リスク」
5. Golden Ticket=KRBTGTハッシュ奪取、XSW=XML署名の外側に不正挿入
6. nonce=リプレイ防止、state=OAuthのCSRF防止 — どちらもランダム値を使う点は同じ
