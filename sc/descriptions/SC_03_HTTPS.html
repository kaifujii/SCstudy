Cookie の仕組みと安全な管理

Set-Cookie Header — 推奨設定例
Set-Cookie: session_id=abc123xyz789; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
Cookie属性説明セキュリティ上の意義
HttpOnlyJavaScriptのdocument.cookieからのアクセスを禁止する。XSS攻撃によるCookie窃取を防ぐ
SecureHTTPS接続時にのみCookieを送信する。HTTP接続では送信しない。通信経路上の盗聴（MITM）を防ぐ
SameSite=Strict同一サイトからのリクエストのみCookieを送信。外部リンク遷移でも送信しない。CSRF攻撃を最も強く防ぐ
SameSite=Lax同一サイト＋トップレベルナビゲーション（GETリンク遷移）でCookieを送信。フォームPOSTでは送信しない。CSRFを防ぎつつ使い勝手を保つ（推奨）
SameSite=NoneクロスサイトリクエストでもCookieを送信。Secure属性必須。サードパーティCookie・埋め込みコンテンツ用。プライバシーリスクあり。
DomainCookieを送信するドメインを指定。指定するとサブドメインにも送信される。省略時は発行元ホストのみ対象（より安全）
Max-Age / ExpiresCookieの有効期限。省略するとセッションCookie（ブラウザを閉じると削除）になる。長すぎる有効期限は盗まれたCookieの悪用期間を延ばす
1
HttpOnly + Secure + SameSite=Lax の3点セットを必ず設定する。
2
セッションIDは128ビット以上のCSPRNGで生成。連番・推測可能な値は厳禁。
3
ログイン成功後はセッションIDを再発行する（セッション固定攻撃対策）。
4
タイムアウト2種類：アイドルタイムアウト（最終操作から）＋絶対タイムアウト（最長有効期間）を設定。
!
URLへのセッションID埋め込みを避ける。Referer・履歴・プロキシログに漏洩する。

Cookieセキュリティの3原則

HttpOnly（XSS盗取防止）＋ Secure（HTTPS強制）＋ SameSite=Lax以上（CSRF緩和）の3属性を必ずセッションCookieに設定する。この3つが最低限の基準です。

攻撃手法の全体整理

XSSによるCookie窃取
ブラウザのCookie → JS経由で盗取
掲示板等にスクリプトを注入してdocument.cookieを読み、外部サーバへ送信。セッションIDが漏洩する。
対策：HttpOnly属性 / CSP / 出力時のHTMLエスケープ
通信経路での盗聴
HTTP通信 → MITM攻撃
HTTP（非暗号化）通信を傍受しCookieを盗む。公衆Wi-Fi等で特に危険。
対策：HTTPS強制 / Secure属性 / HSTS
CSRF
Cookie自動送信 → 被害者を操作
被害者のブラウザを使って不正リクエストを送信。CookieがGET/POST時に自動付与されるためサーバが正規と誤認。
対策：CSRFトークン / SameSite=Lax / Referer検証
セッション固定攻撃
ログイン処理 → 合鍵を仕込む
攻撃者がセットしたIDを被害者に使わせる。ログイン後も同一IDで攻撃者がアクセス可能。
対策：ログイン後にセッションID再発行（必須）
セッションID推測
ID生成ロジック → 総当たり
連番・短い・予測可能なIDを試行する。脆弱なID生成では全IDの試行が現実的になる。
対策：CSPRNG + 128ビット以上 / フレームワーク利用
URLからの漏洩
URLリライティング → ログ露出
URLリライティング方式でIDがReferer・履歴・プロキシログに記録される。
対策：URLへのID埋め込み禁止 / Cookie方式を使う
クリックジャッキング
透明iframe → 偽クリック誘導
透明iframeで対象サイトを重ね、被害者が気づかずにクリック操作（送金・設定変更等）を実行させる。
対策：X-Frame-Options: DENY / CSP frame-ancestors

セキュリティヘッダ — 何の攻撃に対して何が守るか

Strict-Transport-Security
ブラウザにHTTPS接続を強制させる。max-ageで適用期間を秒単位で指定。
防御：HTTPダウングレード・通信傍受
Content-Security-Policy
スクリプト・スタイル・画像等の読み込み元オリジンを制限する。default-src 'self'が基本。
防御：XSS・コンテンツインジェクション
X-Frame-Options
ページのiframe埋め込みを制御。DENYまたはSAMEORIGIN。
防御：クリックジャッキング
X-Content-Type-Options
nosniffを指定。ブラウザがContent-Typeを無視してコンテンツ種別を推測することを防ぐ。
防御：MIMEスニッフィング攻撃
Referrer-Policy
strict-origin-when-cross-originを推奨。クロスサイトへのURL漏洩を防ぐ。
防御：URLパラメータのReferer漏洩

主要な攻撃と対策の対応表

XSS — クロスサイトスクリプティング アプリケーション層を攻撃
攻撃の仕組み
攻撃者が悪意あるスクリプトをWebページに注入し被害者ブラウザで実行させる。Cookieの窃取・フィッシング・偽フォーム表示が可能。
対策
出力時のHTMLエスケープ / Content-Security-Policy / HttpOnly Cookie / DOMPurify等のサニタイザー
SQLインジェクション データ層を攻撃
攻撃の仕組み
入力値にSQL文を混入させてDBを不正操作する。認証バイパス・情報漏洩・データ改ざん・削除が可能。
対策
プリペアドステートメント / パラメータ化クエリ / ORM使用 / 入力値バリデーション / 最小権限DBアカウント
ディレクトリトラバーサル Webサーバ層を攻撃
攻撃の仕組み
../を使い公開ディレクトリ外のファイルにアクセス。設定ファイル・パスワードファイルの漏洩が可能。
対策
ファイルパスの正規化 / ホワイトリスト検証 / Webルート外へのアクセス禁止 / 特殊文字の除去

バナー情報の非公開：Serverヘッダ（Server: Apache/2.4.51等）のバージョン情報を削除。攻撃者への情報提供を減らす。
B
不要なHTTPメソッドの無効化：TRACEメソッド（XST攻撃の温床）やDELETE・PUT等の不要なメソッドを無効化する。
C
ディレクトリリスティングの無効化：インデックスファイルが存在しないディレクトリの一覧表示を禁止する。
D
エラーメッセージの適切な制御：スタックトレース・DB情報・ファイルパスを含む詳細エラーを本番環境で表示しない。詳細はログに記録し、ユーザには汎用エラーページを表示。
E
レート制限：ログインページ・APIへの短時間の大量リクエストをレート制限（429 Too Many Requests）。CAPTCHA・アカウントロックアウトも組み合わせる。
F
WAF（Webアプリケーションファイアウォール）：SQLi・XSS・パストラバーサル等の攻撃パターンをシグネチャで検知・遮断する。
!
ソフトウェアの定期的な更新：CVEが公開されたWebサーバ・ミドルウェアはすぐに更新。未パッチの既知脆弱性は攻撃の主要な入口になる。
13

過去問スタイル 練習問題

Q1セッション固定攻撃（Session Fixation Attack）の対策として、最も適切なものはどれか。
正解：ウ
セッション固定攻撃は攻撃者がセットしたIDを被害者に使わせ、ログイン後に同一IDで不正アクセスする攻撃です。ログイン成功後にセッションIDを必ず再発行（新規ID発行）することで、攻撃者がセットした古いIDは無効になり攻撃が無効化されます。
ア：HTTPS化は重要ですが、根本対策ではありません。
イ：URLへのID埋め込みは漏洩リスクがあり非推奨。
エ：有効期限を長くするのはリスクを高めます。
Q2CSRFトークンをHiddenフィールドに埋め込む対策について、正しいものはどれか。
正解：ウ
CSRFトークン（同期トークンパターン）は、フォーム生成時にサーバがランダム値を生成してHiddenフィールドとセッションに紐付ける仕組みです。攻撃者は正規ページを読めないためトークンを入手できず、不一致でリクエストが拒否されます。
ア：Cookieに入れると自動送信されるためCSRF防止の効果がなくなります。
イ：Hiddenフィールドはブラウザには表示されませんが、HTMLソースを見れば値が分かります。
エ：URLリライティングでもCSRF攻撃は成立します。
Q3Cookie の SameSite=Lax 属性の動作として、正しいものはどれか。
正解：イ
SameSite=Laxは「緩やかな同一サイト制限」です。外部サイトのリンクをクリックした通常のGET遷移ではCookieを送信しますが、クロスサイトのフォームPOST・XHR・iframeリクエストではCookieを送信しません。CSRF攻撃（多くはPOSTリクエスト）を防ぎながら、通常のユーザ体験（外部リンクからのアクセス）を維持します。
ア：SameSite=Strictは外部リンクからの遷移でもCookieを送らないため、より厳格です。
ウ：SameSite=Noneの説明（Secure属性必須）。
エ：JavaScriptアクセスの禁止はHttpOnly属性の役割です。
Q4同一オリジンポリシー（SOP）とCORSの関係として、正しいものはどれか。
正解：イ
SOPはブラウザに実装されたデフォルトのセキュリティ制約（クロスオリジンのXHR等を禁止）です。CORSはサーバがAccess-Control-Allow-Originなどのレスポンスヘッダを返すことで、SOPを管理された形で緩和する仕組みです。
ア：SOPとCORSの説明が逆です。
ウ：SOPはXHR/Fetchを制限しますが、HTMLフォームからのPOSTはSOPの対象外です。これがCSRFが成立する理由の一つです。
エ：*とCredentials=trueの組み合わせはブラウザが拒否します。
Q5X-Frame-Options: DENY を設定する主な目的として、正しいものはどれか。
正解：ウ
クリックジャッキング攻撃は透明なiframeで対象サイトを重ね、被害者に気づかれずにクリックさせる攻撃です。X-Frame-Options: DENYはどのサイトもこのページをiframeで表示できないようにし、クリックジャッキングを防ぎます。現代的にはContent-Security-Policy: frame-ancestors 'none'も同様の効果があります。
ア：XSS対策はCSP・出力エスケープ・HttpOnly Cookieが担います。
イ：HTTPS強制・リダイレクトはHSTS（Strict-Transport-Security）が担います。
エ：SQLi対策はプリペアドステートメント等が担います。
Q6セッションIDの管理に関して、最も不適切なものはどれか。
正解：イ（最も不適切）
URLパラメータにセッションIDを含める方式（URLリライティング）は、アドレスバー表示・ブラウザ履歴への記録・Refererヘッダによる漏洩・プロキシやサーバのアクセスログへの記録など多くの経路でIDが漏洩します。Cookieが無効な環境への対応であっても推奨されない手法です。
ア・ウ・エはいずれも正しいセッション管理の実践です。

重要用語まとめ

HTTPHyperText Transfer Protocol。Webの通信プロトコル。アプリケーション層（OSI第7層）。ステートレス。
HTTPSHTTPをTLSで暗号化したプロトコル。ポート443。サーバ証明書による認証も実施。
CRLFCarriage Return + Line Feed（\r\n）。HTTPメッセージの行末区切り。空行でヘッダとボディを区切る。
冪等性（Idempotent）同じ操作を複数回実行しても結果が変わらない性質。GET・PUT・DELETE=冪等。POST=非冪等。
セッションHTTPのステートレス性を補うためにサーバ側で維持するユーザの状態情報。セッションIDで識別。
CookieサーバがSet-Cookieヘッダでクライアントに渡す小データ。以降のリクエストでCookieヘッダとして自動送信。
Hiddenフィールド<input type="hidden">によるフォーム内の非表示フィールド。セッション管理・CSRFトークン格納に使用。HTMLソースには露出。
URLリライティングURLパラメータにセッションIDを付与する方式。Referer・履歴・ログへの漏洩リスクがあり現代では非推奨。
HttpOnlyJavaScriptからのCookieアクセスを禁止するCookie属性。XSSによるCookie窃取を防ぐ。
Secure（Cookie属性）HTTPS接続時のみCookieを送信するCookie属性。通信経路での盗聴を防ぐ。
SameSiteクロスサイトリクエストでのCookie送信を制御するCookie属性。Strict/Lax/None。CSRF対策。
CSRFCross-Site Request Forgery。被害者のブラウザを利用して不正リクエストを送信させる攻撃。CSRFトークン・SameSiteで対策。
XSSCross-Site Scripting。悪意あるスクリプトをWebページに注入し被害者ブラウザで実行させる攻撃。HttpOnly・CSP・エスケープで対策。
セッション固定攻撃攻撃者がセットしたセッションIDを被害者に使用させる攻撃。ログイン後のセッションID再発行で対策。
CSRFトークンCSRF対策のためフォームに埋め込むランダム値。サーバ側で生成・検証し、攻撃者は入手不可。
SOP（同一オリジンポリシー）ブラウザのデフォルトセキュリティ制約。スキーム・ホスト・ポートがすべて一致しないクロスオリジンアクセスを制限。
CORSCross-Origin Resource Sharing。サーバのレスポンスヘッダでSOPを管理された形で緩和する仕組み。
HSTSHTTP Strict Transport Security。Strict-Transport-SecurityヘッダでブラウザにHTTPS強制を指示。
CSPContent Security Policy。Content-Security-PolicyヘッダでXSSを軽減するリソース制限ポリシー。
X-Frame-Optionsページのiframe埋め込みを制御するレスポンスヘッダ。クリックジャッキング対策。DENY/SAMEORIGIN。
WAFWeb Application Firewall。SQLi・XSS・パストラバーサル等の攻撃パターンをシグネチャで検知・遮断。
クリックジャッキング透明なiframeで対象サイトを重ね、被害者に気づかれずにクリック操作を実行させる攻撃。X-Frame-Optionsで対策。

試験対策 8つの鉄則

1. 401 vs 403 — 401は「未認証」、403は「認可失敗（権限なし）」
2. Cookie3属性 — HttpOnly（XSS）＋Secure（盗聴）＋SameSite=Lax以上（CSRF）
3. セッション固定の対策 — ログイン後にセッションIDを必ず再発行する
4. CSRFトークン = Hiddenフィールド活用 — サーバ生成ランダム値をフォームに埋め込みサーバ側で検証
5. URLへのセッションID埋め込みは禁止 — Referer・履歴・ログへの漏洩リスク
6. SOPはフォームPOSTを制限しない — これがCSRFが成立する根拠
7. XSSの根本対策は出力エスケープ — HttpOnlyはCookie窃取防止にすぎない
8. セキュリティヘッダの役割対応 — HSTS=HTTPS強制 / CSP=XSS軽減 / X-Frame-Options=クリックジャッキング対策
