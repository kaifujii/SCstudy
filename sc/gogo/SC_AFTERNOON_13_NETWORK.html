ネットワーク防御装置の全体像

位置づけ — 何層で何を守るか

ネットワーク防御装置はOSI参照モデルのL3〜L7を異なる粒度で監視する。下位層ほど高速・大量処理向き、上位層ほどコンテンツ理解できるが計算コスト大。

OSI層と装置の対応

L7 アプリケーション
WAF / Reverse Proxy / API Gateway
L5-L6 セッション/表現
SSL Inspection / Forward Proxy
L4 トランスポート
Stateful FW / Load Balancer / IDS-IPS
L3 ネットワーク
Router ACL / Packet Filter / DDoS Mitigation
L2 データリンク
Switch (VLAN, 802.1X)
たとえ話：空港の保安検査
L3-L4のFW＝パスポート/搭乗券チェック（送信元・宛先のみ確認）。L7のWAF＝X線・手荷物検査（中身まで開けて検査）。Proxy＝関税職員（出入国の代行と記録）。IDS=監視カメラ（記録・通知のみ）、IPS=セキュリティスタッフ（その場で身柄拘束）。
H30春 PM1問3 / R元秋 PM2問2 / H31春 PM1問3 旧過去問より — LAN分離・OT・IoTという「古典の三本柱」
古典の旧形式時代（〜H30）にはLAN分離・OT/工場・IoT機器がNW論点の中心テーマとして繰り返し出題された。LAN分離＝インターネット用と業務用を物理分離（2NIC/2PC）またはVDI（仮想ブラウザ＋画面転送）で分ける（H30春）。OT/工場＝Purdueモデルに基づき制御系を階層化しゾーン間にFW/データダイオード配置（R元秋）。IoT機器＝TPM/SE活用、デバッグポート（UART/JTAG）の物理封印（H31春）。新形式では大問にならなくなったが、境界防御の発想として今も応用が利く。第14章Q45/Q46/Q50参照。
H28秋 PM1問1 / H28春 PM1問3 旧過去問より — IPsec/IKEモードと Evil Twin（黎明期の連続経典）
IPsec/IKEはNWの古典中の古典。H28秋ではIKEv1のメインモード vs アグレッシブモードが問われた——双方IPアドレスが固定ならメインモード（より安全）、片方が動的IPならアグレッシブモード必須（IDが平文流れるため強固な事前共有鍵で補う）。トンネルモード／トランスポートモードの選択も連動（ルータ間VPNはトンネルモード）。SSHホスト鍵の共有は中間者攻撃を許す（同一鍵を持つ他機器が介在可能）ため、機器毎ユニーク鍵が必須。H28春の公衆無線LANのEvil Twin攻撃＝偽AP対策にはVPN必須化＋EAP-TLS（証明書認証）。SSIDとPSKだけでは騙される。第14章Q58/Q59参照。

FW/WAF/IDS/IPSの違い

4装置の比較

装置主な層判断基準対応得意
FW（パケットフィルタ）L3-L4送信元/宛先IP・ポート・プロトコル許可/拒否ネットワークセグメンテーション
Stateful FWL3-L4+ TCPセッション状態許可/拒否戻り通信の自動許可
NGFWL3-L7+ アプリ識別・URLフィルタ・IPS機能許可/拒否/検知統合防御（SASEに連動）
WAFL7HTTP/HTTPSの中身（パラメータ・ヘッダ・Body）遮断/検知SQLi/XSS等のWeb攻撃
IDSL3-L7シグネチャ/異常検知検知のみ監視・調査用途
IPSL3-L7同上遮断能動的防御

WAFの2方式

ブラックリスト方式（ネガティブ）

「既知の攻撃パターンを拒否」する。ModSecurity/OWASP CRS等。誤検知が少ないが新種攻撃に弱い。導入容易。

vs

ホワイトリスト方式（ポジティブ）

「正規パターンのみ許可」。学習期間でアプリの正常通信を覚え、それ以外を拒否。誤検知が多いが0day対応可。チューニング必要。

IDSの2方式

方式仕組み例
シグネチャ型 (Misuse Detection)既知攻撃のパターンを照合Snort, Suricata
アノマリ型 (Anomaly Detection)平常時から逸脱した振る舞いを検知Zeek, ML型NDR

NIDS と HIDS の使い分け

種別設置場所得意
NIDS（ネットワーク型）SPANポート/TAPで通信ミラー横方向の通信を一括監視。暗号化通信は中身が見えない
HIDS（ホスト型）各サーバ・端末OSログ・ファイル変更検知。暗号化解除後の通信も見える

プロキシ — Forward / Reverse

2種のプロキシの位置

Forward Proxy（社員→外部）

社内端末がインターネットへ出る際に経由。URLフィルタ・ウイルス検査・SSL Inspectionを実施。一括で出口を集約することで監査ログ取得・攻撃通信遮断が可能。

vs

Reverse Proxy（外部→社内サーバ）

公開Webサーバの前段に配置。負荷分散・SSL終端・WAF・キャッシュ・DDoS吸収。直接サーバに到達させず一段挟むことで攻撃面を縮小。

SSL/TLS Inspection — 暗号化通信の中身を見る

社員PC
社内CA信頼
SSL Inspection
Proxy
外部サイト
①PC→Proxy：HTTPS要求
②Proxy→外部：本物の証明書受領
③Proxy→PC：動的生成した社内CA署名証明書（PCには社内CAをルート信頼として配布済）
④Proxy⇔PC、Proxy⇔外部 で別々のTLSセッションが確立
⑤Proxyは復号した平文を検査（マルウェア検出/DLP）
⑥再暗号化して相手側に転送
SSL Inspection の例外：金融取引・医療データなど機微情報サイトは復号せずバイパス（プライバシ保護・規制対応）。証明書ピンニング（第12章）を実装したアプリは復号失敗で接続不可になる。

ログ相関分析の実例

シナリオ：標的型攻撃の侵害再構成

下記は侵入から内部探索・データ持出までの典型的なログ断片を時系列で並べたもの。試験では類似のログを読み、何時何分に何が起きたか・どこを止めるべきかを答えさせる。

① メール経由の侵入（10:23頃）

2024-09-15 10:23:14 JST mail-gw [INFO] msg-id=<abc123@example.jp> from="hr-info@suplly-c0rp.com" to="tanaka@example.jp" subject="9月度給与明細" attachment="明細.xlsm" verdict=DELIVERED scan=PASSED 2024-09-15 10:24:02 JST edr-tanaka-pc [WARN] proc="EXCEL.EXE" child="cmd.exe /c powershell -enc JABzPSdo..." parent_doc="明細.xlsm" 2024-09-15 10:24:05 JST proxy [INFO] src=10.1.4.27 user="tanaka" url="https://paste-bin-cdn.io/raw/x9k2" bytes_out=412 bytes_in=8421 verdict=ALLOW

→ 怪しいドメイン（似たり名）からの.xlsmマクロ → PowerShellエンコード実行 → 外部からスクリプトダウンロード。EDRはWARNを出したが遮断していない。Proxyは未知ドメインを通過させた。

② 内部探索・C2通信（10:30〜11:00）

2024-09-15 10:31:18 JST dns [INFO] qname="a7f2e8.cdn-update.online" qtype=A src=10.1.4.27 2024-09-15 10:31:18 JST dns [INFO] qname="b91c3d.cdn-update.online" qtype=A src=10.1.4.27 2024-09-15 10:31:19 JST dns [INFO] qname="c4e7a1.cdn-update.online" qtype=A src=10.1.4.27 2024-09-15 10:34:55 JST ad-controller [INFO] event=4624 logon-type=3 user="tanaka" src=10.1.4.27 dst=fileserver01.example.local 2024-09-15 10:42:11 JST fileserver01 [INFO] share="\\fs01\share\hr" user="tanaka" access=READ files=132 bytes=2.3GB

→ 同一ドメインのサブドメインへ毎秒問い合わせ＝DGA（Domain Generation Algorithm）の典型。10:34に田中PCから人事ファイルサーバへログオン、8分間で2.3GB読出。通常の田中の業務（経理）と一致しない。

③ データ持出（11:05）

2024-09-15 11:05:43 JST proxy [INFO] src=10.1.4.27 user="tanaka" method=POST url="https://paste-bin-cdn.io/upload" bytes_out=2,312,847,109 verdict=ALLOW 2024-09-15 11:06:02 JST dlp-gateway [ALERT] policy="PII-Detection" pattern="マイナンバー*132" action=BLOCKED user="tanaka" dst=paste-bin-cdn.io 2024-09-15 11:08:11 JST proxy [INFO] src=10.1.4.27 user="tanaka" method=POST url="https://stor-relay.cf/up" bytes_out=2,312,847,109 verdict=ALLOW

→ 2.3GBの巨大POSTを業務時間中の単一ユーザが。DLPが1回はブロックしたが、攻撃者は別ドメインに切替えて再送に成功。

このログから記述させられる典型問

初動侵入の時刻と手口を答えよ：10:24、Excelマクロから起動したPowerShellが外部スクリプトを取得・実行
10:31〜のDNSログから何が読み取れるか：DGA型C2通信の特徴。ランダム文字列サブドメイン群で正規通信に紛れる
事前防御が機能しなかった理由：EDRがWARNのみで遮断せず・Proxyに未知ドメイン遮断機能なし・DLPが宛先別ホワイトリストになっていない
是正策：EDRのアラートをSOAR連携で自動隔離 / プロキシで未分類ドメインを既定拒否 / DLPの宛先制御を「許可リスト方式」に変更

NDR / EDR / XDRの位置づけ

3つの「-DR」

製品種別監視対象強み例
NDR (Network Detection & Response)ネットワーク全通信横展開（Lateral Movement）検知・暗号化通信のメタデータ分析Darktrace, ExtraHop, Vectra
EDR (Endpoint Detection & Response)端末プロセス・ファイルマルウェア挙動・コマンド実行ログの保全と隔離CrowdStrike, SentinelOne, Defender for Endpoint
XDR (eXtended D&R)NDR+EDR+メール+クラウドクロス相関で誤検知を減らす・自動応答Cortex XDR, Microsoft Defender XDR
MDR (Managed D&R)SOCをアウトソース24/365の有人監視・運用コスト削減各社のMSSサービス

EDR と AV (アンチウィルス) の違い

従来型AV

シグネチャ照合中心。既知マルウェアのファイル単位検知・除去。0day/標的型に弱い。

EDR

挙動監視＋ログ保全＋遠隔隔離。「侵入されたあと」の検知・封じ込め・調査を可能にする。

R3秋 PM1問3 旧過去問より — シグネチャ型では検知できないマルウェア対策
旧形式の経典問題。シグネチャ型のマルウェア対策ソフトを運用していたが、新種のファイルレスマルウェア感染を検知できなかったケースが問われた。採点ポイントの3要素：①シグネチャ非依存の検知方式を答える（ふるまい検知／ヒューリスティック／EDR）、②仕組み＝プロセスのAPI呼出し・ファイル操作・NW通信のパターンを監視し異常を検出、③具体的な観測対象に言及。「シグネチャ未登録でも検知可能」が肝。新形式でも複合シナリオ内に登場する不変の論点。第14章Q38参照。

過去問演習 — ログ読解

複合 ログ分析論点（R5秋問2 / R6秋問1 ベース）

設問1：時刻同期の重要性
複数機器のログを相関分析する際、機器ごとの時刻が秒単位でずれていると分析が困難になる。これを防ぐため運用上必須となる仕組みを答えよ（15字以内）。
模範解答（11字）：NTPによる時刻同期
別解：「PTP/NTPサーバの利用」「全機器のNTP同期」も可。
設問2：DGA型C2通信の検出
同一2次ドメイン配下のランダムなサブドメインへの大量問い合わせがDNSログに見られた場合、どのような攻撃の特徴と考えられるか（30字以内）。
模範解答（28字）：DGAアルゴリズムを用いたC2通信の特徴である。
別解：「マルウェアによる動的生成ドメインへのC2接続」
採点ポイント：DGA・C2のキーワード両方に言及。
設問3：ログの改ざん防止
侵害されたサーバ上のログを攻撃者が改ざんする可能性がある。これを防ぐためログ保管に求められる要件を1つ挙げよ（30字以内）。
模範解答（27字）：外部のWORM領域へリアルタイム転送・保管する。
別解：「中央集中ログサーバへ即時転送し権限分離する」
採点ポイント：「攻撃者の権限が及ばない場所に保管」が要件。
設問4：EDRが警告を出したが遮断しなかった事象への対応
EDRが「Excelからcmd.exeが起動した」というWARNログを出したが、ユーザは作業を継続した。再発防止のためEDRの運用に追加すべき仕組みを述べよ（35字以内）。
模範解答（33字）：SOAR連携で当該プロセスの自動隔離・端末分離を行う。
別解：「Office由来のシェル起動を遮断するポリシーへ変更」
採点ポイント：WARNを実際の遮断アクションに繋げる仕組み（SOAR/Auto-isolation）に言及。
