CI/CDパイプライン全体像

位置づけ — どこに属する話か

CI/CDは「ソースコードを書いてから本番に乗るまで」のすべての工程を自動化するしくみ。Web/APIセキュリティ（第3章）が「動いているアプリの中身」、本章は「アプリが本番に到達するまでのレール」。レール側に毒を仕込まれると、いくらアプリが堅牢でも全システムが汚染される（=サプライチェーン攻撃の主要侵入口）。

たとえ話：寿司屋の調理場
コードを書く＝魚を仕入れる、ビルド＝さばく、テスト＝味見、デプロイ＝客に出す。「客に出す前に毒見をする」のが昔ながらの方法（リリース前検査）。シフトレフトは「仕入れの段階で毒見する」——さばいた後より仕入れ時点のほうが入れ替えが効くし、被害も小さい。

シークレット管理

なぜシークレットは漏えいするか

APIキー・DB接続文字列・証明書秘密鍵などをソースコード/設定ファイル/CI環境変数に直書きすると、Git公開リポジトリへの誤プッシュ・退職者の手元PC・ビルドログ流出のいずれかで遅かれ早かれ流出する。GitHub上だけで日常的に検出されており、攻撃者は公開直後のコミットを継続スキャンしている。

4段階の成熟度モデル

段階方式問題
L0ソースに平文で埋め込みGit公開で即漏えい・ローテ不可
L1環境変数 + .env（gitignore）誤コミット・サーバ侵入で全漏えい
L2暗号化済み設定 + 復号鍵を別管理復号鍵そのものの管理が課題に
L3Secret Manager（HashiCorp Vault等）+ 短期トークン運用整備が必須だが攻撃面が最小

シークレット取得のシーケンス（Vault Dynamic Secrets）

CIジョブ
Vault
IDプロバイダ
DB
①CIジョブ→IDプロバイダ：OIDC/サービスアカウントトークン要求
②Vault→IDプロバイダ：トークン検証
③CIジョブ→Vault：DB接続情報を要求（短期）
④Vault→DB：その場で1時間有効のユーザを動的作成
⑤Vault→CIジョブ：1時間TTLの一時資格情報を返却
⑥CIジョブ→DB：マイグレーション実行
⑦TTL満了→Vault→DB：ユーザ自動削除

→ 万一トークンが漏えいしても1時間で自然失効するため、被害が最小化される（Static Secretとの最大の違い）。

記述問題で問われやすい論点

「コードに直書きはなぜ問題か」 → ローテーション不可・公開リポジトリ誤投稿で履歴に残り続ける・退職者環境からも参照可能 の3点を書く
「git rm で削除すれば良いか」 → 履歴に残るためNG。漏えいシークレットは失効・再発行が必須
「動的シークレットの利点」 → 短いTTLで自然失効・利用主体ごとに別資格・監査ログで誰がいつ使ったか追跡可能
R3秋 PM1問2 旧過去問より — システム開発工程での情報漏えい対策
旧形式の時代、開発工程の情報漏えいがCI/CD領域の代表的論点として問われた。論点は：①本番データの開発環境への流入防止（マスキング・匿名加工）、②ソースコード中のハードコードされた認証情報（git-secrets等のpre-commitフック導入）、③テスト環境のアクセス管理（本番と同等の権限管理）。新形式R5秋問3「CI/CD」では同テーマが大問丸ごと出題されており、旧形式の論点は完全に発展継承されている。「シフトレフト」「シークレット管理」を学ぶ前提として旧過去問の発想は有効。

IaCのセキュリティ統制

IaCの威力と表裏一体のリスク

IaC（Infrastructure as Code）は「インフラ構成を宣言的にコードで記述」する手法。Terraformで「S3バケットを作る」と宣言すれば、何度実行しても同じ構成が再現される（冪等性）。同時にたった1行のミスで全環境が公開設定になる「核戦争ボタン」でもある。

たとえ話：レシピと料理
手作業での構築＝シェフが毎回手作り（味のばらつき）。IaC＝レシピ通り全工場で同じ味（再現性）。ただしレシピに塩を10倍と書けば、全国の工場で塩辛い料理が一斉生産される。だからこそレシピ自体の校閲（IaCコードレビュー）が極めて重要。

典型的なIaC誤設定TOP5

#誤設定影響検知ツール
1S3バケット public-read機密ファイル全世界公開tfsec, Checkov
2SG inbound 0.0.0.0/0:22 (SSH全開放)総当たり攻撃の標的化tfsec
3RDS パブリックアクセス有効DBへの直接接続が可能にCheckov
4暗号化（At Rest）無効スナップショット流出時に平文露出tfsec, KICS
5IAMポリシーで Action: "*" Resource: "*"権限過剰による横展開Checkov, AWS IAM Access Analyzer

State ファイルの取扱い注意

Terraformのterraform.tfstateには取得した秘密鍵・DBパスワードが平文で残る場合がある。

→ どの層でCVEが見つかっても全体が脆弱になる。ベースOS層を「Distroless」など最小化すれば攻撃面が劇的に減る。

イメージ署名とSLSA

用語内容
Sigstore / cosignコンテナイメージへの署名・検証OSS。短期証明書で署名

in-toto各ビルドステップのattestation（出所証明）を集約するフレームワーク

コンテナ実行時セキュリティ

NetworkPolicy — Kubernetes上でPod間通信を必要最小限に

過去問記述演習（R5秋問3より）

R5秋 問3「CI/CD環境のセキュリティ」

設問1：シークレット管理の問題点
CIジョブから利用するDB管理者パスワードを、.gitlab-ci.yml内の環境変数（変更履歴付）に直接記述している。この管理方法のセキュリティ上の問題点を、25字以内で述べよ。
ヒント：「Git履歴」と「ローテーション」がキーワード。
模範解答（22字）：履歴から削除できず漏えい時に失効困難。
採点ポイント：「履歴に残る」「失効/ローテーションが困難」の両方に触れる。
別解：「過去のコミット参照で平文取得が可能」もOK。
設問2：Vault導入後のシーケンス
HashiCorp Vault導入後、CIジョブが認証トークンを偽装される攻撃を防ぐため、CIサーバ側で実装すべき対策を1つ挙げよ（35字以内）。
ヒント：「OIDC」と「Audience(aud)」の検証。
模範解答（32字）：OIDCトークンのaudクレームをVaultで厳格に検証する。
採点ポイント：OIDCのClaim検証（aud, iss, sub）の仕組みに言及できているか。
設問3：IaC誤設定の検知タイミング
本番環境のS3バケットが意図せず public-read 設定でデプロイされ、機密ファイルが公開された。この事故をデプロイ前に検知するため、CIパイプラインに組み込むべき工程を述べよ（30字以内）。
模範解答（28字）：tfsec等によるIaCコードの静的解析を必須化する。
採点ポイント：「IaCコードを静的解析する」工程の追加に言及。具体的ツール名（tfsec/Checkov）はあれば加点。
設問4：本番デプロイ時の追加統制
未署名のコンテナイメージが本番環境にデプロイされることを防ぐため、Kubernetesクラスタ側に導入すべき機能を答えよ（25字以内）。
模範解答（23字）：署名検証を行うAdmission Controller。
採点ポイント：OPA/Gatekeeper, Kyverno, Sigstore policy-controller のいずれかでも可。
