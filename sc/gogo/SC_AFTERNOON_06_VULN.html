脆弱性管理プロセスの全体像

脆弱性管理は「資産棚卸 → 脆弱性検出 → 評価 → 対応 → 検証」のループ。試験では各段階の使用ツール・指標・優先順位が問われる。

1資産棚卸
2脆弱性検出
3評価・優先順位
4対応
5検証・記録
1. 資産棚卸 (Asset Inventory)
守るべきものの全数把握。ハード・OS・ミドル・ライブラリ（OSS含む）・クラウドサービス。SBOMがここで活躍。資産が見えていない＝脆弱性管理は始められない。
2. 脆弱性検出 (Detection)
脆弱性スキャナ（Nessus、OpenVAS、Qualys）／SCAスキャナ（Snyk、Dependabot）／ペネトレーションテスト／CVE/JVN/CISAアラートの監視。
3. 評価・優先順位付け (Evaluation)
CVSSでリスク値を算出、KEV掲載有無で実害可能性を加味、EPSSで悪用確率を予測。資産価値・到達経路（外部公開か内部か）も合わせて優先度決定。
4. 対応 (Remediation)
パッチ適用／設定変更／代替ワークアラウンド／撤去。SLA（例：Critical 7日／High 30日）に基づいて期限管理。
5. 検証・記録 (Verification)
パッチ適用後の再スキャンでクローズ確認、台帳に記録、再発防止策を整理。経営層への報告。

CVE / CWE / CVSS — 脆弱性の語彙

脆弱性管理で使う3つのID体系・指標。それぞれ役割が違う。混同しないこと。

用語意味例運営
CVE（Common Vulnerabilities and Exposures）個別脆弱性の識別子CVE-2021-44228（Log4Shell）MITRE社・CISA
CWE（Common Weakness Enumeration）脆弱性の分類体系CWE-79（XSS）、CWE-89（SQLi）MITRE社
CVSS（Common Vulnerability Scoring System）深刻度スコアリング方式9.8 / 10.0（Critical）FIRST.org
JVN日本国内ポータル（CVE等を集約）JVNDB-2021-014116JPCERT/CC + IPA
NVD米国の脆弱性DB（CVE参照元）NIST運営NIST

CVE/CWE/CVSSの関係

あるソフトの脆弱性 = 1つのCVE-ID　→　その分類はCWE　→　深刻度はCVSS。例：

// Log4Shell の登録例 CVE-ID: CVE-2021-44228 タイトル: Apache Log4j2 JNDI features used in configuration, log messages, and parameters do not protect against attacker controlled LDAP and other JNDI related endpoints. CWE分類: CWE-502 (Deserialization of Untrusted Data) CVSS v3.1: 10.0 / Critical (AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H) JVN: JVNDB-2021-014116 KEV登録: あり（即時対応必須）
3

CVSS v3.1 メトリクス完全解説

CVSSは3つのメトリック群からなる。試験では基本評価基準（Base）が頻出。

3つのメトリック群

① 基本評価基準 (Base)
脆弱性固有の特性。時間や環境に依存しない。CVE登録時のスコア。
② 現状評価基準 (Temporal)
時間とともに変化する要因。エクスプロイト公開状況、修正状況、報告信頼性。
③ 環境評価基準 (Environmental)
利用組織固有の文脈。資産の重要度、緩和策の有無で再計算。

基本評価メトリクス（8項目）

CVSS v3.1基本評価には次の8つの指標がある。AV/AC/PR/UI/S/C/I/Aと覚える。

記号名称値意味
AVAttack Vector（攻撃元）N(ネットワーク) / A(隣接) / L(ローカル) / P(物理)外部からアクセスできるほど高スコア
ACAttack Complexity（攻撃複雑度）L(低) / H(高)攻撃成立条件が単純なほど高スコア
PRPrivileges Required（必要権限）N(なし) / L(低) / H(高)権限不要なほど高スコア
UIUser Interaction（利用者関与）N(不要) / R(必要)ユーザ関与不要なほど高スコア
SScope（影響範囲）U(変更なし) / C(変更あり)他コンポーネントへ波及するなら C
CConfidentiality（機密性）N(なし) / L(低) / H(高)情報漏えいへの影響
IIntegrity（完全性）N(なし) / L(低) / H(高)改ざん影響
AAvailability（可用性）N(なし) / L(低) / H(高)サービス停止影響

スコアバンドと深刻度

0.1〜3.9Low
4.0〜6.9Medium
7.0〜8.9High
9.0〜10.0Critical
0.0None

ベクトル文字列の読み方

CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H // 解読 AV:N → Attack Vector: Network（インターネット越し） AC:L → Attack Complexity: Low（簡単） PR:N → Privileges Required: None（権限不要） UI:N → User Interaction: None（被害者の操作不要） S:C → Scope: Changed（被害範囲が他コンポーネントに波及） C:H → Confidentiality Impact: High（高い機密影響） I:H → Integrity Impact: High（高い完全性影響） A:H → Availability Impact: High（高い可用性影響） → 計算結果: 10.0 / Critical（Log4Shellの実例）
R7春 問4：CVSSのバージョン違いと、KEV掲載の意味、EPSSの位置付けが組み合わせで問われた。CVSSは深刻度、KEVは実害確認、EPSSは悪用確率予測と整理できれば即答。
4

KEV — 既知悪用脆弱性カタログ

KEV (Known Exploited Vulnerabilities Catalog)は、米国CISAが「実際の攻撃で悪用されたことが確認された脆弱性」を集めたリスト。CVSSスコアと違い「実害」を直接示すため、優先度付けに極めて有用。

CVSS vs KEV vs EPSS — 3つの違い

指標意味用途更新頻度
CVSS理論的深刻度（0.0〜10.0）初期評価静的（基本値はほぼ不変）
KEV実害確認の有無（Yes/No）緊急対応判断随時追加
EPSS今後30日以内の悪用確率（0%〜100%）予測的な優先度毎日更新

運用例：CVSS 9.0以上＋KEV掲載＋EPSS 70%以上 → 即時対応（数日以内）。CVSS 9.0以上だがKEV未掲載＋EPSS 5%以下 → 定期パッチサイクルで対応（30〜60日）。

たとえると、CVSSは「健康診断の血圧値」、KEVは「実際に倒れた人が出ている病気」、EPSSは「明日倒れる確率」。すべてが揃って初めて、限られたパッチ適用リソースを最適配分できる。

R7春 問4：「KEV」が題材で出題。CVSSスコアだけでなく実際の悪用状況を加味して優先度を決める運用が答え。CISAのKEVカタログは cisa.gov で公開。

SCAP / SBOM — 自動化と可視化

SCAP — Security Content Automation Protocol

NIST策定。脆弱性管理を機械処理可能な形式で自動化するための仕様群。

SCAP構成要素役割
CVE脆弱性識別
CCE（Common Configuration Enumeration）設定項目識別
CPE（Common Platform Enumeration）プラットフォーム/製品識別
CVSS深刻度評価
OVAL（Open Vulnerability and Assessment Language）判定ロジック記述言語
XCCDF（Extensible Configuration Checklist Description Format）チェックリスト記述
CCSS設定不備のスコアリング

SBOM — Software Bill of Materials

ソフトウェアの「材料表」。利用しているOSSライブラリ・コンポーネント・バージョンを機械処理可能な形式で列挙したファイル。Log4Shell以降、米国大統領令で政府調達ソフトに義務化された。

SBOMの主要フォーマット

フォーマット運営特徴
SPDXLinux FoundationISO標準（ISO/IEC 5962:2021）。ライセンス情報強化
CycloneDXOWASPセキュリティ志向、VEX（脆弱性影響表明）対応
SWIDISOタグ形式、限定的に利用

SBOMの価値

「Log4j 2.x を含む製品はどれか？」をSBOM一覧から即座に検索可能。Log4Shell発覚時、SBOMを持つ組織は数時間で影響範囲特定、持たない組織は数週間を要した。

R7春 問1（サプライチェーン）でSBOMが論点：委託先からのソフトウェア納品時にSBOMの提出を要求する運用が問われた。納品物の内容を発注側が把握するためのツールとして位置づけられる。

脆弱性診断とペネトレーションテスト

「脆弱性診断」と「ペネトレーションテスト」は目的・手法が異なる。混同しないこと。R6秋問4の主題。

脆弱性診断（Vulnerability Assessment）

目的：「どんな脆弱性があるか」の網羅的洗い出し

手法：自動スキャナ（Nessus、OpenVAS）＋目視確認

深さ：浅く広く。シグネチャベース

結果：脆弱性一覧（CVE-IDとCVSS付与）

ペネトレーションテスト（Penetration Test）

目的：「攻撃が成立するか／何ができるか」の実証

手法：診断員（White Hat）が手動で攻撃を試行

深さ：深く狭く。シナリオベース

結果：攻撃シナリオ・到達範囲・データ持ち出し可能性

診断の3レベル

Black Box
情報なし。外部攻撃者視点。最もリアル、最も時間がかかる
Grey Box
一部情報あり（一般利用者アカウント等）。もっとも費用対効果が高い
White Box
全情報あり（ソースコード・構成情報）。網羅性は高いが現場感に乏しい
R6秋 問4：セキュリティ診断の調達で、診断員に提供する情報の範囲（Grey Box設計）と、診断結果の取扱い手順が問われた。診断結果は機密情報として暗号化保管、診断員も守秘義務契約（NDA）が必須。
H30秋 PM1問3 / H30春 PM1問1 旧過去問より — SCA（Software Composition Analysis）の登場前夜
2018年（平成30年）の旧形式時代から、ソフトウェアの脆弱性管理は連続出題されている。当時の論点は：①OSSライブラリの脆弱性把握＝どのプロジェクトでどのバージョンを使用しているか即答できるか、②CVSSによる優先順位付け＝深刻度判定の標準化、③パッチ適用と検証の運用フロー。これがR7春のSBOM/KEV論点に直結している。「SCAツールをCIに組み込み自動検出する」のが現代の正攻法（第14章Q48参照）。歴史を辿るとマネジメントテーマの普遍性が見えてくる。

パッチ管理プロセス

脆弱性を見つけたら次は対応。パッチ適用＝即時実施とはいかず、業務影響評価が必要。

パッチ適用のステップ

1
情報収集　ベンダ通知・JVN・CISA KEV・X (Twitter) 監視。RSS自動収集。
2
影響評価　自社環境の対象資産抽出（SBOM活用）。CVSS×KEV×EPSS×資産価値で優先度判定。
3
テスト　検証環境でパッチ適用。業務アプリの回帰テスト。互換性問題の有無確認。
4
変更管理承認　CAB（Change Advisory Board）／変更管理プロセス。緊急時はFast-Track。
5
本番適用　メンテナンス時間に実施。ロールバック計画必須。段階展開（カナリア→部分→全体）。
6
検証・記録　再スキャン・台帳更新・経営層報告。

パッチを当てられない場合のワークアラウンド

業務影響・互換性問題でパッチを即時適用できないケースは多い。代替策：

WAFルール追加
攻撃パターンを境界で遮断。Log4Shell時の典型対応
FWで通信制限
該当機能の利用元IPを限定、外部公開停止
機能無効化
脆弱な機能だけを無効化（例：Log4jのlookup機能）
監視強化
SIEMで該当攻撃シグネチャを検知、即応体制

過去問記述演習

演習1CVSS解読（R7春問4類題）
『次のCVSS v3.1ベクトルが付与された脆弱性が公表された：CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H』
設問：このベクトルから読み取れる脆弱性の特徴を、(1)攻撃の到達経路、(2)攻撃成立に必要な条件、(3)発生する影響 の3点で簡潔に述べよ。
解答例：
(1) ネットワーク経由（インターネット越し）で到達可能（AV:N）
(2) 攻撃複雑度が低く、認証情報も利用者操作も不要（AC:L, PR:N, UI:N）
(3) 機密性・完全性・可用性のすべてに高い影響（C:H, I:H, A:H）
→ 極めて深刻、即時対応が必要
演習2優先度判定（KEV+CVSS）
『社内の脆弱性管理担当が、新たに公開された4つのCVEを評価している。 (ア)CVSS 9.8、KEV未掲載、外部公開Webサーバ。 (イ)CVSS 7.5、KEV掲載あり、外部公開Webサーバ。 (ウ)CVSS 9.0、KEV未掲載、内部限定サーバ。 (エ)CVSS 6.5、KEV掲載あり、検証環境のみ。』
設問：もっとも優先的に対応すべきCVEはどれか、理由とともに述べよ。
解答例：(イ) を最優先で対応すべき。外部公開のWebサーバに存在し、KEVに掲載されている＝既に実際の攻撃に使われている脆弱性のため、CVSSスコアより実害発生リスクが高い。CVSSが高くてもKEV未掲載かつ内部限定の(ウ)より緊急度が上回る。
本章のまとめ

① 脆弱性管理は「資産→検出→評価→対応→検証」の5サイクル。② CVE/CWE/CVSSは識別・分類・スコアの3点セット、KEVは実害確認、EPSSは悪用確率。③ CVSS v3.1の8メトリクス（AV/AC/PR/UI/S/C/I/A）を読めるように。④ SBOMでOSS依存関係を可視化。⑤ 診断とペンテストは目的が違う、Grey Boxが費用対効果良。⑥ パッチ適用前にWAF・FWでワークアラウンドを打つのが定石。
