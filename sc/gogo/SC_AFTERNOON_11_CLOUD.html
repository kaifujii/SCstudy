従来型 vs クラウド型のセキュリティ思想

項目オンプレ・境界防御クラウド・ゼロトラスト
守るもの「内側」のネットワーク「個別のリソース」と「ID」

「事業者の責任」と「利用者の責任」を分ける呼び方

クラウドの「で」(of) のセキュリティ

Security of the cloud — 事業者の責任。物理DC・H/W・仮想化基盤の安全性。利用者から見えない部分。

vs

クラウド「内」(in) のセキュリティ

Security in the cloud — 利用者の責任。設定・データ・ID管理。過去問の論点はほぼ全てこちら。

→ AWSでは"Shared Responsibility Model"、Azureでは"Shared Responsibility for Cloud Computing"、GCPでは"Shared Fate"（より事業者寄り）と呼称が異なるが本質は同じ。

R5春 PM2問2 / R4春 PM2問2 旧過去問より — オンプレからクラウド移行のセキュリティ要件
旧形式時代に2回連続で「クラウド移行」がPM2の長文総合問題として出題されている。論点は：①責任共有モデルに基づく分担表の作成（OSパッチは利用者・ハイパーバイザは事業者）、②移行に伴うネットワーク設計の見直し（VPNとPrivateLinkの選択、IGWを通さない閉域網接続）、③監査要件（CloudTrail等で全API操作のログを保全）、④データの所在地（リージョン選択と各国法令の準拠）。新形式R7秋でもクラウドが大問丸ごと出題されており、知識は完全に継承される。

IAMと最小権限

IAMの3要素

プリンシパル
行為者：ユーザ・グループ・ロール・サービスアカウント
アクション
操作：s3:GetObject, ec2:RunInstances 等
リソース
対象：arn:aws:s3:::mybucket/* 等

最小権限原則 (PoLP) の実装パターン

パターン仕組みリスク低減効果
ロール (Role) ベース権限はロールに付与し、ユーザはロールを assumeユーザ毎の個別ポリシーを排除。退職時取消が容易
属性ベース (ABAC)タグや属性に基づき動的判定大規模組織で運用負荷を抑える
Just-In-Time (JIT) アクセス必要時のみ権限を付与・自動失効常時権限保持を排除
権限境界 (Permission Boundary)ロールの最大可能範囲を定義権限昇格攻撃を防ぐ
Service Control Policy組織全体に強制する禁則ルール「rootでもS3公開禁止」等を強制

典型的なIAM落とし穴

過剰な"*": "Action": "s3:*" や "Resource": "*"。意図せぬ操作も全許可
長期アクセスキー：人ユーザに発行したIAMアクセスキーをコードに直書き → 漏えい時に永続使用
ConfusedDeputy：信頼ポリシーが緩く、第三者が自分のID扱いで AssumeRole してしまう
IMDSv1放置：EC2メタデータサービスからクレデンシャル盗取（SSRF と組み合わせ）→ IMDSv2必須化
MFA未強制：root含む特権アカウントでMFA未設定。フィッシング1発で侵入

ゼロトラストの7原則

NIST SP 800-207 (Zero Trust Architecture) で定義された7つの基本原則。

①リソース個別保護
DB/API/ファイル毎に防御
②全通信の保護
場所に依らずTLS強制
③セッション単位
リソース毎に認可
④動的ポリシー
属性・コンテキスト評価
⑤資産状態監視
端末健全性を常時確認
⑥動的認証
毎回MFA・条件付
⑦継続的測定
利用ログでポリシー改善

ゼロトラスト構成の代表モデル — PEP/PDP方式

利用者

①利用者→PEP：リソースAアクセス要求
②PEP→PDP：「このユーザ・端末・時刻・場所でAは可？」
③PDP：IDaaS/ディレクトリ/EDR/SIEM/MFAから属性収集

R2秋 PM2問2 / H31春 PM1問2 / H30秋 PM2問1 旧過去問より — テレワーク／クラウドセキュリティの胎動
クラウドは古典時代から連続出題されている。20回中11回出題、IRに次ぐ第3の頻出テーマ。古典時代の論点は：①R2秋（COVID-19直後）＝VPN集約構成 vs SaaS直接接続の選択、IDaaS/MFA/MDM/CASBの組み合わせ＝後のSASE/ZeroTrustの先駆け、②H31春＝SaaS利用時の責任分界の整理、③H30秋＝オンプレからIaaS移行時のOSパッチ責任の明確化。2018年からの一貫した流れとして「責任共有モデル＋ID連携＋境界依存からの脱却」を読み取れる。第14章Q43/Q49参照。
H29春 PM1問3 / H27秋 PM2問1・PM2問2 旧過去問より — クラウド認証連携／シンクライアントという黎明期パラダイム
2015〜2017年はクラウドが「企業の選択肢」になり始めた時期。①H29春のクラウド認証連携＝OAuth 2.0アクセストークン検証（イントロスペクション vs JWT）が論点で、現代のZero Trust ID連携の源流。②H27秋のシンクライアント＝マルウェア感染対策として、端末にデータを置かない＋集中監査・ログ管理を実現する設計。これが後のVDI／DaaS／クラウドPC（Windows 365等）へと進化した。ZeroTrust「データはクラウドに、端末は処理装置に過ぎない」思想の源流がここにある。第14章Q56/Q60参照。

CASB / SASE / SSE / SDP

ゼロトラスト時代の用語整理。実装製品の用語が氾濫しているため、4語の関係性を押さえておくと混乱しない。

4語の役割マトリクス

用語主な対象解決する課題例
CASBSaaSアクセス全般シャドーIT可視化・DLP・利用統制Netskope, McAfee MVISION, Microsoft Defender for Cloud Apps
ZTNA / SDP社内アプリ（旧VPNの代替）従業員の社内アプリへの安全なアクセスZscaler Private Access, Cloudflare Access
SWGWebアクセスマルウェア/フィッシングサイト遮断Zscaler Internet Access, Cisco Umbrella
SSECASB+ZTNA+SWGの統合セキュリティ機能をクラウドで統合提供Zscaler ZIA+ZPA, Netskope SSE
SASESSE + SD-WANセキュリティ＋ネットワーク全部クラウド統合Cato Networks, Palo Alto Prisma SASE
たとえ話：宅配サービスの進化
CASB＝郵便物（SaaS）を仕分けるセンター。ZTNA＝書留（社内アプリ）専用ルート。SWG＝迷惑物（怪しいサイト）の差止。SSE＝この3つを1社が一括提供。SASE＝そこに配送網（SD-WAN）まで含めて全部1社で。=「セキュリティとネットワークの境界がクラウドで再統合された世界」。

IDaaSの位置づけ

IDaaS（Identity as a Service）はゼロトラストの中核。各SaaSへのSSOとMFA、条件付アクセスを集中管理する。代表：Okta, Azure AD（Entra ID）, Google Workspace ID, OneLogin。「IDaaSが落ちると全SaaSにログインできない」ためBCP上は冗長ID連携も検討。

過去問記述演習

R7秋 問1「SaaSのロール管理とXSS・ファイルUL」

設問1：管理者ロールの過剰付与
運用簡素化のため全部署の担当者に「管理者」ロールを付与したSaaS環境で、ある担当者がフィッシングで侵害された。被害が極大化した理由を、ロール設計の観点から述べよ（35字以内）。
模範解答（33字）：最小権限の原則に反し全担当者が全データへ操作できたため。
採点ポイント：「最小権限の不徹底」と「広範囲データへの操作可能性」の両方に言及。
設問2：是正策（IAMの観点）
設問1の状況を是正するため、各部署担当者に付与すべき権限のあり方を述べよ（30字以内）。
模範解答（28字）：業務に必要な範囲のみのロールを部署別に付与する。
別解：「最小権限原則に基づき業務単位でロール分離（22字）」も可。
設問3：ファイルアップロードのリスク
SaaS上のファイルアップロード機能で、HTMLファイルがアップロードされ閲覧時に実行されることでXSSが発生した。サーバ側で実装すべき対策を1つ挙げよ（40字以内）。
模範解答（38字）：Content-Disposition: attachment を付け同一オリジン外で配信。
別解：「サンドボックスドメインから配信し本体ドメインのCookieを遮断する」
採点ポイント：「ブラウザに実行させない」「同一オリジンを切り離す」のいずれかに言及。
設問4：シャドーIT発見
情報システム部門が把握していないSaaSを社員が業務利用していることが判明した。これを継続的に可視化する仕組みとして導入すべき製品種別を答えよ（15字以内）。
模範解答（4字）：CASB
別解：「クラウドアクセスセキュリティブローカー（CASB）」
採点ポイント：SaaS可視化・統制の役割を担うCASB（またはSSE/SASE）と回答。
