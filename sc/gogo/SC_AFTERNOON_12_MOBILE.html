スマホアプリのリスク全体像

位置づけ — Webアプリと何が違うか

第3章のWebアプリは「サーバ側にコードがある」が、スマホアプリはコード本体が利用者の端末上にある。攻撃者がアプリのコピーを所持できるため、解析・改変・再配布が容易。さらに端末がRoot化/Jailbreakされていれば、サンドボックスごと突破される。

たとえ話：金庫の設計図をお客様に渡す
Webアプリ＝銀行（金庫は銀行内）。スマホアプリ＝「金庫を1台ずつ全顧客に配布」。攻撃者は手元で何時間でも分解・X線撮影・解錠手順試験ができる。だから金庫は中身（鍵）を入れず、銀行への通信だけを担う方式が基本。

通信の保護 — 証明書ピンニング

なぜTLSだけでは不十分か

通常のTLSはOS信頼ストアのすべてのCAを信頼する。攻撃者が以下のいずれかに成功すれば、別CAが発行した偽証明書で中間者攻撃が成立する：
① 端末にCA証明書を不正インストール（マルウェア・MDM悪用）
② 信頼CAそのものへの侵入・誤発行
③ 政府・通信事業者によるCA強要

証明書ピンニング (Certificate Pinning) の仕組み

アプリ内に正規サーバ証明書（または公開鍵）のハッシュを事前埋込み、TLSハンドシェイク時に「OSの信頼CA」ではなく「埋込ハッシュ」と一致するかを確認する。一致しなければ通信を中断。

スマホアプリ
公開鍵ハッシュ埋込
中間者
偽CAで偽証明書
正規サーバ
①アプリ→中間者：TLS ClientHello（中間者が傍受）
②中間者→アプリ：偽証明書（偽CA署名・OS信頼CAリストにあれば通常は通る）
③アプリ：受信した証明書の公開鍵SHA-256ハッシュを計算
④アプリ：埋込ハッシュ ≠ 計算ハッシュ → 通信中断
⑤アプリ：エラー画面表示・通信ログ送信なし
→ 信頼CAの誤発行や端末への偽CA注入があってもMITM不成立。

ピンニング実装の選択肢

対象メリットデメリット
サーバ証明書全体シンプル証明書更新時にアプリ更新が必須
サーバ公開鍵更新が同じ鍵なら継続使用可鍵ローテーション時に更新必要
中間CA証明書サーバ証明書更新の影響を受けない同CAなら他社証明書も通ってしまう
ルートCA証明書影響範囲最小だが…事実上ピンニングの意味が薄い

記述問題で問われやすい論点

「TLSのみでは不十分な理由」 → 端末に不正CAが追加された場合、信頼ストア経由で偽証明書が通ってしまう
「ピンニング失効時のリスク」 → サーバ証明書更新を忘れるとアプリが全ユーザで通信不能（バックアップピン推奨）
「公開鍵ピンが推奨される理由」 → 同じ鍵で証明書を再発行できるため、有効期限切れに対応しつつピンを継続できる

Keychain / KeyStore の特徴

iOS Keychain + Secure Enclave

Apple T2/A系チップ内の専用セキュリティチップに鍵格納。CPUからも鍵本体を取り出せず、署名/復号操作だけが可能。生体認証（Face ID/Touch ID）と連動。

vs

Android Keystore + StrongBox

API 28+ でStrongBox（独立TEE/Secure Element）対応。鍵はOSからもアクセス不能。BiometricPromptと組み合わせて鍵使用を生体認証ゲート化できる。

バックアップ漏えい対策

iOS：機密ファイルに NSURLIsExcludedFromBackupKey を設定し iCloud/iTunesバックアップから除外
Android：Manifestで android:allowBackup="false" または fullBackupContent でホワイトリスト/ブラックリスト指定
クリップボード：機密フィールド（パスワード等）は android:isSensitive（API 33+）/ UIPasteboardのexpiry設定で短時間保持
スクリーンショット：FLAG_SECURE（Android）/ screen capture protection（iOS）で重要画面の撮影/録画を阻止

Root化/Jailbreak検知と難読化

Root/Jailbreak環境で何が起きるか

サンドボックスが無効化され、他アプリのストレージ・メモリが読み取り可能になる。デバッガアタッチで実行中の暗号鍵を抽出されたり、Frida等の動的計装ツールで関数フックを差し込まれたりする。

検知の典型的なシグナル

OS検知シグナル
Android/system/app/Superuser.apk等のファイル存在
suバイナリの存在 (/system/bin/su等)
Magisk由来パスの検出
SafetyNet/Play Integrity API のテスト失敗
iOS/Applications/Cydia.app等の存在
/usr/sbin/sshd, /etc/aptなどUnix系ファイル
サンドボックス外（/private/）への書込テスト
fork() が成功する（通常はブロック）
注意：単一シグナルでの判定は容易にバイパスされる。Frida hook や ObjectionでJailbreak検知関数を上書きされるため、複数の独立した手法を組み合わせ、サーバ側でも端末アテステーション（Play Integrity / DeviceCheck）を検証する。

難読化 (Obfuscation)

レベル手法効果
初級R8/ProGuard（クラス名・メソッド名短縮）静的解析の可読性低下
中級文字列暗号化・分岐難読化API URL等の可読抽出阻止
上級商用難読化（DexGuard, iXGuard, Arxan）制御フロー難読化・改ざん検知・自己防衛
最強VM保護・ネイティブ化（C/C++移植）解析コスト指数増。ただし開発コスト増

→ 難読化は「攻撃を阻止する」のではなく「攻撃コストを上げる」もの。十分な動機があれば最終的に解析されるため、サーバ側統制と組み合わせる前提。

IPC/Intent/Deep Link の落とし穴

Android — Intent と コンポーネント露出

Activity/Service/BroadcastReceiver/ContentProvider をManifestに android:exported="true" で公開すると、他アプリから直接呼び出せる。意図しない公開は権限昇格・データ漏えいの直接原因になる。

脆弱性典型攻撃対策
Activity 過剰公開悪意アプリが認証画面を直接起動して情報窃取exported=false / カスタムpermission要求
BroadcastReceiver 公開偽のブロードキャストでアプリ動作改変パーミッション付与 + LocalBroadcastManager
ContentProvider 公開SQL Injection で全データ抜出パラメータバインド + URI書込チェック
暗黙的Intent悪意アプリが横取り（Intent Sniffing）明示的Intent（クラス指定）+ パーミッション要求

Deep Link / Universal Link

「myapp://」のようなカスタムスキームは他アプリが奪取可能（Scheme Hijacking）。重要操作はApp Links（Android）/Universal Links（iOS）でドメイン所有を検証する。

App Links (Android): サーバの /.well-known/assetlinks.json でアプリ署名と関連付け検証
Universal Links (iOS): /.well-known/apple-app-site-association でドメイン所有を検証
OAuth Redirect: 「カスタムスキーム」より「PKCE + Universal Link」を推奨。code intercept 攻撃を防止

WebView の落とし穴

setJavaScriptEnabled(true) + addJavascriptInterface で Java側メソッドが JS から呼び放題になりRCEに発展（特にAPI 17未満）
setAllowFileAccess(true) でローカルfile://が読まれ、アプリ内ファイルがJSから抽出される
ロード先URLの検証不足 → 攻撃者URLが読まれてリダイレクト・フィッシング

OWASP MASVS / MASTG

モバイルアプリのセキュリティ要件・テスト基準のデファクトスタンダード。MASVS（要件）とMASTG（テスト手順書）の2本立て。

MASVS の8カテゴリ（v2.x）

カテゴリ要件の概要
MASVS-STORAGE機密データの安全な保管（Keychain/Keystore）
MASVS-CRYPTO暗号アルゴリズム選定・鍵管理の正しさ
MASVS-AUTH認証・認可・セッション管理
MASVS-NETWORK通信の保護（TLS・ピンニング）
MASVS-PLATFORMプラットフォーム機能の正しい使用（Intent/権限）
MASVS-CODEコード品質・依存ライブラリの脆弱性管理
MASVS-RESILIENCE改ざん・解析耐性（Root検知・難読化）
MASVS-PRIVACY個人データの取扱い（収集最小・透明性）

レベル分け

L1 — 標準セキュリティ

一般的なアプリで満たすべきベースライン。MASVS-RESILIENCE以外を網羅。

vs

L2 — 防御的アプリ

金融・医療等。L1 に MASVS-RESILIENCE（耐解析・耐改ざん）を加えた最高レベル。

過去問記述演習

R7春 問3「スマホアプリの開発」

設問1：通常のTLSで防げない攻撃
スマホアプリは標準のTLS実装でサーバと通信している。利用者の端末に攻撃者が不正なCA証明書をインストールできた場合、TLSのみでは防げない攻撃名を答えよ（15字以内）。
模範解答（10字）：中間者攻撃
別解：「MITM攻撃」「マンインザミドル攻撃」も可。
設問2：対策の実装
設問1の攻撃を防ぐためにアプリ側で実装すべき仕組みを答えよ（20字以内）。
模範解答（10字）：証明書ピンニング
別解：「公開鍵ピンニング（8字）」も可。
設問3：ピンニング設計の考慮事項
サーバ証明書を更新したところ、特定アプリバージョン以前で通信不能になる事故が発生した。これを防ぐため、ピンニング設計時に取るべき対策を1つ挙げよ（35字以内）。
模範解答（30字）：バックアップピン（次世代の鍵ハッシュ）を併記する。
別解：「複数の公開鍵ハッシュをピンに含める（19字）」
採点ポイント：「次回鍵ローテーション分も予め埋め込む」考え方に言及。
設問4：認証トークン保管
アプリは認証用トークンを SharedPreferences に平文で保管している。Root化端末ではこれが他アプリから読み取り可能となる。修正案を述べよ（35字以内）。
模範解答（33字）：Android Keystoreで暗号化しEncryptedSharedPreferencesに保管。
別解：「Keystoreで生成した鍵で暗号化して保管」
採点ポイント：「Keystore（or Keychain）+ 暗号化」のセットに言及。
設問5：難読化の限界
アプリにR8/ProGuardによる難読化を施した。これでも完全には解析を防げない理由を簡潔に述べよ（30字以内）。
模範解答（28字）：動的解析や十分な時間で論理復元が可能なため。
採点ポイント：「難読化はコストを上げるがゼロにはしない」の本質に言及。
