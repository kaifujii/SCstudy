PCI DSS — 12要件と4レベル

PCI DSS（Payment Card Industry Data Security Standard）はカード情報を扱うすべての事業者に課されるセキュリティ基準。最新はv4.0（2024年3月施行）。

12要件（6カテゴリ）

カテゴリ要件
① 安全なネットワーク構築1. FW構築維持
2. デフォルトパスワード変更
② カード会員データ保護3. 保管時の保護（暗号化/トークン化）
4. 公衆網経由の通信暗号化
③ 脆弱性管理プログラム5. マルウェア対策
6. 安全なシステム/アプリ開発
④ 強固なアクセス制御7. Need-to-Knowによる権限制限
8. 利用者の識別・認証（MFA含む）
9. 物理アクセス制限
⑤ 定期的監視・テスト10. すべてのアクセスを記録・監視
11. セキュリティテスト・脆弱性スキャン
⑥ 情報セキュリティポリシー12. 従業員/委託先向けポリシー策定・教育

事業者レベル（取引件数による分類）

v4.0で強化された主な点

多要素認証の必須化（カード情報環境への全アクセス）、パスワード最低12文字、Webスキミング対策（決済ページの整合性監視）、カスタマイズドアプローチ（柔軟性向上）。2025年4月から完全適用。

3

カード情報「非保持化」

日本特有の概念。「カード情報を保持しない」=PCI DSS適用範囲外として、加盟店の負担を軽減する考え方。割販法の改正で実装が促進された。

非保持化の3類型

① リンク型
決済画面がPSP側に遷移。加盟店サイトはカード番号入力欄を持たない。最も安全
② JavaScript型
加盟店の決済画面で入力 → JSが直接PSPへ送信。加盟店サーバを通らない
③ トークン型
PSPがカード番号をトークンに変換、加盟店はトークンのみ保持。継続課金に有用

「保持」とみなされる典型ケース

① サーバログにカード番号が記録 → 保持　② メモリ上に一瞬でもカード番号が存在 → 保持（流通中とみなさない場合）　③ FAX/メール受信でカード番号を受領 → 保持　④ 従業員のメモに書く → 物理的保持

「保持していない」と謳うには、すべての処理経路でカード番号がアプリ・OS・ストレージに到達しないことを技術的に証明する必要がある。

4

3-Dセキュア 2.0（EMV 3-D Secure）

カード会員本人を確認する仕組み。3-Dセキュア 1.0は廃止（2022年10月）、現在は2.0。不正利用率の低下とカゴ落ち率の低下を両立させた。

1.0 vs 2.0の違い

3-D Secure 1.0（廃止）

取引のたびに毎回パスワード入力を要求

カゴ落ちが多発、利用者離れ

パスワード使い回し攻撃（クレデンシャルスタッフィング）に脆弱

3-D Secure 2.0

リスクベース認証（RBA）：低リスク取引はパスワード省略

200項目以上のデータ（端末情報、過去履歴等）でリスク評価

高リスク取引のみ生体認証・OTP・アプリ認証でチャレンジ

EMV 3DSの認証フロー

1取引開始
2リスク評価
3分岐
4決済承認
STEP 1：取引開始
加盟店が3DSサーバへリスク評価データを送信（端末情報、IP、過去履歴、金額、カテゴリ）
STEP 2：リスク評価
イシュアのACSがリスクスコアを算出。低リスク=Frictionless、高リスク=Challenge
STEP 3：分岐
Frictionless：追加認証なしで決済承認
Challenge：OTP・アプリ・生体認証で本人確認
STEP 4：決済承認
認証成功後、通常のオーソリ→キャプチャに進む

義務化スケジュール

日本では割賦販売法に基づき、2025年3月までにEC加盟店で原則義務化。経済産業省「クレジットカード取引におけるセキュリティ対策強化に向けた実行計画」が根拠。

5

リンク型・トークン型決済

リンク型決済

会員がカード番号を入力する画面がPSPのドメイン。加盟店サイトに番号は流れない。

長所

加盟店はPCI DSS適用範囲外

カード情報漏えいリスクが極小化

実装が簡単

短所

UX分断（ドメインが変わる）

フィッシング誤認の可能性（正規PSPサイト vs 偽物）

継続課金にはトークン化との併用が必要

トークン型決済

初回決済後、PSPが返すトークン（カード番号と1:1対応する代替値）を加盟店が保管。次回以降はトークンで決済できる。

// 初回決済 会員 → カード番号 4111-1111-1111-1111 → PSP PSP → トークン "tok_abc123" を加盟店に返却 // 加盟店DBに保存されるのはトークンのみ user_id: 12345, payment_token: "tok_abc123" // 2回目以降の決済（継続課金など） 加盟店 → トークン "tok_abc123" + 金額 → PSP PSP → 内部でカード番号復元 → オーソリ実行

Webスキミング対策（PCI DSS v4の新項目）

Webスキミング（Magecart攻撃）：加盟店の決済ページに悪性JSを注入し、利用者入力中のカード番号を盗む攻撃。リンク型でなく自社決済画面を使う場合、SRI（Subresource Integrity）による外部スクリプト改ざん検知、CSPによる外部送信制限が必須対策。

過去問記述演習

演習1非保持化への移行（R6秋問3類題）
『A社のEC加盟店サイトで、カード番号入力フォームから加盟店サーバを経由してPSPへ送信する方式を採用していた。サーバのログにカード番号が記録される事故が発生した。』
設問：再発防止策として加盟店サーバを「非保持化」する具体的な実装方式を1つ挙げ、その仕組みを50字以内で述べよ。
解答例：リンク型決済を採用し、カード番号入力画面をPSPのドメインに遷移させる方式とする。（41字）

または：JavaScript型として、カード番号入力値をブラウザから直接PSPへ送信する。
本章のまとめ

① PCI DSS v4は2024年施行、MFA必須化・Webスキミング対策追加。② 非保持化はリンク型・JS型・トークン型の3パターン。③ 3DS 2.0はリスクベース認証で低リスクならFrictionless、UXとセキュリティを両立。④ Webスキミング対策にはSRI+CSPが必須。
