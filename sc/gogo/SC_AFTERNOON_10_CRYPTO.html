暗号方式の全体像

位置づけ — どこで効いているか

暗号は機密性・完全性・認証・否認防止の4つを支える基盤技術。本シリーズの第3章（Web）の通信路は本章のTLSで、第4章（DNS）はDNSSEC署名で、第8章（PCI DSS）はカード情報暗号化で、第11章（クラウド）はKMSで——すべて本章の応用。

3大カテゴリの違い

項目共通鍵暗号
(対称暗号)		公開鍵暗号
(非対称暗号)		ハッシュ関数
鍵の種類1個（送受で同じ）2個ペア（公開鍵+秘密鍵）鍵なし
用途大量データの暗号化鍵交換・署名・少量暗号完全性検証・パスワード保管
速度非常に高速低速（共通鍵の数百倍遅い）非常に高速
代表アルゴリズムAES-128/256, ChaCha20RSA, ECDSA, Ed25519, ECDHSHA-256, SHA-3, BLAKE2
鍵配送問題あり（事前共有が必要）なし—
典型用途TLSのデータ転送TLS鍵交換・電子署名HMAC, パスワード, ブロックチェーン
たとえ話：金庫と郵便受け
共通鍵=同じ鍵で開け閉めする金庫。鍵を相手に渡す道中が危険。公開鍵=投函口は誰でも入れられるが、取り出せるのは郵便受けの所有者だけ。投函口（公開鍵）はネットに晒してOK、取出鍵（秘密鍵）は厳重保管。ハッシュ=シュレッダー。原本に戻せないが、同じ書類を投入すれば必ず同じ「散乱パターン」が出る。

ハイブリッド暗号 — TLSで実際に使われる形

公開鍵暗号で共通鍵そのものを安全に交換し、以降の大量データ通信は共通鍵で行う。「速度の共通鍵」と「鍵配送の公開鍵」のいいとこ取り。

公開鍵暗号と署名 — 役割の違い

同じ公開鍵ペアでも、「誰の鍵で暗号化し」「誰の鍵で復号するか」で意味が真逆になる。試験で最も間違えやすいポイント。

① 暗号化（機密性）

  • 受信者の公開鍵で暗号化
  • 受信者の秘密鍵で復号
  • 「鍵を誰でも投函できるが、開けるのは受信者だけ」
  • 用途：データの秘匿（盗聴防止）

② 署名（真正性・否認防止）

  • 送信者の秘密鍵でハッシュを暗号化（=署名）
  • 送信者の公開鍵で復号して検証
  • 「自分にしか押せない印鑑を押す」
  • 用途：本人確認・改ざん検知

署名検証のシーケンス

送信者 Alice
秘密鍵保有
受信者 Bob
Aliceの公開鍵保有
①Alice：ハッシュ化 — H(M) ＝ ダイジェスト
②Alice：自分の秘密鍵でダイジェストを暗号化 → 署名 S
③Alice→Bob：M（平文）と S（署名）を送信
④Bob：受信した M を再ハッシュ → H(M')
⑤Bob：Aliceの公開鍵で S を復号 → ダイジェスト D
⑥Bob：H(M') == D ならば「本人が送り、改ざんされていない」

署名アルゴリズムの選択

アルゴリズム鍵長速度用途
RSA-20482048bit遅い・大きい従来主流。互換性◎
RSA-PSS2048bit以上同上より安全な署名フォーマット
ECDSA (P-256)256bit速い・小さいTLS証明書の主流

OAuth 2.0 / OIDC / SAML

位置づけの違い

仕様主目的規格元主流域
OAuth 2.0認可の委譲（権限の貸与）IETF (RFC 6749)API認可
OpenID Connect (OIDC)認証（誰なのか）+ OAuth 2.0OpenID FoundationSNSログイン・モバイル
SAML 2.0認証アサーションの連携（XMLベース）OASIS企業SSO・基幹SaaS
「認証(Authentication)と認可(Authorization)を混同しない」—— 認証は「誰か」、認可は「何ができるか」。OAuth単体では認証用途に使ってはならない（user-id を id_token のように扱うと脆弱）。OIDCがOAuth上に認証の標準を定義したのはそのため。

User
Client App
認可サーバ
リソースサーバ
①Client：code_verifier（ランダム）生成 → SHA-256 → code_challenge
②Client→認可サーバ：認可リクエスト（client_id, redirect_uri, code_challenge, scope）
③User→認可サーバ：認証 + 同意
④認可サーバ→Client：認可コード（ブラウザリダイレクト）
⑤Client→認可サーバ：トークン要求（code + code_verifier）

※PKCE（RFC 7636）により認可コード盗聴があっても code_verifier がない攻撃者は token に交換できない。

JWT — alg=NONE攻撃（R6春問1の論点）

JWT (JSON Web Token) は header.payload.signature の3部構成。header の alg フィールドに "none" を指定して署名なしで送る攻撃がある。古いライブラリは「アルゴリズム none ＝署名検証スキップ」と解釈し、改ざんペイロードを通してしまう。

対策1：許可するアルゴリズムを明示的にホワイトリスト（RS256のみ等）。jwt.verify(token, key, {algorithms:['RS256']})
対策2：HS256とRS256の混在に注意（鍵混同攻撃: 公開鍵をHS256のシークレットとして使う）
対策3：有効期限（exp）と発行者（iss）と対象（aud）の3つを必ず検証
R3春 PM1問1 旧過去問より — SAMLによるSSO実装
旧形式時代の認証SSO問題。複数のSaaS利用環境で各サービス独立のID管理が運用負担となっており、SAMLによるSSO化を設計する。採点ポイントの3要素：①IdP（認証主体）とSP（サービス側）の分担、②SAMLアサーション（XML）への署名と検証、③ブラウザリダイレクトを介した受け渡し。新形式でも複合シナリオの一部として頻出。OIDCとの違いも問われやすい（SAMLはXML/SPベース、OIDCはJSON/JWT/モバイル親和性高）。第14章Q40参照。
H29秋 PM1問3 / H29秋 PM2問2 旧過去問より — TLS暗号スイート＋HSTS／鍵階層 KEK/DEK
2017年（黎明期）の連続出題テーマ。①TLSサーバ運用＝RC4・3DESなど脆弱な暗号スイートの無効化、AES-GCM等の強い暗号のみ許可、HSTSヘッダでブラウザを強制HTTPS化。②データ暗号化設計＝KEK/DEK鍵階層でDEK（データ毎の鍵）をKEK（マスター鍵）で暗号化保管。HSMでKEKを保護すれば、DBごとDEKが漏えいしても復号不能。大量データのDEK更新が不要になり運用コストが下がる。両者とも現代の暗号運用設計の基礎であり、TLS 1.3時代でも考え方は不変。第14章Q52/Q54参照。
H29春 PM1問3 旧過去問より — OAuth 2.0アクセストークン検証
クラウド認証連携の黎明期出題。OAuth 2.0アクセストークンの検証方式として2方式の対比が問われた。①イントロスペクション方式＝認可サーバへ毎回問合せ、常に最新の失効状態を反映できるが認可サーバ負荷大。②JWT自己完結型＝署名検証のみで即可否判断、スケールしやすいが失効反映が遅延。失効性 vs 性能のトレードオフが中心論点で、短い有効期限＋リフレッシュトークンの組み合わせで折衷するのが現代の正解。第14章Q56参照。

サイドチャネル攻撃と対策

R7秋 問2「鍵管理と暗号通貨」で電磁波解析が出題

サイドチャネルとは — 「鍵を直接取らずに横から漏らさせる」

暗号アルゴリズム自体が数学的に堅牢でも、実装しているハードウェア/ソフトウェアの「副次的な情報」から鍵を推測する攻撃。観測対象は処理時間・電力消費・電磁波・キャッシュアクセスパターン・音響など多岐にわたる。

たとえ話：金庫破りの上級技
普通の泥棒は鍵穴をピッキングする（暗号解読）。サイドチャネル攻撃者は金庫が動く時の音・温度・電気使用量を計って、内部のダイヤル位置を割り出す——金庫を1ミリも触らずに番号を当てるイメージ。

主要なサイドチャネル攻撃

攻撃観測対象典型シナリオ
タイミング攻撃処理時間の差パスワード文字列比較が「1文字目で違えば即return」だと、文字単位で総当たり可能
電力解析（SPA/DPA）消費電力波形ICカードのRSA処理時、ビット0/1で消費電力が違うことから秘密鍵ビットを逐次推定
電磁波解析（EMA）放射電磁波R7秋問2の論点。HSM/ICカードに非接触で近接アンテナ測定
音響解析CPUコイル鳴きマイクでRSA鍵抽出（GenkinらRSA音響解析）
キャッシュ攻撃L1/L2キャッシュアクセス同一CPU上の他プロセスからAES鍵を抽出（Flush+Reload, Spectre）
故障注入（FI）—（能動的）電源グリッチ・レーザでビット反転を起こし、誤動作からの差分解析

対策の3層

アルゴリズム層
定数時間実装 / マスキング / シャッフリング / ブラインディング
実装層
分岐の排除 / 配列アクセスの非依存化 / RSA-CRTのチェック
物理層
耐タンパHSM / 電源フィルタ / シールドケース / センサ

HSMとは何か（再確認）

HSM（Hardware Security Module）は秘密鍵を外部に取り出せない専用ハードウェア。FIPS 140-2/140-3 Level 3以上では物理開封でゼロ化される。クラウドではAWS CloudHSM, Azure Dedicated HSM, GCP Cloud HSM。サイドチャネル耐性試験もFIPS 140-3で強化された。

記述で問われやすい論点

「なぜ非接触で攻撃できるか」 → ICチップが動作する際に放射される電磁波/消費電力の波形に、処理しているビット列の情報が含まれているため
「対策となる実装」 → 定数時間実装・マスキング（中間値の乱数化）・耐タンパHSMの利用
「鍵更新の意義」 → 1つの鍵で十分なサンプル数を観測される前にローテーションすれば攻撃難度が上がる

過去問記述演習

R7秋 問2「暗号通貨ウォレット鍵管理」

設問1：HSMから鍵が漏えいする可能性
耐タンパHSMに格納した秘密鍵が、HSM自体を攻撃者が物理的に保有した場合に外部抽出される懸念がある。サイドチャネル攻撃の観点から、攻撃者が観測する物理量を1つ挙げよ（20字以内）。
模範解答（10字）：放射電磁波
別解：消費電力波形（8字）/ 処理時間（4字）
採点ポイント：サイドチャネル攻撃の観測対象を具体的に1つ挙げる。
設問2：ソフトウェア実装側の対策
RSA秘密鍵を扱うコードに対し、タイミング攻撃を防ぐためにソースコードレベルで実装すべき対策を1つ挙げよ（30字以内）。
模範解答（25字）：条件分岐に依存しない定数時間実装にする。
別解：「ブラインディングを適用する（13字）」も可。
採点ポイント：処理時間が秘密値に依存しない仕組み（定数時間/マスキング/ブラインディング）に言及。
設問3：鍵更新（ローテーション）の意義
サイドチャネル攻撃に対する運用面での対策として、定期的な鍵更新（ローテーション）が有効である理由を述べよ（35字以内）。
模範解答（33字）：攻撃に必要な観測サンプル数が集まる前に鍵が無効化されるため。
採点ポイント：「サイドチャネル攻撃が統計的に多数のサンプルを必要とする」点と「鍵更新で攻撃のタイムウィンドウを閉じる」両方に言及できると満点。
設問4：JWT alg=none
R6春応用：JWT検証ライブラリで jwt.verify(token, key) とのみ呼び出している。alg=none攻撃を防ぐためソースに加えるべき修正を述べよ（30字以内）。
模範解答（28字）：algのホワイトリスト（RS256のみ等）を指定する。
採点ポイント：「許可するアルゴリズムを明示する」ことに言及。
